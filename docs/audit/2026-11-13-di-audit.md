# DI performance, architecture and stability audit — 2026-11-13

## Outcome and scope

The audit confirmed six localized defect families in cache identity, memory retention, availability coherence and reentrant registration. They were reproduced against identified pre-fix sources, corrected within the existing architecture, covered by public behavior tests, independently reviewed, and pushed to the existing `main` branch in seven source/test slices. The cache and resolution architecture was not replaced.

Three additional lifecycle failures remain reproducible and require an explicit ownership/retirement protocol. Their [next-major specification](../plans/definition-owner-lifecycle.md) describes the concrete API, publication order, compatibility cost and acceptance tests. The unavailable-attribute performance investigation also produced measured results and counterexamples: its faster prototype changes observable autoload behavior and was not adopted. The [availability plan](../plans/attribute-availability-performance.md) now distinguishes completed experiments from unresolved contract choices.

The starting commit was `65da4acc18b19989041a2813dbc92f2f474b7177`. Final production/test verification belongs to **32b1142ede099e398cba03961372584aef069e69**; documentation is published afterwards. Machine-readable observations, commands, runtime/source identities and CI results are in [2026-11-13-evidence.json](2026-11-13-evidence.json). This report extends the [November 12 audit](2026-11-12-cache-parity-recheck.md); it does not treat yesterday's results as proof for today's changes.

The reviewed boundaries include canonical and requested-entry caches; aliases and deferred delegators; definition selection and factory/ClassDefinition ownership; callable signatures and native magic dispatch; prepared parameters; attributes, object phases and late discovery; request-source/provider isolation; external containers; failure recovery, in-flight mutations and Fibers. The central question was whether reusing metadata or a warmed result changes current values, object identity, discovery timing, exception behavior or lifetime.

### F1 — Preserve native static dispatch and shared identity

`DelegatorRegistry::dependencyIds()` now recognizes a known native static callable with `is_callable([$owner, $method])`, including PHP magic dispatch. It no longer requires a declared public static method to avoid recording an owner-service dependency. The complete string service ID remains a dependency where service resolution can override that callable, so replacing an actual deferred callable still invalidates the result.

Four cases cover declared static, dynamic magic, inaccessible instance-method and inaccessible static-method dispatch. Two failed before the fix and two were successful controls. All four pass with 32 assertions on both runtimes. Related tests verify replacement, same-owner identity and normal deferred dependency invalidation. This changes classification at registration, not the ordinary shared lookup path.

A final review found the same unwanted owner dependency when the first class probe misses but the fallback interface probe loads the class. The owner is already present at the end of registration, yet both probe return values can be false. The follow-up adds a loaded-only class check, preserving the existing autoload attempts. Its before/after fixture compares an already loaded owner with a class alias declared on the second probe: before correction one case fails and five controls pass; the final six-case file passes with 38 assertions on both runtimes. Late unresolved non-static owners retain conservative dependency tracking.

### F2 — Do not cache an unbounded history of magic method names

`CallableExecutor::plan()` preserves its normal cache-hit fast path. When the selected callable refers to a nonexistent method, it now returns the existing native invocation fallback without publishing a per-name null cache entry or constructing a reflection exception. Real declared methods retain signature caching; runtime receiver binding and native argument handling remain current.

The public regression exercises instance-array, static-array and static-string forms using 512 distinct long names. Each form retained about 4.23 MB before correction and passes the bounded fixture budget afterwards. That test budget is not a production cache limit. A separate native-dispatch control covers unusual spelling, repeat calls and embedded NUL behavior; PHP's own method-name handling is the reference.

A 50,000-name probe in five batches measured the following sum of retained-memory deltas on both runtimes:

| Path | Retained bytes across five batches |
| --- | ---: |
| Original DI path | 12,222,704 |
| Corrected DI path | 1,880 |
| Native invocation control | 1,880 |

This removes approximately 12.2 MB of name-history retention in that workload. It does not claim that a process never grows or that named metadata for arbitrarily many loaded classes is bounded. Discarding the null cache alone roughly doubled the reused-magic cost in the exploratory benchmark because reflection exceptions were repeated. The selected early native-fallback check avoids that regression: reused instance magic measured about 1.46 µs on PHP 8.4 and 1.57 µs on PHP 8.5, within the original sample range; unique instance magic measured about 1.52 and 1.65 µs. These local samples justify the implementation choice, not a general throughput percentage.

The final pre-fix regression had three failures and one native-behavior control passing on each runtime; after correction all four cases pass with 35 assertions. Expanded callable/parameter coverage also passed.

### F3 — Observe a class loaded by the fallback probe in the same poll

The registry first calls `class_exists($name)`, then `interface_exists($name)`. A stateful autoloader can return no declaration on the first call and declare a class during the second. `interface_exists` still returns false because the new declaration is a class. Previously the registry kept its old generation even though the class was now loaded.

The concrete public failure used a private-constructor class with a then-unavailable `NoConstructor` attribute. After warming `has() === false`, the fallback loader made the attribute available. Cached plans still returned false on the first lookup; a public no-op composition rule, which disables semantic-plan memoization, returned true with the same two loader calls. A second cached lookup repaired itself.

The correction adds `class_exists($name, false)` after the fallback probe. It recognizes the declaration without invoking another loader, preserving both existing autoload attempts and exception timing. Thirteen cases cover native classes, aliases, interfaces, first/fallback discovery, absent names and throwing loaders. Four failed before correction; all thirteen pass afterwards. No attribute instance, constructor or handler is eagerly executed to refresh availability.

### F4 and F5 — Keep the operation target stable and its dependency view current

Validation is not necessarily a pure metadata step: loading a definition class can execute application autoload code, including nested container mutations. `set()` must retain the canonical target it validated, while deriving affected deferred dependencies from the graph that exists after successful validation.

F4 passes the already captured canonical ID to the existing invalidation helper. The original source and its decorated siblings refresh; a nested alias retarget remains effective; the other source and its siblings retain exact shared identity.

F5 moves the existing deferred-dependency scan after registration/base publication. It uses the current graph, not a union of old and new dependencies. The regression explicitly covers an incoming dependency, a stable dependency and an outgoing dependency. The nested alias operation already invalidates the outgoing old relationship; reusing the obsolete pre-validation list would wrongly discard its valid newly warmed result. Both `ClassDefinition` and `InvokableDefinition` are covered. Each two-case file fails on its pre-fix source and passes with 26 assertions after correction.

Neither change introduces a general service graph. Replacing an ordinary constructor dependency still does not rebuild every existing shared consumer; the scan covers the container's declared deferred-delegator dependencies.

### F6 — Validate first, recheck the protected target, then publish

Callable preparation now performs the existing normalization and dependency classification before publication. `Container::delegator()` then resolves the current alias target and checks protection again, before the internal registry appends the prepared specification. There is no second callable validation/autoload pass after that check. The internal registry's only production caller was migrated; no public extension interface changed.

The three cases cover retargeting the requested alias, retargeting its ancestor, and a permitted ordinary-service retarget. The first two failed before correction. All three pass afterwards with 28 assertions on both runtimes, including no partial pipeline, preservation of the successful nested mutation, successful retry and unaffected sibling identity. Fourteen adjacent files passed with 44 tests and 245 assertions per runtime. Existing cached-chain invalidation can still release objects after publication; its destructor boundary is the separate L3 architecture concern, so this fix does not claim that all user code becomes impossible after validation.

This is a trusted configuration/reentrant-autoload invariant failure, not evidence of a remotely reachable exploit. The protected core service itself was not replaced; the incorrect result was reachable through a newly decorated alias. The fix restores the existing protected-target rule and keeps an ordinary alias retarget valid.

## 2. Cache-equivalence and stability checks

A single universal cache-off switch would not be a faithful oracle for this container: `get()` intentionally shares and decorates, while `make()` creates through local entry resolvers. The audit used narrower independent references:

- Public no-op composition rules disable semantic-plan memoization while preserving the supported rule path. These expose discovery/value differences without pretending that `get()` and `make()` have identical lifecycle contracts.
- Native PHP invocation supplies the reference for magic names, argument spelling and receiver behavior.
- [MutationParity.php](reproductions/MutationParity.php) compares a warmed container with a newly constructed container replaying the same mutation history without prior reads. Twelve deterministic seeds exercise 600 mutations across 24 observable IDs: **14,400 value comparisons per runtime**. The fixture includes base/decorator replacement, alias retargeting and direct/deferred/transitive decoration. It fails on unexpected exceptions or types rather than treating them as successful comparisons.
- Dedicated public tests check exact shared identity, invocation counts, failure recovery and suspended-resolution revision protection. The value-only replay probe does not establish those properties on its own.
- Weak references, with fixture-owned references deliberately dropped, distinguish object retention from allocator/RSS behavior. In-flight and application-owned objects are allowed to remain alive.

| Boundary | Evidence and conclusion |
| --- | --- |
| Base versus requested result | Source changes invalidate affected siblings; requested decoration preserves unrelated source/sibling identity. F1/F4/F5 close additional invalidation mistakes. |
| Deferred callables | Current owner binding, aliases, full-string service overrides and transitive declared dependencies remain observable; F6 closes publication after a stale protection check. |
| Attributes and object phases | Cached/non-memoized paths preserve late discovery, completed-phase guards, pending-instance lifetime and no replay; F3 closes same-poll fallback discovery. |
| Callable and parameter metadata | Metadata remains reusable without storing invocation values or receiver state. Dynamic magic misses no longer grow the name cache. |
| Request sources and providers | Existing request parity/provenance suites verify fresh request/provider values, null/false, mapping validation and failure recovery. No new request caching defect was confirmed. |
| External ownership and protected core IDs | Live external lookup precedence and local protected ownership remain under their existing contracts. No external ownership cache or global dependency rebuild was added. |
| Failures and Fibers | Existing in-flight mutation, concurrency/cycle and recovery contracts remain in the complete suite. The unresolved destructor cases below are reported separately, not hidden by passing ordinary tests. |

## 3. Remaining lifecycle defects and the architecture they require

The following are confirmed on both PHP 8.4.23 and 8.5.8 and remain present in the final 5.x source:

| Finding | Reproduction | Consequence |
| --- | --- | --- |
| L1 — obsolete definition owner retains configuration | [DefinitionLifecycle.php](reproductions/DefinitionLifecycle.php), cross-owner factory → invokable transition | The new resolver is selected, but the old factory and its captured payload stay reachable until container disposal. The control replacing one factory with another releases both. |
| L2 — throwing factory destructor interrupts publication | Same script, warmed factory replaced within the same owner | The new factory is installed, `set()` reports a configuration exception, `get()` retains the old shared value and `make()` uses the new definition. |
| L3 — throwing cached-wrapper destructor interrupts family invalidation | [CacheRetirement.php](reproductions/CacheRetirement.php) | After replacing a source, the first alias and source use `new`, but a later sibling still returns `old`. |

L1 is bounded by the obsolete registration retained by each former owner for an ID; the evidence does not show unbounded growth on every repeated owner switch. L2/L3 require destructors that throw at the release boundary. They are real consistency failures in dynamic mutation, but are not evidence that ordinary construction or shared retrieval is unstable in every application.

The current public `DefinitionAwareResolverInterface` only registers definitions. It provides no way to detach a previous owner's configuration or hand its lifetime to the container. Initial declarative definitions live in leaf maps before `CompositeResolver::definitionOwners` records any runtime owner, so cleaning only that map would miss them. During cache invalidation, `EntryCache` and `DelegatorRegistry` also release user objects while still traversing the affected graph.

A local unconditional invalidation-on-error would change the documented identity behavior of rejected registrations. Concrete-type cleanup would miss custom/nested resolvers and couple the orchestrator to a leaf implementation. A void removal method would still permit destruction before invalidation completes. These alternatives do not establish the required behavior at the public extension boundary.

The selected next-major design adds required definition removal and a **`MutationRetirement` holder** returned by definition replacement/removal. Existing resolvers remain the owners and execution paths. The container combines detached definitions, replaced base values, evicted requested results and discarded callable chains into one operation-local holder. It finishes publication, revisions, indexes and all affected invalidations before releasing those roots. Release failures become a distinct committed-state exception; validation rejection remains separate. No outer binding/cache writes occur after release starts, so a destructor's nested successful mutation is not overwritten by unfinished outer work.

This gives a concrete foundation for safe runtime reconfiguration, bounded ownership, custom resolver conformance, nested composites and predictable failure recovery. It changes the public resolver interface and therefore belongs in the next major. The proposal covers all four runtime registration mutations—`set`, `alias`, `delegator`, `addContainer`—because they share release-sensitive helpers. It adds no work or holder allocation to ordinary `get()` cache writes, no service shutdown API, no general rollback, no forced GC and no persistent cleanup queue.

The [specification](../plans/definition-owner-lifecycle.md) fixes the API, bootstrap cleanup, nested mutable-owner uniqueness, direct caller obligations, raw-value `set()`/fresh-`make()` preservation and multiple/reentrant destructor behavior. Its three implementation slices are: coherent ownership/publication/retirement; extension/nesting/Fiber conformance; consumer migration/documentation and complete verification. That architecture was independently reviewed; it has not been implemented during this audit.

## 4. Performance findings and decisions

### Normal paths

The unchanged stock harnesses ran against the immutable starting source with the same installed dependencies. Optimized Composer classmap entries and autoloaded DI functions were remapped to the selected snapshot; reflection checks reported zero source violations. Ordinary harnesses used CLI OPcache on, JIT disabled, 30,000 runtime operations and 1,000 builds. Each harness's aggregation remains explicit in the evidence; the generated-versus-reflection fixture is not presented as a fair cold-start comparison.

| --- | ---: | ---: |
| Build default container | 62.252 | 65.625 |
| Build representative container | 88.232 | 83.660 |
| `make`, no arguments | 5.036 | 5.556 |
| `make`, autowiring | 10.500 | 11.840 |
| Call reused closure | 13.257 | 14.169 |
| Call fresh closure | 14.509 | 13.691 |
| Call method array | 6.684 | 6.778 |

These are baseline diagnostic measurements, not final-fix speedups, cross-host comparisons or an application request-latency prediction. Prepared plans avoid repeated classification. An explicit factory avoids responsibilities of general reflection/attribute processing; its lower fixture cost is not proof that the two paths are interchangeable. Nothing here justifies replacing the component with a compiler or persistent object graph.

### Unavailable attributes remain the measurable performance issue

The availability harness uses independent containers, OPcache off, seven rounds of 10,000 operations and an instrumented loader. A previously inspected unrelated class with unavailable annotations increases later plain `make()` work:

| Registry state | PHP 8.4 baseline, µs | PHP 8.5 baseline, µs | Missing-name loader calls/op |
| --- | ---: | ---: | ---: |
| Clean | 5.120 | 5.502 | 0 |
| One unavailable annotation | 22.057 | 25.278 | 22 |
| Eight unavailable annotations | 132.175 | 137.716 | 176 |
| Shared `get`, all three states | 0.200–0.202 | 0.199–0.205 | 0 |

The stable evidence is the exact repeated probing, identical in every round. The nominal revision getter scans all unavailable names and can invoke arbitrary autoload code even when validating an unrelated target's cache. Timings include instrumentation and should not be combined with the OPcache-enabled table above.

Prototype A retained polling locations but suppressed the second autoload attempt. Counts fell to 11/88, and exploratory one/eight-name latency fell to about 14.66/74.97 µs on PHP 8.4 and 16.65/79.60 µs on PHP 8.5. Fifteen preservation suites passed on baseline and prototype. Nevertheless, the 56-process isolated comparison proved that a second-attempt class/interface/alias appears later and a second-attempt exception moves to a later poll. The prototype is not transparently equivalent and was not copied into production. F3 instead fixes the discovered stale revision while retaining the existing attempts.

The updated [availability plan](../plans/attribute-availability-performance.md) includes the complete observation matrix and a source-level checkpoint map across discovery, parameters, object phases, direct APIs, bootstrap and lazy/proxy initialization. A root-only refresh is insufficient: an unchanged loader can become ready inside an earlier dependency without directly declaring the attribute. A TTL, miss cap or autoloader-list identity check does not preserve that behavior.

The potential architectural benefit is separating a cheap coherent-generation read from explicit availability synchronization, or limiting unresolved-name work to relevant targets. Either direction must define which loader side effects may change and cover every required checkpoint. The current evidence supports keeping existing behavior until that contract is explicit; it does not support an unqualified implementation-ready optimization.

After all seven fixes, ten sequential smoke processes passed on `32b1142`: all four ordinary harnesses plus availability on both runtimes. Ordinary smoke workloads used 10,000 operations and 1,000 builds; availability used 1,000 operations and three rounds. The latter retained exactly **22/176 missing-name calls per operation in every round**, with zero on clean/shared paths. Its final medians were:

| --- | ---: | ---: |
| Clean `make()` | 4.896 | 5.628 |
| One unavailable annotation | 21.479 | 24.626 |

This smaller smoke is an integration/count check, not a matched latency comparison with the baseline. The portable G1 matrix also ran in 28 fresh final-source processes. Outcomes, events, exception timing and constructor/handler counts match the original baseline except for the intended class/alias revision correction: the first poll now returns 1 instead of 0 while retaining exactly two loader calls. All preloaded controls make zero loader calls. Source-map checks had zero violations, and all 161 production file hashes still matched the final commit afterwards.

## 5. False positives rejected and limits

- The reflection dependency's closure reflector store was examined using weak references. Replaced/rejected closures and captures were collectable on both runtimes, including before an explicit reflector clear. No dependency rewrite is justified by that suspicion.
- Native dynamic `ReflectionProperty` probes did not retain the source object in the tested cases. The established `ReflectionObject` lifetime exclusion remains covered separately.
- Native PHP magic-name handling, including embedded NUL behavior, is not a DI defect. The corrected regression compares native invocation rather than assuming a different string contract.
- Custom parameter `supports()` classifies immutable target metadata. State-dependent values belong in `resolveParameter()`, which is called again. Violating an extension contract is not evidence that valid parameter caching is stale.
- Closure plans intentionally avoid long-lived capture ownership. Replacing that behavior with a strong global closure cache would create a new lifetime problem.
- `get()` sharing/decorators/external precedence, `make()` local fresh creation, `ClassDefinition`'s explicit lifecycle and configuration-level lazy-value policies remain distinct contracts. Missing proposed union-autowiring/callback features are not current regressions.
- The deterministic replay probe checks pure-value histories, not arbitrary third-party callbacks, destructors or concurrency. Dedicated tests and the documented lifecycle reproductions address those separate properties.

This is a bounded executable audit, not a proof that all application extensions are correct or that every workload is faster. Supported ordinary paths and the new concrete failures were verified; the three unresolved lifecycle failures remain clearly identified.
