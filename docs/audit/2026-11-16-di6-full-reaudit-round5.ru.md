## 2. Исправленные дефекты

### INV-EX-1: конструктор invokable терял тип и identity DI-исключения

**Проблема.** `InvokableResolver::resolveDefinition()` оборачивал любое исключение конструктора в `ResolutionException`. Если конструктор повторно запрашивал тот же сервис, внутренний `CircularDependencyException` терял публичный подтип и идентичность объекта на внешней границе. Обработчик, рассчитанный на конкретное DI-исключение, работал иначе, чем для остальных путей создания.

**Исправление.** [InvokableResolver](../../src/Resolver/Entry/InvokableResolver.php) сначала повторно выбрасывает `ExceptionInterface`; существующая нормализация остальных `Throwable` сохранена. Исходный объект исключения, цепочка зависимости и владелец диагностики доходят до вызывающего кода. Сторонняя ошибка конструктора по-прежнему превращается в `ResolutionException` с исходным `previous`. Прямой вызов конструктора без аргументов и отдельный от атрибутов жизненный цикл invokable сохранены.

**Доказательство.** [InvokableExceptionContractTest](../../tests/Contract/InvokableExceptionContractTest.php) проверяет реальную рекурсию конструктора через общий `get()` и свежий `make()`, точную identity исключения, цепочку цикла, число вызовов и восстановление после сбоя. Сторонние исключения служат отрицательными контролями. На каждой стабильной версии PHP исходный код дал **2 failed / 2 passed / 16 assertions**, исправленный — **4 passed / 28 assertions**. Связанные тесты и полный набор проходят. Коммит: [`5067bf7`](https://github.com/componenta/di/commit/5067bf78d3b949531b807f572d000319e7e14c7e).

### PROXY-CTOR-1: допустимость proxy ошибочно требовала публичный конструктор

**Проблема.** При проверке virtual proxy [MakeHandler](../../src/Resolver/Attribute/Handler/MakeHandler.php) вызывал `ReflectionClass::isInstantiable()`. Это отклоняло конкретный класс с private/protected конструктором, даже если создание реального объекта принадлежало пользовательской фабрике либо уже поддерживаемой политике `NoConstructor`. Предварительная проверка не давала допустимой стратегии выполнить свою работу.

**Исправление.** Теперь явно отклоняются interface, trait, abstract и enum. Доступность конструктора проверяется выбранным путём создания реального объекта. Проверки совместимости типов, результата фабрики, ограничений стандартного нативного адаптера и передачи управления пользовательскому адаптеру сохранены. Фабрика вызывается при отложенной инициализации; D1 по-прежнему отклоняет неподдерживаемый propertyless target на границе стандартного адаптера.

**Доказательство.** [NonPublicConstructorProxyContractTest](../../tests/Contract/NonPublicConstructorProxyContractTest.php) охватывает private/protected конструкторы через параметры и свойства, отложенный вызов фабрики, identity proxy/backing, `NoConstructor` вместе с setup, четыре недопустимых вида классов и два propertyless-контроля. На окончательных байтах теста каждая версия PHP дала **8 failed / 4 passed / 24 assertions** до исправления и **12 passed / 82 assertions** после. Коммит: [`ce0c0a6`](https://github.com/componenta/di/commit/ce0c0a6414d649eb86bf099cc88f2559b63baa1e).

Полный CI затем выявил unused-trait в новой фикстуре: адресная проверка PHPStan его не обнаружила. Коммит [`eefedd0`](https://github.com/componenta/di/commit/eefedd038090e686c06bca44f1dfa4e496af4280) использует этот trait в уже проверяемом абстрактном классе. Исключение из правил анализатора не добавлялось. Полный PHPStan и те же RED/GREEN-проверки на окончательных байтах пройдены. Промежуточный неуспешный CI и заменённые доказательства сохранены с явными пометками.

### REPRO-RUNTIME-ID-1: повтор серии PHP перезаписывал логи benchmark

**Проблема.** [run-cycle-guard-benchmark.py](reproductions/run-cycle-guard-benchmark.py) принимал несколько `--php`, но включал в имена логов только major/minor. Две сборки PHP 8.4 писали в одни файлы. Повтор идентичной версии дополнительно смешивал статистические группы; хеши в записи переставали соответствовать перезаписанным файлам.

**Исправление.** Runner определяет версии всех выбранных бинарников до создания output directory, обхода исходников и измеряемой работы. Повтор major/minor отклоняется с указанием обеих конфликтующих пар binary/version. Одна PHP 8.4 и одна PHP 8.5 поддерживаются. Сравнение patch-версий одной серии требует отдельных новых каталогов. В [инструкции воспроизведения](reproductions/OptimizationReproduction.md) закреплено это условие и снято прежнее утверждение о полном совпадении текущего драйвера с историческим. Worker, измеряемые участки и старые результаты не менялись.

**Доказательство.** Детерминированная фикстура протокола subprocess запускает реальные старую и новую Python-программы с синтетическими ответами PHP worker. Старый runner выполнял восемь workers, оставлял четыре уникальных stdout-файла; четыре сохранённых хеша уже не совпадали. Новый runner возвращает exit 2, не вызывает workers, не обходит исходники и не создаёт output. Контроль с разными сериями 8.4/8.5 сохраняет восемь файлов без перезаписи. Отдельные запуски с настоящими PHP 8.4.27 и 8.5.12 подтверждают отказ при повторе бинарника до обращения к отсутствующим source directories. Это доказательство корректности драйвера, а не замер PHP. Коммит: [`42b62af`](https://github.com/componenta/di/commit/42b62afd9c6a57caa0db3916585e823ab6ebaafa).

**Мутационный анализ.** Завершённый запуск создал **4276 мутаций в 115 файлах**: **3749 `tested`, 59 `timeout`, 468 `untested`**. **MSI Pest — 89,06%**, формула `(tested + timeout) / total`, то есть `3808 / 4276`. Доля завершённых результатов `tested` отдельно — **87,68%** (`3749 / 4276`); знаменатель здесь по-прежнему включает все мутации. В plugin v4.0.1 категория `tested` означает, что worker завершился с неуспешным exit status. Это не независимое доказательство семантического assertion failure для каждого worker. Категория `untested` означает успешное завершение worker: мутация пережила этот прогон. Сумма категорий совпадает с общим количеством, остатка pending или uncovered нет.

Свежий каталог из 468 survivors содержит **458 сохранившихся ID, 10 добавившихся ID и 19 отсутствующих ID из прежнего каталога**. Для всех десяти добавлений найден единственный предшествующий печатный diff мутации в двух изменённых production-файлах: девять полных diff context совпадают, у одного совпадают изменённые строки при обновлённом соседнем guard. Все десять пар проверены по окончательному коду. Ещё девять прежних записей больше не входят в `untested`; само отсутствие не устанавливает, получил worker категорию `tested` или `timeout`. Свежий каталог, таблица соответствий и индивидуальные уточнения сохранены отдельно от исторического каталога из 477 записей.

### Как трактовать мутационный анализ

Разобраны все **477 survivors предыдущего завершённого каталога**: по каждой записи сохранены точный diff, причина классификации и ограничения. Области: 227 core, 146 attributes, 104 parameters/callables/request. В реестре различаются эквивалентность в конкретном текущем пути, избыточные проверки, изменения только стоимости, неиспользуемые/native helper-границы и кандидаты на поведенческие пробелы.

Из прежнего каталога на обеих стабильных версиях выполнены **восемь точных мутаций**: семь теперь обнаруживаются новыми публичными тестами, одна остаётся GREEN под конечными проверками времени жизни. Для остальных **469 записей** выполнен только статический разбор. Клонирование владельца фабрики — отдельная синтетическая мутация вне каталога. Из этих адресных проверок не выводится показатель мутационного анализа всего набора.

Отдельно выполненная мутация времени жизни `090c1a0b20df101a` осталась GREEN под существующими **9 тестами / 19 assertions** на обеих PHP. Она меняет владение metadata и число записей WeakMap, сохраняя условие чтения из кеша. Эти конечные проверки не воспроизвели утечку и не доказывают глобальную эквивалентность или ограниченность удержания для любых графов объектов. Незапущенные кандидаты, касающиеся промежуточных побочных эффектов, взаимодействия источников revision и полноты диагностики параметра, остаются гипотезами о мутированном коде; они не являются подтверждёнными багами исходной реализации.

Свежая проверка также сузила несколько прежних статических объяснений. `Proxy` объявлен final и readonly, поэтому пример со stateful-наследником `Proxy` невозможен; для повторного `newInstance()` оставлена только явно незапущенная гипотеза о native materialization/coercion аргумента. PHP class alias может иметь имя, недопустимое в обычном объявлении класса, поэтому мутация sentinel-строки invokable классифицирована как искусственный literal edge, а не безусловная эквивалентность. Это исправления логики разбора, а не новые воспроизведённые дефекты библиотеки. Объединённый реестр содержит уточнённые текущие объяснения, а прежние записи сохраняет с явной пометкой superseded.

Свежие полные показатели CI учитываются отдельно от исторического каталога из 477 записей. Timeout выделены отдельно от завершённых результатов `tested` инструмента. Успешный порог MSI не доказывает эквивалентность каждого оставшегося survivor.

## 5. Безопасность

Проведён ручной аудит исходников, границ доверия и зависимостей. Управляемый координатор deep-security не был доступен среди подключённых инструментов; результат такого сканирования не заявляется.

**Модель доверия.** Definitions, callable specifications, атрибуты, автозагрузчики, обработчики расширений и реализации proxy/caster/validator принадлежат коду приложения. Значения HTTP-запросов, проходящие через PSR extraction/mapping, считаются недоверенными данными. Проверены приоритет authoritative source, происхождение полей после mapping, конфликты имени/типового ключа, transport callback suffix, приватные метаданные DI, границы конструктора/свойств, момент защитного отказа относительно побочных эффектов приложения и восстановление после ошибки.

Нового эксплуатируемого пути не подтверждено. В проверенных путях значения request не выбирают callback, класс или DI service: выбор задаётся метаданными приложения. Этот слой не разбирает raw stream/JSON и не десериализует присланные программы. Проекция object payload может вызывать его публичные PHP property hooks, поэтому сам объект parser/application остаётся частью доверенной границы расширения. Пользовательский validator, игнорирующий предусмотренное протоколом исключение при ошибке, не доказывает обход в стандартном pipeline.

Ограничения размера/глубины запросов и стоимости пользовательских callbacks остаются политикой приложения. Аудит не обещает очистку произвольных пользовательских исключений и trace от секретов. Результат проверки зависимостей относится к сохранённому установленному набору и времени проверки. Права workflows и закреплённые ссылки на actions прочитаны в составе 50 действующих файлов вне `src/` и `tests/`.

## 6. Архитектура и производительность

### Текущее распределение ответственности согласовано

Прослежены admission/snapshot definitions, публикация через прикреплённый root, invalidation и retirement после публикации; зависимости aliases/deferred и владение при Fiber; identity callable и время жизни metadata; общий цикл разрешения параметров и защищённый первый смысловой аргумент callback; происхождение request-данных; подготовка записи свойств; lazy/proxy initialization. Исправления сохраняют текущих владельцев и публичные контракты. D1/A реализован на границе стандартного нативного адаптера. Пользовательские proxy factories сохраняют свой механизм и обязанности по отложенным callbacks.

Действующие миграции и планы EN/RU прочитаны полностью: **14 файлов / 3440 строк**. Дополнительных исправлений контрактов в них не потребовалось. В русском README отсутствовал необходимый раздел о допустимости native laziness — он добавлен в `fb3f8e0`; затем обе языковые версии дополнены пояснениями двух production-fix.

### B2: стоимость поиска отсутствующих атрибутов требует отдельного решения

Свежий availability smoke на окончательных исходниках дал следующие результаты. Каждый случай: 10 000 операций, три раунда, 2000 warmup-операций перед раундом. Время включает считающий autoloader. Режимы OPcache у версий различаются; таблица не ранжирует скорость версий языка.

| Операция | Autoload отсутствующих имён на операцию, обе PHP | Медиана PHP 8.4.27 | Медиана PHP 8.5.12 |
|---|---:|---:|---:|
| Обычный `make()` без отсутствующих аннотаций | 0 | 4,360 мкс | 3,985 мкс |
| `make()` после наблюдения одной недоступной аннотации | 24 | 18,468 мкс | 17,432 мкс |
| `make()` после наблюдения восьми недоступных аннотаций | 192 | 108,282 мкс | 105,808 мкс |
| Прогретый общий `get()`, все три контроля | 0 | 0,131–0,133 мкс | 0,119–0,138 мкс |

Измерение устанавливает стоимость конкретного workload. Оно не является сравнением оптимизации до/после, оценкой задержки приложения или доказательством роста памяти. Исправления багов не обосновывались этими временами.

**Проблема и возможный выигрыш.** Долгоживущий контейнер, увидевший недоступные optional annotations, повторно проверяет эти имена на последующих границах разрешения. Если профиль реального приложения показывает существенную долю затрат здесь, B2 может уменьшить повторную работу, разделив явный refresh доступности и чистое наблюдение generation у существующих владельцев. У чистого пути и прогретого общего `get()` этой повторной работы нет.

**Почему требуется решение.** Autoload исполняет наблюдаемый код приложения. Уменьшение числа проверок может изменить момент появления class/alias, момент исключения loader и обнаружение несовместимого изменения metadata после уже выполненной части работы. Глобальный отрицательный кеш или неявная заморозка изменили бы эти контракты.

**План и критерии приёмки.** Сначала подтвердить workload и долю затрат в приложении. До G2 явно пересмотреть или заменить затронутые compatibility constraints G1: назвать разрешённые изменения момента discovery, исключений loader и побочных эффектов, зависящих от числа вызовов, обновить нормативный контракт и ожидания. Текущее решение G1 сохраняет polling; один лишь профиль workload его не отменяет. Затем в G2 определить владельца, точки refresh/наблюдения и обработку отказов: discovery в том же poll, запрет несовместимого изменения после выполненной работы, bootstrap, request/callback suffix, фазы объекта и deferred initialization. После этого в G3 квалифицировать изолированный B2-кандидат: публичные проверки поведения, проверка происхождения кода и последовательные парные замеры чистого пути, missing names, shared/fresh graphs, custom rules и startup. Ожидаемый выигрыш — измеренное сокращение повторных проверок при сохранении выбранной семантики. Пока необходимость workload или заменяющий контракт не определены, текущая реализация сохраняется. Подробный [план B2](../plans/attribute-availability-performance.ru.md) остаётся условным; G2/G3 заблокированы, production-участок не выбран.

### Большие холодные alias-графы: отдельная возможность оптимизации

Свежий разбор [AliasResolver](../../src/Internal/AliasResolver.php) подтверждает: конструктор проверяет каждую вставку обходом уже собранной цепочки target. Если длинная цепочка поступает в порядке от ближайшего к конечной цели alias, суммарный обход может быть квадратичным. Успешное разрешение использует сжатие пути; здесь речь о холодном построении. Исторический замер прошлого раунда включал конструктор и одно разрешение, поэтому его нельзя представлять как чистую стоимость lookup. Нового alias benchmark в этом раунде нет.

Если профили приложения оправдают такую работу, сначала раздельно измерить построение, холодное и прогретое разрешение на реалистичных размерах графа. Затем спроектировать общий обход visited/color с целевой сложностью O(V+E), сохранив выбранный приоритет ошибок, детерминированную цепочку цикла, непрозрачные/numeric-string IDs и проверки пустых/self-reference значений. Изменение alias через `AliasResolver::set()` в составе публичного `Container::alias()` должно остаться транзакционным: ошибочная проверка цикла не публикует карту и не сбрасывает корректный кеш; успешное изменение сохраняет invalidation потомков и deferred-зависимостей. Квалификация включает цепочки обоих порядков, ветвления, циклы, недопустимые IDs и mutation/reentrancy-контроли, затем ограниченные парные замеры и проверку памяти. Возможный выигрыш — снижение startup cost для необычно больших alias-конфигураций; ускорение прогретого общего `get()` не обещается. Это условное проектное направление, не новый блокирующий баг и не выполненная оптимизация.

### E1: ограничение native trait-callable PHP остаётся актуальным

Свежая самостоятельная проверка на зафиксированной стабильной PHP **8.5.12** прошла **2 из 10** случаев; восемь проверок scope/identity завершились несоответствием. DI в этой фикстуре не загружается. Прошли контроли named public callable default и inline attribute closure. Затронутые формы `self`, `parent` и private reference могут сохранять scope/identity первого класса, использовавшего trait. Точные ожидания и полученные значения включены в архив.

Результат подтверждает необходимость сохранять существующее ограничение E1. Он не требует вводить в DI слой перепривязки callback или повышать минимальную PHP для всего пакета. Библиотека сохраняет `^8.4`; новый нативный синтаксис выражений требует 8.5. Перед расширением поддержки нужно проверить подходящий выпущенный runtime полным native acceptance fixture, записать происхождение бинарника/исходников и получить корректное поведение всех затронутых форм. Процедура описана в [плане E1](../plans/php85-callbacks.ru.md). Исторические source-only наблюдения сохраняют свои идентификаторы. Хеш официального release archive свежего бинарника проверен отдельной записью сборки; собственные provenance flags семантического probe не переписаны в `true`.
