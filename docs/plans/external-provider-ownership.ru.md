# Динамическая смена владельца во внешних контейнерах

**Статус (2026-11-20): предложено; не реализовано.** Результат аудита **A20-C1** остаётся открытым. Отчёт сохраняет подтверждённую границу согласованности и решение, необходимое до изменения контракта внешних контейнеров. Он не разрешает внедрение нового протокола и не возвращает отозванную поправку с повторным `has()`. [English version](external-provider-ownership.md).

## Перепроверка после сохранения отчёта

Последующая [перепроверка доказательств](audit-architecture-recheck-2026-11-20.ru.md) содержит новые исполнения на PHP 8.4.28 и 8.5.13 после сохранения отчётов и [машиночитаемый вывод](audit-architecture-recheck-2026-11-20.json). Исторические коммиты и указания на отсутствие повторного запуска при первоначальном сохранении остаются историческими; новый отчёт добавляет последующее доказательство. Архитектурный вариант этой проверкой не реализован.

## 1. Область и подтверждённое последствие

DI учитывает зарегистрированные внешние PSR-11 контейнеры и инвалидирует локальные цепочки отложенных делегаторов, если новая регистрация получает их ID зависимостей. Произвольные изменения внутри уже зарегистрированного поставщика ему недоступны. Вызов `has()` поставщика может изменить владение другим ID, не меняя состав реестра. В результате регистрация способна опубликовать нового прямого владельца, сохранив старый зависимый shared-результат.

В воспроизведении есть два отложенных ID, `first.owner` и `second.owner`, и прогретый локальный shared service `first`. Ранее добавленный поставщик предоставляет callable для `first.owner`. Пока `addContainer($candidate)` проверяет `second.owner`, прежний поставщик перестаёт предоставлять `first.owner`. Кандидат предоставляет замену. После регистрации прямой `get('first.owner')` возвращает замену, но shared `get('first')` может вернуть тот же прежний объект со значением `first:previous`.

Этому контрпримеру нужны следующие условия:

- Проверяются как минимум два ID отложенных зависимостей.
- Локальный shared-результат, зависящий от первого ID, уже создан.
- Более ранний внешний поставщик первоначально владеет этим ID; более поздний кандидат способен предоставить его после потери владельца.
- Callback для другого ID изменяет первый ID после последнего значимого наблюдения первого.
- Изменение не проходит через мутацию DI или другой сигнал, меняющий наблюдаемое состояние реестра/alias.

Мутация происходит внутри callback, вызванного самой регистрацией. Не нужны изменение приложения между API-вызовами, некорректное поведение отсутствующего entry или параллельный поток. Воспроизводились варианты с вложенной регистрацией и без неё. Изменения поставщика между API-вызовами — связанный отдельный случай, которому также требуется явный сигнал.

Отчёт касается внешнего владения и уже существующего в DI графа отложенных зависимостей. Он не предлагает перестраивать обычные зависимости конструкторов или изменять ранее выданные приложению объекты. Реализованный [контракт владения определениями и освобождения](definition-owner-lifecycle.ru.md) отвечает за локальные регистрации и порядок освобождения; снимка непрозрачного внешнего состояния он не предоставляет.

## 3. Воспроизведение и отозванная поправка

Сохранить PHP-блок ниже как `owner-reproducer.php` вне checkout и выполнить:

```sh
php owner-reproducer.php /absolute/path/to/di
```

Использовать checkout указанного коммита с установленными development-зависимостями. [`tests/bootstrap.php`](../../tests/bootstrap.php) и [`ContainerBuilder`](../../tests/Support/ContainerBuilder.php) создают обычный контейнер и не копируют исследуемый алгоритм. Выполнять сценарий на каждой квалифицируемой версии PHP. Вместе с коммитом сохранять выведенные путь и hash исходника.

```php
<?php
declare(strict_types=1);

namespace ComponentaAudit20Peer;

use Closure;
use Componenta\DI\Exception\NotFoundException;
use Componenta\DI\Tests\Support\ContainerBuilder;
use Psr\Container\ContainerInterface;
use Psr\Container\NotFoundExceptionInterface;

$repository = realpath($argv[1] ?? getcwd());
if ($repository === false) {
    throw new \LogicException('Pass the checked-out DI repository as the first argument.');
}
require $repository . '/tests/bootstrap.php';

final readonly class Product
{
    public function __construct(public string $value) {}
}
final class Provider implements ContainerInterface
{
    public array $queries = [];
    public function __construct(private array $entries, private ?Closure $probe = null) {}
    public function has(string $id): bool
    {
        $this->queries[] = $id;
        return $this->probe === null ? array_key_exists($id, $this->entries) : ($this->probe)($id);
    }
    public function get(string $id): mixed
    {
        if (!$this->has($id)) {
            throw NotFoundException::forService($id);
        }
        return $this->entries[$id];
    }
}

/** These checks cannot fire the second-ID callback because they inspect different IDs. */
function verifyProviderLookup(Provider $provider, string $id, bool $expectedHas, mixed $expectedValue = null): array
{
    $has = $provider->has($id);
    try {
        $value = $provider->get($id);
        $found = true;
    } catch (NotFoundExceptionInterface) {
        $value = null;
        $found = false;
    }
    $valid = $has === $expectedHas && ($expectedHas ? $found && $value === $expectedValue : !$found);
    if (!$valid) {
        throw new \LogicException('The fixture violated its observed get/has contract for ' . $id);
    }
    return ['has' => $has, 'get' => $found ? 'same value' : 'NotFoundException', 'valid' => $valid];
}

$results = [];
foreach ([0, 1, 2] as $releaseOnSecondIdProbe) {
    $local = static fn(Product $entry): Product => new Product($entry->value . ':local');
    $previous = static fn(Product $entry): Product => new Product($entry->value . ':previous');
    $replacement = static fn(Product $entry): Product => new Product($entry->value . ':replacement');
    $di = (new ContainerBuilder())->addServices([
        'first' => new Product('first'),
        'second' => new Product('second'),
        'first.owner' => $local,
        'second.owner' => $local,
    ])->addDelegator('first', 'first.owner')->addDelegator('second', 'second.owner')->build();
    $state = (object) ['armed' => false, 'ownsFirst' => true, 'secondChecks' => 0];
    $earlier = new Provider(['first.owner' => $previous, 'second.owner' => $previous],
        static function (string $id) use ($state, $releaseOnSecondIdProbe): bool {
            if ($id === 'first.owner') {
                return $state->ownsFirst;
            }
            if ($id === 'second.owner') {
                if ($state->armed && ++$state->secondChecks === $releaseOnSecondIdProbe) {
                    $state->armed = false;
                    $state->ownsFirst = false;
                }
                return true;
            }
            return false;
        });
    $di->addContainer($earlier);
    $before = $di->get('first');
    $di->get('second');
    $candidate = new Provider(['first.owner' => $replacement, 'second.owner' => $replacement]);
    $state->armed = true;
    $di->addContainer($candidate);
    $candidateRegistrationQueries = $candidate->queries;
    $after = $di->get('first');
    $actualOwner = $di->get('first.owner');
    $expected = $state->ownsFirst ? 'first:previous' : 'first:replacement';
    $psrChecks = [
        'earlier_first' => verifyProviderLookup($earlier, 'first.owner', $state->ownsFirst, $previous),
        'candidate_first' => verifyProviderLookup($candidate, 'first.owner', true, $replacement),
        'earlier_missing' => verifyProviderLookup($earlier, 'missing.owner', false),
        'candidate_missing' => verifyProviderLookup($candidate, 'missing.owner', false),
    ];
    $results[] = [
        'release_on_second_id_probe' => $releaseOnSecondIdProbe,
        'second_id_checks' => $state->secondChecks,
        'final_owner' => $actualOwner === $replacement ? 'replacement' : 'previous',
        'actual' => $after->value,
        'expected' => $expected,
        'shared_identity_preserved' => $after === $before,
        'candidate_registration_queries' => $candidateRegistrationQueries,
        'ok' => $after->value === $expected,
        'provider_contract_checks' => $psrChecks,
    ];
}
$containerSource = (new \ReflectionClass(\Componenta\DI\Container::class))->getFileName();
echo json_encode([
    'php' => PHP_VERSION,
    'source_directory' => $repository . '/src',
    'container_source' => $containerSource,
    'container_sha256' => hash_file('sha256', $containerSource),
    'probe_sha256' => hash_file('sha256', __FILE__),
    'results' => $results,
], JSON_PRETTY_PRINT | JSON_THROW_ON_ERROR), "\n";
```

Случай `0` контролирует стабильного поставщика. На алгоритме после revert, который сохранён в текущем коде, случай `1` сообщает прямого владельца replacement, shared-значение `first:previous`, прежнюю identity и `ok: false`. Случай `2` не активирует смену владельца на этом алгоритме, потому что дополнительного заключительного опроса в нём нет.

Коммит [`cc4f0e3c8eca5045cda9b6d2b15f32edf39d0c94`](https://github.com/componenta/di/commit/cc4f0e3c8eca5045cda9b6d2b15f32edf39d0c94) пробовал запоминать ID, пропущенные из-за прежнего владельца, и проверять их повторно. Первые четырнадцать сценариев и выполненные для той поправки suites проходили. Независимая проверка затем перенесла мутацию на последний callback добавленной проверки:

| Момент мутации в предложенной поправке | Прямой владелец | Shared `first` | Оценка |
| --- | --- | --- | --- |
| Владение не меняется | Previous | `first:previous`, тот же объект | Корректный контроль. |
| Первый `has('second.owner')` | Replacement | `first:replacement`, новый объект | Исходный пример исправлен. |
| Добавленный заключительный `has('second.owner')` | Replacement | `first:previous`, тот же объект | Контрпример сохраняется. |

Исторический коммит [`a25051ec6ddc3342c1e2191941deffe42ce8255d`](https://github.com/componenta/di/commit/a25051ec6ddc3342c1e2191941deffe42ce8255d) содержит предложенный алгоритм. Для сравнения следует выполнить случай `2` в отдельном checkout этого коммита; нельзя считать его падением текущего алгоритма, если условие мутации там не наступает. `get()` тестового поставщика проверяет доступность и выбрасывает PSR not-found exception для отсутствующего entry; явные проверки согласованности также покрывают отсутствующие ID.

Предложенная поправка и временный файл с четырнадцатью регрессиями **полностью отозваны** коммитом [`23aefed0c2578609fe7b05d5f328f6753c08c025`](https://github.com/componenta/di/commit/23aefed0c2578609fe7b05d5f328f6753c08c025). Ранняя рекомендация peer review интегрировать локальную поправку заменена последующими контрпримером и revert. Эти тесты не являются текущим регрессионным покрытием, а та поправка не входит в план реализации ниже.

## 4. Почему требуется решение о контракте

В любой конечной последовательности непрозрачных `has()` с побочными эффектами последний вызов может изменить уже проверенный ID, сохранив прежний boolean для собственного ID. DI получит те же ответы и revision состава, что в стабильном случае. Стабильный случай требует сохранить identity незатронутого shared-объекта, изменённый — инвалидировать зависимую цепочку. Без дополнительного сигнала или ограничения стабильности алгоритм не может различить эти состояния.

Третий или последующий конечный проход перемещает контрпример, но не предоставляет недостающую информацию. Кроме того, он добавляет наблюдаемые вызовы прикладного кода. Этот вывод касается доступных наблюдений и не утверждает, что каждый поставщик ведёт себя так.

[PSR-11](https://www.php-fig.org/psr/psr-11/) определяет `get()` и `has()`, но не протокол поколения поставщика или уведомления об инвалидации. Его [meta-документ](https://www.php-fig.org/psr/psr-11/meta/) оставляет mutators вне стандарта. Более сильное правило стабильности будет extension-контрактом Componenta, а не уже существующей гарантией чистоты PSR. Удалённая эксплуатация этим сценарием не доказана: поставщик выполняет доверенный прикладной код. Подтверждённое последствие — несогласованное локальное состояние сервисов при перечисленных условиях.

## 5. Варианты и рекомендация

| Вариант | Решаемая проблема и выигрыш | Цена и совместимость |
| --- | --- | --- |
| **A. Явная стабильность владения обычного поставщика** | Определяет условия согласованности существующего lookup и адресной инвалидации. Не добавляет polling или сброс кешей. | Приложение сохраняет владение стабильным, пока используются зависимые shared-результаты, либо применяет согласованный механизм обновления. Ограничение следует документировать как явную границу extension-контракта. |
| **B. Добровольный протокол поколения или уведомления изменённых ID** | Делает динамическую смену наблюдаемой, включая изменения между вызовами DI. Позволяет адресную инвалидацию с сохранением identity незатронутых объектов. | Нужны участие поставщика, публичный контракт, правила публикации/ошибок, конкурентности и времени жизни подписок. |
| **C. Консервативная инвалидация при регистрации** | Старые отложенные результаты не переживают регистрацию только потому, что проверка владельца пропустила изменение. | Нерелевантная регистрация может менять shared identity и повторять фабрики/delegator. Выданные объекты не обновляются. Изменения после регистрации всё равно требуют контракта или сигнала. |

**Предлагаемая рекомендация:** принять A как документированный режим обычных непрозрачных поставщиков. Если реальному потребителю нужна динамическая смена владельца, отдельно спроектировать B как добровольное расширение. Предпочесть уведомление изменённых ID, когда поставщик уже знает их: это может позволить избежать опроса всех поставщиков на прогретом `get()`. Варианту с поколением нужна точная и измеренная точка наблюдения, включая обнаружение изменений между вызовами до возврата кешированного значения. Нельзя молча выбрать C или утверждать, что он сохраняет прежнюю семантику sharing.

Само принятие A определит границу поддержки, но не заставит контрпример возвращать свежий результат. DI не обязан обнаруживать поставщика, нарушающего A. Реализация не должна утверждать, что свежий изменяемый ответ `has()` доказывает дальнейшую стабильность.

## 6. Решения до реализации

1. **Поддерживаемые изменения.** Разделить состав поставщиков, получение/потерю ID, замену callable-значения тем же владельцем и изменение уже выданного объекта. Решить, какие изменения инвалидируют кешированные callable и shared-результаты цепочек. Определить поведение между API-вызовами и время жизни уже выданных объектов.
2. **Сигнал и порядок публикации.** Для поколения определить владельца счётчика, монотонность, порядок публикации состояния и механизм наблюдения без callback. Произвольный getter версии с побочными эффектами лишь перенесёт проблему. Для уведомлений определить затронутые ID, синхронный порядок публикации/инвалидации и допустимый повторный вход. Выбрать один точный протокол до добавления интерфейсов.
3. **Согласованность операции.** Охватить прежних поставщиков и кандидата. Обнаруженное во время проверки изменение не должно публиковать выводы разных поколений. Сохранить `candidate.has() <= 1` для ID в одной регистрации: это несовместимо с произвольными внутренними повторами. Практичный предлагаемый исход — конфликт до публикации внешней операции и новая явная попытка приложения. Тип исключения/API и политика retry остаются проектным решением.
4. **Ответственность за ошибки.** Callback уже мог завершить независимую вложенную мутацию. Не обещать откат прикладных эффектов или вложенной работы. Задать состояние реестра/кешей после ошибок сигнала, конфликтов и вложенной регистрации того же кандидата. Сохранить защиту alias и публикацию до освобождения.
5. **Адресная инвалидация.** Использовать существующий граф зависимостей цепочек, не создавая универсальный граф объектов. Сохранять identity незатронутых shared services. Определить инвалидацию и освобождение callable/результатов, исключения деструкторов и защиту от поздних записей старых выполняющихся вызовов.
6. **Время жизни и конкурентность.** Задать вложенные уведомления, регистрацию во время проверки, приостановку Fiber, освобождение поставщиков/подписок и предотвращение циклов. Не удерживать receiver отдельных вызовов или захваченные callbacks в общих metadata.

Эти правила не приписываются PSR-11. |
| 2. Прототип B, если выбран | Соответствующий контракту тестовый поставщик и нативные/публичные сценарии проверяют сигнал; взаимодействие адаптера/registry проектируется до production-публикации. | Сигнал различает стабильный контроль и оба контрпримера, включая последний callback. Заданы число вызовов кандидата и исход ошибки. |
| 3. Интеграция одного протокола | Расширить публичный контракт адаптера и `ExternalContainerRegistry`; при необходимости связать проверку/инвалидацию `Container` с `DelegatorRegistry`, `EntryCache` и `MutationRetirement`. | Нет публикации смешанного состояния, подмены протокола общим сбросом кешей или повторной непрозрачной проверкой. Существующие локальные контракты мутаций сохранены. |
| 4. Доказательства и документация | Выполнить матрицу приёмки, обычные проверки поддерживаемых платформ, осмысленные прицельные mutation-проверки и сравнительные замеры. Опубликовать доказательства реализации/миграции для точных коммитов. | Наблюдения, гарантии, совместимость и стоимость согласованы; только после этого выбранный вариант помечается реализованным. |

Срез 1 может завершиться независимо как решение о документации. Срезы 2–4 зависят от выбора динамической поддержки и не нужны только для сохранения существующего режима стабильного поставщика.

## 8. Матрица приёмки

Строки ниже — требования к будущему выбранному контракту, а не утверждение о существовании новых тестов.

| Граница | Необходимое наблюдаемое доказательство |
| --- | --- |
| Исходный контрпример | При B изменение с сигналом обновляет зависимый результат либо вызывает заданный конфликт до публикации внешней операции. При одном A сценарий явно находится вне поддержанного контракта стабильности. |
| Последний callback | Перенести изменение на последний прикладной callback каждой фазы. Сигнал/конфликт продолжает его учитывать; не полагаться на ещё один конечный проход `has()`. |
| Стабильный контроль | Прежний владелец, нерелевантный поставщик и незатронутые сервисы сохраняют shared identity. Записаны количества `has()` прежних поставщиков/кандидата. |
| Состав и владение | Обнаруживается соответствующее протоколу изменение владельца без revision состава registry. Сохраняется существующая вложенная регистрация через изменение состава. |
| Ответы кандидата | Положительный/отрицательный ответ, прежний владелец, отсутствие владельца и повторная регистрация сохраняют заданное число вызовов и приоритет. |
| Изменение между вызовами | При B изменение после регистрации наблюдается на определённой границе до возврата устаревшего кешированного результата. |
| Замена значения прежним владельцем | Выполняется выбранная политика замены callable; обычная мутация бизнес-состояния объекта не превращается молча в перестроение графа. |
| Alias и зависимости | Защищённые ID не перенаправляются; изменившиеся alias, новые отложенные ID и транзитивные зависимые цепочки получают текущую инвалидацию. |
| Ошибки и вложенная работа | Ошибки сигнала/`has()` и конфликты поколений не публикуют предварительную внешнюю регистрацию; завершённые вложенные мутации сохраняются. Ошибки освобождения обозначают зафиксированный исход. |
| Конкурентность | Приостановки в проверке, разрешении и освобождении; повторные уведомления не смешивают вызовы и не восстанавливают старые кеши после resume. |
| Время жизни | `WeakReference` подтверждает отсутствие удержания устаревших поставщиков/подписок/callable после исчезновения законных владельцев. Старые продукты, удерживаемые приложением, остаются действительными ссылками. |
| Производительность | Сравнить стабильный прогретый `get()`, регистрацию, динамическое обновление и незатронутый lookup на закреплённых коммитах/версиях PHP; записать вызовы `has()`, выделения и повторные фабрики/delegator. |

Для B следует доказать корректную адресную инвалидацию после наблюдаемой смены владельца с сохранением identity незатронутых объектов. Измеренного ускорения обещать нельзя. A имеет минимальную runtime-стоимость, но задаёт границу контракта, а не автоматическую поддержку изменяемых поставщиков. Решение остаётся отдельным от локального владения определениями, стабилизации bootstrap metadata и произвольных мутаций графа прикладных объектов.
