# Опрос доступности атрибутов: результаты проверки и план проектирования

[English version](attribute-availability-performance.md)

**Решение:** сохранить исправленное поведение опроса в текущем runtime 5.x. Не внедрять по этому плану широкую оптимизацию доступности. Независимо доказанные дефекты согласованности исправлять локально. Если нагрузка приложения позднее обоснует изменение контракта синхронизации, предпочтителен B2: явное обновление доступности и чистое чтение поколения в существующих компонентах, отвечающих за это состояние. C не выбран. Ни один участок оптимизации рабочего кода не имеет статуса `implementation-ready`; условная работа над B2 остаётся `blocked` до выполнения приведённых ниже требований к контракту и проверке кандидата.

В ходе аудита 13 ноября выполнены ограниченное сравнение автозагрузчиков, составление карты контрольных точек по исходникам и изолированный прототип A. A уменьшил измеренное число неуспешных попыток, но изменил наблюдаемые моменты обнаружения объявлений и возникновения исключений, поэтому он не принят. Найденный в том эксперименте дефект согласованности кеша в пределах одной проверки исправлен отдельно в `996187f`; это завершённое исправление сохраняет обе попытки автозагрузки.

## Цель и область работы

Определить, когда повторная работа автозагрузки для ещё недоступных необязательных атрибутов оправдывает изменение синхронизации, и выбрать наименьшее допустимое направление. Любая будущая оптимизация должна сохранить выбранный контракт позднего обнаружения, порядок выполнения и обнаружение несовместимых изменений после частичного завершения разрешения зависимости. Затронутое поведение охватывает создание классов, подготовленные параметры, отображение запросов, фазы обработки объектов, bootstrap и отложенную инициализацию. Получение уже закешированного общего сервиса служит контрольным случаем.

Проблема относится к существующему runtime для PHP 8.4+. Для её решения не требуются рефакторинг callback-атрибутов для PHP 8.5, AOT-компилятор, постоянный кеш метаданных или новый публичный API регистрации.

## Готовность и границы доказательств

Приведённые ниже сохраняемые семантические требования и принятые ограничения проектирования нормативны для текущей работы, сохраняющей поведение. Текущее решение — сохранить исправленный опрос; предпочтение B2 для обоснованного будущего изменения не выбирает его рабочий контракт и не разрешает реализацию. G2/G3 описывают условные исследования исключительно для принятия решений. Сначала их результаты должны уточнить или заменить нормативную спецификацию, и лишь затем из неё можно вывести зависимые участки реализации.

| Область | Состояние | Следующий шаг |
|---|---|---|
| Исходный вариант, изолированное сравнение A, наблюдения G1 и перечень контрольных точек | Доказательства собраны | Использовать записанные результаты; не повторять G1 только ради повторного открытия того же вопроса. |
| Независимое исправление корректности P11 | Завершено и проверено | Сохранить согласованность в пределах одной проверки и подтверждающие её регрессионные сценарии. Это не незавершённый участок оптимизации. |
| Решение G1 о совместимости для текущей 5.x | Принято: сохранить исправленное поведение | Сохранить обнаружение, согласованность в пределах одной проверки и наблюдаемые ошибки загрузчика. Будущее сокращение опросов требует явно пересмотренного контракта. |
| Контракт синхронизации G2 | Заблокирован для условной работы над B2 | Сначала обосновать необходимость по нагрузке и любой пересмотр контракта G1; затем на основе карты влияния завершить обязательства B2 по ответственности, контрольным точкам и ошибкам. |

| Оптимизация рабочего кода | Не выбрана для текущей 5.x | Выводить исполнимые участки реализации только из обновлённой спецификации с определённой целевой семантикой и обязательствами по замене прежних путей. |

Исправленный runtime первого аудита, для которого собраны итоговые доказательства, — `32b1142ede099e398cba03961372584aef069e69`. Измерения A относятся к историческому исходному коду `65da4acc18b19989041a2813dbc92f2f474b7177`, до P11. Те итоговые доказательства включают 28 процессов наблюдения и небольшую проверку работоспособности доступности: обнаружение класса/псевдонима возвращает revision 1 уже в первой проверке, существующее число неуспешных попыток остаётся 22/176 на создание, а контрольные случаи clean/shared сохраняют нулевые значения. Эти проверки не превращают исторические замеры A в сравнение производительности более позднего кода. Завершённое исправление P11 относится к существующему runtime 5.x; оно не отложено до major-релиза или будущего решения о политике производительности.

## Практическая необходимость и предпочтительное направление

У доказанного узкого места есть конкретное условие возникновения: просмотренная аннотация ссылается на класс или интерфейс, который остаётся недоступным. Его не вызывает само наличие атрибутов или любое попадание в кеш. Реестр записывает только недоступные имена; точное зарегистрированное определение находится прямым обращением, а уже загруженный посторонний атрибут не добавляется в множество недоступных. У контейнера, который ещё не встречал отсутствующую аннотацию, нет повторной автозагрузки недоступных имён, которую можно было бы убрать. Эти различия следуют из [`definition()` и `revision`](../../src/Attribute/Composition/AttributeDefinitionRegistry.php), а не из предположения о частоте использования атрибутов приложением.

| Нагрузка | Что делает текущий код | Следствие для решения |
|---|---|---|
| Известные DI-атрибуты | Встроенные определения регистрируются при создании контейнера; для точных имён используется поиск определения. | Корректные DI-атрибуты сами по себе не запускают множитель недоступных имён. Выполнение обработчиков и создание нативных аргументов остаются реальной работой. |
| Установленные, загруженные сторонние атрибуты | Классификация может не найти определения DI, но загруженный класс/интерфейс не сохраняется как недоступный. | Игнорирование посторонней доступной аннотации не создаёт постоянной нагрузки опроса. Первичное обнаружение всё равно имеет стоимость. |
| Отсутствующий атрибут необязательной интеграции | Его имя остаётся в множестве недоступных имён контейнера, пока последующее наблюдение не обнаружит его. | Последующие проверки метаданных посторонних операций `make()` и `call()` повторно проверяют это имя. Затронутая нагрузка — долгоживущие контейнеры с большим числом созданий. |
| Прогретый `get()` общего сервиса | Локальный кеш готовых результатов может вернуть существующий экземпляр без входа в планирование атрибутов. | Эта оптимизация не улучшает контрольное попадание в кеш общего результата. Пользовательские callbacks внешних контейнеров находятся за пределами этого контрольного случая. |
| Повторное создание корня с автоматически подключаемыми сервисами | Корень новый, а [`AutowireByTypeResolver`](../../src/Resolver/Parameter/AutowireByTypeResolver.php) получает зависимости через `has()`/`get()`. | Прогретые дочерние объекты общие. Умножение результата `make()` пустого класса на каждый узел первоначального графа неверно описало бы последующую работу. |
| Граф с явно новыми экземплярами | Вызывающий код может использовать `make()` для каждого узла и явно передавать новые дочерние объекты. | Дополнительные границы создания и параметров вызывают больше опросов; это отдельная нагрузка, отличающаяся от обычного разрешения общих зависимостей. |
| Пользовательские правила композиции | Регистрация пользовательского правила отключает мемоизацию семантических планов, чтобы актуальные состояние и аргументы оставались наблюдаемыми. | Повторное обнаружение/валидация намеренны. Изменение доступности не должно возвращать кеширование устаревших результатов правил и не может устранить работу самого правила. |
| Новый контейнер и первый граф | В стоимость входят конфигурация/bootstrap, первичное обнаружение, построение планов и первое создание сервисов. | Подготовку нужно измерять отдельно от прогретого цикла создания. Один бенчмарк отсутствующих имён не доказывает выигрыш запуска или обработки запросов. |

Поэтому решение — **не выполнять широкий рефакторинг производительности в текущей области 5.x**. Доказательства устанавливают реальную патологическую нагрузку, но не её распространённость или долю в задержке приложения. Локальные исправления согласованности кеша необходимы независимо от того, встречается ли приложению эта нагрузка. Приведённая ниже повторная оценка отдельно показывает обычные пути с корректными атрибутами, загруженные сторонние атрибуты, недоступные необязательные имена, идентичность общих/новых узлов графа, контрольные случаи пользовательских правил и холодную подготовку; более быстрого цикла отсутствующих имён недостаточно для утверждения об общем ускорении библиотеки.

Если приложение действительно тратит существенное время на повторный опрос недоступных имён, **предпочтительное будущее направление — B2**. Существующий реестр каждого контейнера остаётся единственным владельцем состояния доступности; операция, способная выполнять автозагрузчики, отделяется от чистого чтения уже установленного поколения. Потребители должны публиковать или выполнять план вместе с тем поколением и слотами резолвера, из которых он действительно получен. Последующее обновление не может задним числом отметить невыполненный обработчик завершённым. Явная синхронизация облегчает проверку этих обязательств, но одно лишь переименование или разделение существующих чтений не уменьшает их число и не имеет доказанного ускорения.

Сокращение числа опросов B2 — дополнительное изменение контракта. Для каждой сохраняемой границы пользовательского кода нужен названный ответственный компонент обновления, а для каждой пропущенной проверки — явное объяснение её безопасности по пересмотренному контракту. Сама автозагрузка является такой границей. Однократного обновления на входе, проверки идентичности списка автозагрузчиков или чистого getter revision без этих ответственных компонентов недостаточно.

**C отклонён для текущей области работы.** Он обещает избежать перебора посторонних имён, но ни одно квалификационное сравнение не устанавливает дополнительный выигрыш приложения по отношению к правильно специфицированному B2. При этом C добавляет индекс недоступных имён/целей, охватывающий активные планы, проверки завершённой работы, унаследованные члены, цели параметров, вложенные вызовы и отложенные объекты. Такому индексу нужны собственные доказательства инвалидации и времени жизни, включая удержание замыканий и рефлекторов, привязанных к объектам. Ему всё равно потребуются согласованные снимки и границы пользовательского кода из B2; одна релевантность цели этих проблем не решает. Устранение побочных эффектов загрузчиков посторонних имён также является решением о совместимости. Не следует добавлять это состояние только потому, что синтетический случай восьми имён дорог.

Порядок предпочтения: сейчас сохранить исправленное поведение с локальными исправлениями; использовать B2 только для обоснованного будущего изменения контракта; возвращаться к C только если уже прошедший проверку B2 оставит измеренную существенную стоимость перебора нерелевантных имён. A и B1 по-прежнему отклонены как прозрачные оптимизации. Никакая дополнительная архитектура или прототип здесь не выбраны.

## Воспроизводимые доказательства

Каноническая проверка — [AttributeAvailabilityBench.php](../../benchmarks/AttributeAvailabilityBench.php). Запускайте её из корня репозитория отдельно с каждым бинарным файлом PHP:

```bash
COMPONENTA_DI_BENCH_AUTOLOAD="$PWD/vendor/autoload.php" \
COMPONENTA_DI_BENCH_SOURCE="$PWD/src" \
DI_BENCH_ITERATIONS=10000 DI_BENCH_ROUNDS=7 \
php -n benchmarks/AttributeAvailabilityBench.php
```

`COMPONENTA_DI_BENCH_AUTOLOAD` и `COMPONENTA_DI_BENCH_SOURCE` — обязательные пути; используйте абсолютные пути, как в команде выше и в принятом для бенчмарков соглашении. `DI_BENCH_ITERATIONS` и `DI_BENCH_ROUNDS` — необязательные положительные целые числа со значениями по умолчанию 10,000 и 7. Для прогрева выбирается меньшее из 2,000 и числа итераций. Скрипт выводит выбранные исходники, бинарный файл, версию runtime и настройки OPcache/JIT.

Для каждого случая в каждом раунде проверка создаёт отдельный контейнер. В случаях с ранее обнаруженными недоступными атрибутами сначала создаётся посторонний объект с одним либо восемью заведомо несуществующими атрибутами. Измеряемая цель — пустой класс без атрибутов. Bootstrap, первоначальное создание объекта с атрибутами, прогрев и сборка циклического мусора находятся за пределами измеряемого интервала. Порядок случаев меняется на обратный через раунд. Скрипт сообщает медианную задержку по раундам и полный диапазон числа вызовов автозагрузки за раунд.

Автозагрузчик, добавленный в начало очереди, считает запросы только к восьми зарезервированным именам тестовых классов. Он никогда не объявляет класс. Сопоставление имён не учитывает регистр, посторонние запросы Composer игнорируются, счётчики сбрасываются непосредственно перед измерением. Проверки без автозагрузки до и после измерения отклоняют запуск, если другой загрузчик объявил одно из зарезервированных имён. Поэтому счётчики показывают попытки автозагрузки этих отсутствующих имён, а не число чтений файловой системы и не общее количество вызовов функций обратного вызова в стеке автозагрузки. Измеряемое время включает накладные расходы считающей функции обратного вызова.

### Наблюдаемый исходный вариант, 13 ноября

Измерения выполнены на Linux x86_64, статических CLI-бинарных файлах PHP 8.4.23 и PHP 8.5.8, с `-n`, отключённым OPcache CLI и отключённым JIT. Каждая версия запускалась отдельно: семь раундов по 10,000 операций и 2,000 операций прогрева на случай/раунд. Эти измерения используют неизменяемый снимок `65da4acc18b19989041a2813dbc92f2f474b7177`, сделанный до исправлений 13 ноября. В [доказательствах аудита](../audit/2026-11-13-evidence.json) записаны точная идентичность исходников/зависимостей и более поздняя проверка работоспособности итогового кода. Исторические измерения остаются в отчётах 12 ноября; различия между сессиями не приписываются изменениям кода.

| Случай | Медиана PHP 8.4.23, µs/op | Медиана PHP 8.5.8, µs/op | Вызовы автозагрузки отсутствующих имён на операцию, обе версии | Вызовы в каждом раунде из 10,000 операций |
|---|---:|---:|---:|---:|
| `make/clean` | 5.1196 | 5.5019 | 0 | 0 |
| `make/1-unavailable` | 22.0571 | 25.2777 | 22 | 220,000 |
| `make/8-unavailable` | 132.1754 | 137.7157 | 176 | 1,760,000 |
| `get-shared/clean` | 0.2010 | 0.2008 | 0 | 0 |
| `get-shared/1-unavailable` | 0.1997 | 0.2050 | 0 | 0 |
| `get-shared/8-unavailable` | 0.2016 | 0.1993 | 0 | 0 |

Точные числа вызовов автозагрузки совпали во всех раундах обеих версий runtime. Они показывают, что один исследованный класс может добавить повторяющуюся работу при последующем создании других объектов в том же контейнере. Увеличение множества недоступных имён с одного до восьми увеличивает этот счётчик в восемь раз в данном сценарии. Попадание в кеш общего результата `get()` не выполняет эти проверки.

Это локальные измерения с инструментированием, а не утверждение о пропускной способности рабочего приложения или сравнение версий PHP. На затраченное время влияют планирование CPU, реализация автозагрузчика, его собственный отрицательный кеш, поведение файловой системы и расширения. Устойчивый сигнал — повторная автозагрузка ещё недоступных имён; измеренная задержка показывает её стоимость в этом окружении. Бенчмарк не измеряет холодный запуск, задержку реальных запросов приложения или рост памяти при произвольно большом количестве сгенерированных имён классов.

### Повторная оценка нагрузки на исправленном коде

Последующая [повторная проверка всей библиотеки](../audit/2026-11-13-full-library-recheck.ru.md) измерила рабочий код `fce3f176a2ab37b6ac7d595712c3fe5ff18564b0` после исправлений доступности и согласованности параметров. Её [доказательства](../audit/2026-11-13-full-library-evidence.json) сохраняют исходные значения задержки пяти раундов, независимые счётчики автозагрузки, полные хеши исходников и сведения о зависимостях. Это характеристика нагрузки исходного варианта: кандидат B2/C и сравнение до/после исправлений не запускались. ## Текущая ответственность и первопричина

[AttributeDefinitionRegistry](../../src/Attribute/Composition/AttributeDefinitionRegistry.php) владеет зарегистрированными семантическими определениями, политиками возможностей, множеством недоступных имён атрибутов и счётчиком поколений. `definition()` может записать имя, класс/интерфейс которого пока недоступен. Чтение `revision` проверяет каждое записанное имя:

```php
if (class_exists($attribute) || interface_exists($attribute) || class_exists($attribute, false)) {
    unset($this->unavailableAttributes[$attribute]);
    ++$this->generation;
}
```

Обе функции по умолчанию выполняют автозагрузку: см. руководства PHP для [class_exists](https://www.php.net/manual/en/function.class-exists.php) и [interface_exists](https://www.php.net/manual/en/function.interface-exists.php). Для имени, которое остаётся недоступным, происходят обе попытки. Счётчик бенчмарка добавлен в начало очереди согласно документированному поведению [spl_autoload_register](https://www.php.net/manual/en/function.spl-autoload-register.php).

Последняя проверка `class_exists` без автозагрузки — исправление от 13 ноября. Резервный вызов `interface_exists` может запустить загрузчик, объявляющий класс; сам вызов всё равно вернёт false, поскольку объявление не является интерфейсом. Раньше реестр мог вернуть старое поколение после того, как класс уже стал доступен. После прогрева `has()` возвращал false, тогда как публичный контрольный вариант без мемоизации возвращал true. Добавленная проверка замечает объявление немедленно, не вызывая загрузчик ещё раз, не меняя число неуспешных попыток и не откладывая исключение резервной попытки.

Чтение revision обеспечивает корректность сразу в нескольких компонентах:

| Компонент | Текущая ответственность | Почему важно наблюдение revision |
|---|---|---|
| `AttributePlanBuilder` | Композиция атрибутов и инвалидация именованных планов | Ранее проигнорированная аннотация может позднее получить зарегистрированное семантическое определение через наследование или псевдоним. |
| `ObjectPipeline` | Кеширование метаданных и выбор политик конструктора/объекта | План, собранный из разных поколений, нельзя опубликовать как единый согласованный план. |
| `AttributeProcessor` и `ObjectAttributeSequence` | Выбор целей фазы, удержание ожидающего экземпляра и однократное выполнение упорядоченного префикса | Создание атрибута или разрешение зависимости может обнаружить обработчик в ходе того же разрешения. |
| `ParametersResolver` и `AttributeParameterResolver` | Подготовка слотов резолвера, использование планов атрибутов и разрешение параметров | Слоты и семантика атрибутов должны согласоваться до выполнения; метаданные завершённой работы должны описывать действительно использованные обработчики. Более ранние зависимости могут менять последующие политики. |
| `CompletedAttributeGuard` | Проверка уже завершённой работы с параметрами/объектом | Поздняя политика не должна незаметно переопределять смысл уже полученного значения или завершённой фазы. |

Таким образом, запрос доступности имеет побочные эффекты: формальное чтение revision может выполнить произвольный код автозагрузки, загрузить класс, выбросить исключение и изменить поколение. Для постороннего прогретого `make()` эти повторные наблюдения всё ещё перебирают общее для контейнера множество недоступных имён. Одного кеширования метаданных недостаточно, чтобы убрать эту работу: проверка поколения кеша и выполняет опрос.

У текущего поведения есть существенная намеренная часть: отсутствующую аннотацию нельзя навсегда признать незначимой только потому, что она отсутствовала при первом просмотре. Проблему производительности и этот контракт обнаружения нужно решать вместе.

P1–P6 определяют, когда обнаружение должно становиться наблюдаемым; они не устанавливают, что точное число неуспешных вызовов автозагрузки само по себе является поддерживаемым публичным контрактом. Это различие требует проектного решения и не разрешает незаметно менять момент обнаружения.

P11 различает инвариант согласованности в пределах одной проверки и контрольные сценарии двух попыток и исключения резервной попытки, намеренно сохранённые локальным исправлением. В этой редакции обязательны обе части. Если G1 предлагает изменить эти наблюдения автозагрузки, в обновлённой нормативной спецификации должны быть явно указаны затронутые ограничения, ожидания тестов и последствия для совместимости; прототип не может незаметно отменить их. Немедленная инвалидация после фактического обнаружения объявления и согласованность поведения с кешем и без мемоизации остаются требованиями корректности.

Исходные одиннадцать тестовых файлов P1–P8 прошли на обеих версиях runtime; [повторная проверка паритета кеша](../audit/2026-11-12-cache-parity-recheck.md) добавила P9–P10. 13 ноября пятнадцать файлов проверок сохранения поведения прошли и на неизменяемом исходном варианте, и на прототипе A: **117 успешных, два пропуска сценариев, доступных только в PHP 8.5, и 820 утверждений на PHP 8.4; 119 успешных и 828 утверждений на PHP 8.5**. В новом файле P11 до исправления четыре случая падали, а девять контрольных проходили; после исправления прошли все тринадцать. Успешные P1–P10 не доказали эквивалентность произвольных автозагрузчиков: в G1 ниже приведены конкретные контрпримеры. P11 входит в обязательства по сохранению поведения любой будущей оптимизации.

## Принятые ограничения проектирования

Реестр семантических определений остаётся источником истины для зарегистрированной семантики, наблюдаемой доступности и поколения внутри контейнера. Он наблюдает общие для процесса объявления PHP и состояние автозагрузчиков, но не владеет ими и не изолирует их. Закешированные планы атрибутов/объектов/параметров остаются производным состоянием, которым владеют существующие компоненты каждого контейнера. Последовательности выполнения и проверки завершённой работы сохраняют ответственность за порядок и безопасность фаз. Эта проблема не оправдывает ещё один глобальный реестр, постоянный отрицательный кеш или подсистему событий.

Семантические определения владеют элементами массивов `capabilities`, `requires`, `forbids`, `before`, `after` и `rules` с момента создания, до вызова автозагрузчиков при валидации. Ссылки на переменные вызывающего кода не должны менять семантику зафиксированного реестра или приводить к расхождению закешированных и немемоизированных планов. Идентичность и изменяемое состояние объектов обработчиков/правил сохраняются; фиксируются только элементы массивов конфигурации. [AttributeDefinitionSnapshotContractTest](../../tests/Contract/AttributeDefinitionSnapshotContractTest.php) проверяет все шесть массивов, изменение во время автозагрузки, порядок на холодных/прогретых путях и актуальное состояние исходного объекта правила. Это локальное исправление владения в рамках P6, а не оптимизация опроса.

Любое будущее разделение синхронизации доступности и чтения поколения должно определить обе операции и одновременно перевести их потребителей. Потребитель кеша не должен видеть поколение, которое выглядит актуальным, если обязательная контрольная точка обнаружения была пропущена. Контракт должен учитывать повторный вход в разрешение, bootstrap, отложенную инициализацию и прямое использование уже доступных API планов/процессора атрибутов; добавить проверку только в `Container::make()` недостаточно.

Этот отчёт не выбирает целевое значение, счётчик, предел повторных попыток, timeout или политику истечения срока отрицательного результата. Ни одна оптимизация не может навсегда игнорировать ещё недоступные атрибуты, повторно выполнять завершённую работу или удерживать созданные для выполнения экземпляры атрибутов ради экономии на материализации. Полная совместимость исходников остаётся PHP `^8.4`; эта работа над производительностью не должна повышать минимальную версию до PHP 8.5.

Ограниченный эксперимент A завершён. Не повторяйте его только ради более выгодного результата задержки. C находится за пределами этого условного эксперимента. B1 остаётся контрольным вариантом, опровергающим сохранение контракта обнаружения в одном разрешении, а не выбранной по умолчанию архитектурой.

Фиксация недоступных аннотаций после bootstrap, произвольный предел опросов/TTL или использование только изменений `spl_autoload_functions()` как сигнала инвалидации не являются принятыми решениями. Неизменившийся загрузчик может зависеть от изменяемого состояния или недавно появившихся файлов. Явный API уведомлений со стороны приложения изменит ответственность и публичный контракт и потребует отдельного принятого предложения.

## Блокирующие решения и ограниченные эксперименты

### G1 — Какие наблюдения автозагрузчика входят в контракт?

**Статус:** доказательства собраны; решение для текущей 5.x — сохранить исправленное поведение. Из G1 не следует оптимизация рабочего кода. Будущее сокращение опросов должно явно пересмотреть затронутые ограничения совместимости до проверки изменённого контракта в G2/G3.

Репозиторий подтверждает позднюю загрузку классов и защиту завершённой работы. Это решение сохраняет наблюдения исправленной реализации, не объявляя каждое историческое число неуспешных попыток новой общей гарантией публичного API. В частности, никакая оптимизация здесь не может откладывать обнаружение или исключение только потому, что загрузчику нужен дополнительный вызов, либо устранять существующий побочный эффект постороннего имени. Сокращение опросов неизбежно меняет часть наблюдений, зависящих от количества вызовов; для этого нужен пересмотренный контракт, а не заявление о прозрачности изменения.

**Собранные доказательства:** семь изолированных сценариев и их контрольные случаи с заранее загруженными объявлениями выполнены для исходного варианта `65da4acc` и A на обеих версиях runtime: 56 процессов. Для изменения готовности в пределах одного разрешения повторно использован `ObjectAttributeCacheParityContractTest`. Переносимый [AttributeAvailabilityObservations.php](../audit/reproductions/AttributeAvailabilityObservations.php) воспроизводит изолированные наблюдения; в [доказательствах](../audit/2026-11-13-evidence.json) сохранены точные результаты и происхождение исходников.

Успех широкого набора тестов не делает эти различия безвредными. Принятие A или B2 не следует из этого эксперимента, и для определения текущего решения не нужна дополнительная неограниченная серия сценариев.

### G2 — Где можно безопасно пропустить обновление?

**Статус:** заблокирован для условной работы над B2. Текущее решение G1 сохраняет поведение опроса. До проверки пропусков будущее предложение должно обосновать затраты приложения и явно определить любые изменяемые наблюдения. Перечень контрольных точек — карта влияния; контракт синхронизации B2 для замены ещё не определён.

**Решающие доказательства:** использовать существующую карту чтений revision, границ пользовательского кода и проверок завершённой работы, чтобы обосновать каждый предлагаемый пропуск в рамках выбранного контракта. Использовать сценарии выше вместе с наборами P1–P11. Учесть вложенные `make()`/`call()`, прямое использование API планов/процессора атрибутов, bootstrap и отложенную инициализацию lazy/proxy. Подтвердить, как обновление, которое само загружает другой атрибут или повторно входит в разрешение, достигает согласованного поколения без повторного выполнения.

Проверки исходников 13 ноября дали следующую карту контрольных точек. Это карта влияния для B2, а не доказательство того, что любое из перечисленных обновлений уже можно убрать:

| --- | --- | --- |

Чтение поколения без побочных эффектов требует явного владельца синхронизации на каждой применимой границе, включая прямые публичные API. Сама автозагрузка является пользовательским кодом: обход метаданных нельзя просто считать чистой операцией. Оставшаяся проектная работа — выбрать контракт и доказать допустимость каждого пропущенного опроса в его рамках, а не вводить второй реестр.

**Границы:** если после обоснования пересмотренного контракта G1 нужны доказательства сверх существующей карты, временное инструментирование ограничивается изолированной копией исходников реестра и потребителей из карты контрольных точек. Подготовить для выбранного контракта таблицу контрольных точек, указав ответственный компонент, запускающую операцию, обязательное наблюдение и передачу ошибок на каждой границе. Сохранить выводы и происхождение исходников; исключить временное инструментирование из области изменений рабочего кода. Остановиться, когда у каждого сохраняемого сценария есть явная контрольная точка, а у каждой пропускаемой проверки — основание в этой карте, затем обновить нормативный контракт синхронизации. Счётчики профилирования и второй путь синхронизации не становятся зависимостями рабочего кода.

### G3 — Оправдывает ли минимальный сохраняющий поведение кандидат свою сложность?

**Статус:** заблокирован до выполнения предусловий G2 и определения его контракта синхронизации. Исторические доказательства A собраны; B2 — только предпочтительное будущее направление, ни один кандидат на основе текущих исходников не выбран для рабочего кода.

Изолированный эксперимент A дал следующие измерения с теми же зависимостями, настройками и измерительной программой, что и исходный вариант. Это исследовательское непарное сравнение до P11, а не ускорение итогового кода и не статистическое доказательство отсутствия регрессии:

| Сценарий | PHP 8.4, исходный вариант → A, µs | PHP 8.5, исходный вариант → A, µs | Вызовы для отсутствующих имён на операцию |
| --- | ---: | ---: | ---: |
| Один недоступный атрибут | 22.057 → 14.656 | 25.278 → 16.654 | 22 → 11 |
| Восемь недоступных атрибутов | 132.175 → 74.966 | 137.716 → 79.601 | 176 → 88 |
| Контрольные случаи чистого создания и получения общего результата | Новых проверок отсутствующих имён нет | Новых проверок отсутствующих имён нет | 0 → 0 |

Все проверки соответствия исходников прошли; оптимизированная карта классов Composer и автоматически загружаемые функции были перенаправлены на выбранную неизменяемую копию. Точное сокращение счётчика установлено. Показатели задержки включают инструментирование и не оправдывают отказ от P11 или изменение момента возникновения исключений. В том историческом эксперименте реализация B2/C не предпринималась. Текущее решение сохраняет исправленный опрос и не трактует эти результаты как разрешение другой архитектуры.

**Решающие доказательства:** после принятия обоснованного пересмотренного контракта G1 и решения G2 использовать в качестве базы сравнения актуальный на тот момент исправленный код, включая P11 и исправления согласованности выполнения параметров. Исторический A остаётся доказательством; не переносить его на новую базу только ради повторного рассмотрения уже завершённого отклонения как прозрачного исправления. Сравнить не более одного кандидата B2. Использовать одинаковые настройки и целевые наборы проверок сохранения поведения; версии runtime запускать последовательно. Наряду с затронутыми случаями отсутствующих имён включать обычные пути с корректными атрибутами, контроль пользовательских правил, графы с общими/новыми объектами, холодную подготовку и чистый/shared-get контроль. Записывать точное число неуспешных попыток, исходные раунды задержки и их медиану, любой диапазон счётчика и дополнительные удерживаемые метаданные. Диапазон числа вызовов автозагрузки не является распределением задержки; инструментирование времени и счётчиков должно быть указано отдельно.

Также сохранить контролируемое сравнение `RuntimeBench.php`, включая повторно используемые и новые замыкания. Последующие исправления согласованности показали увеличение задержки повторно используемого замыкания даже без недоступного атрибута в этом сценарии (см. [измерения повторной проверки](../audit/2026-11-12-cache-parity-recheck.md#controlled-runtime-comparison)). Кандидат должен учитывать обычный путь без мемоизации наряду с бенчмарком отсутствующих имён; удаление проверки revision допустимо только после того, как требуемое наблюдение покрыто принятым контрактом контрольных точек.

**Границы:** только временные копии кандидатов; без изменений рабочего кода или принятия публичного API. Отклонить кандидата при любом нарушении сохраняемого поведения. После этого сравнения остановиться: выбрать минимального удовлетворяющего требованиям кандидата, сохранить исходный вариант с объяснением компромисса или пересмотреть спецификацию целевого состояния, если необходимо изменение контракта. Прототип не становится выбранной архитектурой автоматически.

## Порядок реализации и приёмка

Бенчмарк, исторический ограниченный прототип с доказательствами и независимое исправление корректности P11 — завершённые результаты. В этой редакции нет исполнимого участка оптимизации рабочего кода. Следующий порядок определяет оставшиеся решения и условные задачи сбора доказательств; он не разрешает реализацию в рабочем коде:

1. Сохранить бенчмарк и измеренный исходный вариант как сигнал проблемы. Этот результат готов.
2. Применить принятое решение G1: сохранить исправленное поведение в текущей 5.x. Не выводить исправление рабочего кода из синтетического бенчмарка. Будущее предложение, обоснованное нагрузкой приложения, должно явно пересмотреть любое изменяемое наблюдение до сокращения опросов.
3. Только для этого обоснованного будущего предложения B2 решить G2. Записать нормативный контракт синхронизации, включая прямые вызовы API, вложенные вызовы, поведение при ошибках, согласованное использование планов и отложенную работу.
4. Решить G3 с одним изолированным кандидатом B2. Обновить этот документ, указав выбранную архитектуру, измеренный компромисс и доказательства приёмки, либо сохранить исправленный опрос, если сравнение не оправдает принятие кандидата.
5. Только после этого вывести участки реализации из обновлённой нормативной спецификации. В рамках контракта сохранения поведения этой редакции каждый участок должен менять одно согласованное поведение доступности вместе со всеми необходимыми потребителями, сохранять P1–P11 и удалять заменяемый опрос в том же участке после доказательства корректности замены. Любое намеренное изменение совместимости требует явного обновления нормативной части, описанного в G1; его нельзя ввести отдельным участком реализации или успешным бенчмарком. Результат не должен оставлять обе стратегии активными на неопределённый срок.

Для будущей реализации приёмка требует сокращения автозагрузки отсутствующих имён в затронутых случаях бенчмарка, объяснённого результата задержки на обеих версиях runtime, отсутствия новых проверок недоступных имён в чистом/shared-get путях и успешных сценариев P1–P11. Числовая цель пропускной способности не подразумевается. Актуальность и поведение при ошибках важнее ускорения некорректного результата.

Подтверждённая исходниками область изменений — `AttributeDefinitionRegistry::revision`/`definition()`, `AttributePlanBuilder`, `ObjectPipeline::metadata`, `AttributeProcessor`, `ObjectAttributeSequence`, `CompletedAttributeGuard`, `ParametersResolver` и `AttributeParameterResolver`, с включением потребителей источников запросов/bootstrap там, где их затрагивает выбранный контракт. Это карта влияния, а не указание изменить каждый файл. Опрос в реестре остаётся неизменным до полного определения контракта его замены и потребителей.

Итоговая сверка должна сопоставить принятый контракт синхронизации с фактическими путями runtime, проверить отсутствие устаревшего пути опроса или скрытого отрицательного кеша и подтвердить, что актуальность пользовательских правил, время жизни ReflectionObject, нативное вычисление аргументов и идентичность общего сервиса не принесены в жертву результату производительности.
