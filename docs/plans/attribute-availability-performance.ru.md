# Опрос доступности атрибутов: результаты проверки и план проектирования

[English version](attribute-availability-performance.md)

**Готовность:** `blocked` для оптимизации рабочего кода из-за G1–G3 ниже. В этой редакции ни один новый участок рабочего кода не имеет статуса `implementation-ready`. В ходе аудита 13 ноября выполнены ограниченное сравнение автозагрузчиков, составление карты контрольных точек по исходникам и изолированный прототип варианта A. A уменьшил измеренное число неуспешных попыток, но изменил наблюдаемые моменты обнаружения объявлений и возникновения исключений, поэтому он не принят. Найденный в эксперименте дефект согласованности кеша в пределах одной проверки исправлен отдельно в `996187f`; это завершённое исправление сохраняет обе попытки автозагрузки.

## Цель и область работы

Сократить повторную работу автозагрузки для ещё недоступных необязательных атрибутов, сохранив позднее обнаружение атрибутов, порядок выполнения и обнаружение несовместимых изменений после частичного завершения разрешения зависимости. Затронутое поведение охватывает создание классов, подготовленные параметры, отображение запросов, фазы обработки объектов, bootstrap и отложенную инициализацию. Получение уже закешированного общего сервиса служит контрольным случаем.

Проблема относится к существующему runtime для PHP 8.4+. Для её решения не требуются рефакторинг callback-атрибутов для PHP 8.5, AOT-компилятор, постоянный кеш метаданных или новый публичный API регистрации.

## Готовность и границы доказательств

Приведённые ниже сохраняемые семантические требования и принятые ограничения проектирования нормативны для этой работы, сохраняющей поведение. Измерения и варианты решения служат доказательствами, а не выбранной архитектурой замены. G2/G3 описывают условные исследования исключительно для принятия решений; описание или завершение прототипа не разрешает его внедрение в рабочий код. Сначала их результаты должны уточнить или заменить нормативную спецификацию, и лишь затем из неё можно вывести зависимые участки реализации.

Исправленный runtime, для которого собраны итоговые доказательства, — `32b1142ede099e398cba03961372584aef069e69`. Измерения A относятся к историческому исходному коду `65da4acc18b19989041a2813dbc92f2f474b7177`, до P11. Итоговые доказательства включают 28 процессов наблюдения и небольшую проверку работоспособности доступности: обнаружение класса/псевдонима возвращает revision 1 уже в первой проверке, существующее число неуспешных попыток остаётся 22/176 на создание, а контрольные случаи clean/shared сохраняют нулевые значения. Эти проверки не превращают исторические замеры A в сравнение производительности итогового кода. Завершённое исправление P11 относится к существующему runtime 5.x; оно не отложено до major-релиза или до ещё не принятого решения G1 о политике производительности.

## Воспроизводимые доказательства

Каноническая проверка — [AttributeAvailabilityBench.php](../../benchmarks/AttributeAvailabilityBench.php). Запускайте её из корня репозитория отдельно с каждым бинарным файлом PHP:

```bash
COMPONENTA_DI_BENCH_AUTOLOAD="$PWD/vendor/autoload.php" \
COMPONENTA_DI_BENCH_SOURCE="$PWD/src" \
DI_BENCH_ITERATIONS=10000 DI_BENCH_ROUNDS=7 \
php -n benchmarks/AttributeAvailabilityBench.php
```

`COMPONENTA_DI_BENCH_AUTOLOAD` и `COMPONENTA_DI_BENCH_SOURCE` — обязательные пути; используйте абсолютные пути, как в команде выше и в принятом для бенчмарков соглашении. `DI_BENCH_ITERATIONS` и `DI_BENCH_ROUNDS` — необязательные положительные целые числа со значениями по умолчанию 10,000 и 7. Для прогрева выбирается меньшее из 2,000 и числа итераций. Скрипт выводит выбранные исходники, бинарный файл, версию runtime и настройки OPcache/JIT.

Для каждого случая в каждом раунде проверка создаёт отдельный контейнер. В случаях с ранее обнаруженными недоступными атрибутами сначала создаётся посторонний объект с одним либо восемью заведомо несуществующими атрибутами. Измеряемая цель — пустой класс без атрибутов. Bootstrap, первоначальное создание объекта с атрибутами, прогрев и сборка циклического мусора находятся за пределами измеряемого интервала. Порядок случаев меняется на обратный через раунд. Скрипт сообщает медианную задержку по раундам и полный диапазон числа вызовов автозагрузки за раунд.

Автозагрузчик, добавленный в начало очереди, считает запросы только к восьми зарезервированным именам тестовых классов. Он никогда не объявляет класс. Сопоставление имён не учитывает регистр, посторонние запросы Composer игнорируются, счётчики сбрасываются непосредственно перед измерением. Проверки без автозагрузки до и после измерения отклоняют запуск, если другой загрузчик объявил одно из зарезервированных имён. Поэтому счётчики показывают попытки автозагрузки этих отсутствующих имён, а не число чтений файловой системы и не общее количество вызовов функций обратного вызова в стеке автозагрузки. Измеряемое время включает накладные расходы считающей функции обратного вызова.

### Наблюдаемый исходный вариант, 13 ноября

Измерения выполнены на Linux x86_64, статических CLI-бинарных файлах PHP 8.4.23 и PHP 8.5.8, с `-n`, отключённым OPcache CLI и отключённым JIT. Каждая версия запускалась отдельно: семь раундов по 10,000 операций и 2,000 операций прогрева на случай/раунд. Эти измерения используют неизменяемый снимок `65da4acc18b19989041a2813dbc92f2f474b7177`, сделанный до исправлений 13 ноября. В [доказательствах аудита](../audit/2026-11-13-evidence.json) записаны точная идентичность исходников/зависимостей и более поздняя проверка работоспособности итогового кода. Исторические измерения остаются в отчётах 12 ноября; различия между сессиями не приписываются изменениям кода.

| Случай | Медиана PHP 8.4.23, µs/op | Медиана PHP 8.5.8, µs/op | Вызовы автозагрузки отсутствующих имён на операцию, обе версии | Вызовы в каждом раунде из 10,000 операций |
|---|---:|---:|---:|---:|
| `make/clean` | 5.1196 | 5.5019 | 0 | 0 |
| `make/1-unavailable` | 22.0571 | 25.2777 | 22 | 220,000 |
| `make/8-unavailable` | 132.1754 | 137.7157 | 176 | 1,760,000 |
| `get-shared/clean` | 0.2010 | 0.2008 | 0 | 0 |
| `get-shared/1-unavailable` | 0.1997 | 0.2050 | 0 | 0 |
| `get-shared/8-unavailable` | 0.2016 | 0.1993 | 0 | 0 |

Точные числа вызовов автозагрузки совпали во всех раундах обеих версий runtime. Они показывают, что один исследованный класс может добавить повторяющуюся работу при последующем создании других объектов в том же контейнере. Увеличение множества недоступных имён с одного до восьми увеличивает этот счётчик в восемь раз в данном сценарии. Попадание в кеш общего результата `get()` не выполняет эти проверки.

Это локальные измерения с инструментированием, а не утверждение о пропускной способности рабочего приложения или сравнение версий PHP. На затраченное время влияют планирование CPU, реализация автозагрузчика, его собственный отрицательный кеш, поведение файловой системы и расширения. Устойчивый сигнал — повторная автозагрузка ещё недоступных имён; измеренная задержка показывает её стоимость в этом окружении. Бенчмарк не измеряет холодный запуск, задержку реальных запросов приложения или рост памяти при произвольно большом количестве сгенерированных имён классов.

## Текущая ответственность и первопричина

[AttributeDefinitionRegistry](../../src/Attribute/Composition/AttributeDefinitionRegistry.php) владеет зарегистрированными семантическими определениями, политиками возможностей, множеством недоступных имён атрибутов и счётчиком поколений. `definition()` может записать имя, класс/интерфейс которого пока недоступен. Чтение `revision` проверяет каждое записанное имя:

```php
if (class_exists($attribute) || interface_exists($attribute) || class_exists($attribute, false)) {
    unset($this->unavailableAttributes[$attribute]);
    ++$this->generation;
}
```

Обе функции по умолчанию выполняют автозагрузку: см. руководства PHP для [class_exists](https://www.php.net/manual/en/function.class-exists.php) и [interface_exists](https://www.php.net/manual/en/function.interface-exists.php). Для имени, которое остаётся недоступным, происходят обе попытки. Счётчик бенчмарка добавлен в начало очереди согласно документированному поведению [spl_autoload_register](https://www.php.net/manual/en/function.spl-autoload-register.php).

Последняя проверка `class_exists` без автозагрузки — исправление от 13 ноября. Резервный вызов `interface_exists` может запустить загрузчик, объявляющий класс; сам вызов всё равно вернёт false, поскольку объявление не является интерфейсом. Раньше реестр мог вернуть старое поколение после того, как класс уже стал доступен. После прогрева `has()` возвращал false, тогда как публичный контрольный вариант без мемоизации возвращал true. Добавленная проверка замечает объявление немедленно, не вызывая загрузчик ещё раз, не меняя число неуспешных попыток и не откладывая исключение резервной попытки.

Чтение revision обеспечивает корректность сразу в нескольких компонентах:

| Компонент | Текущая ответственность | Почему важно наблюдение revision |
|---|---|---|
| `AttributePlanBuilder` | Композиция атрибутов и инвалидация именованных планов | Ранее проигнорированная аннотация может позднее получить зарегистрированное семантическое определение через наследование или псевдоним. |
| `ObjectPipeline` | Кеширование метаданных и выбор политик конструктора/объекта | План, собранный из разных поколений, нельзя опубликовать как единый согласованный план. |
| `AttributeProcessor` и `ObjectAttributeSequence` | Выбор целей фазы, удержание ожидающего экземпляра и однократное выполнение упорядоченного префикса | Создание атрибута или разрешение зависимости может обнаружить обработчик в ходе того же разрешения. |
| `ParametersResolver` | Подготовка и разрешение планов параметров | Более ранние зависимости могут изменить политики, применимые к последующим параметрам. |
| `CompletedAttributeGuard` | Проверка уже завершённой работы с параметрами/объектом | Поздняя политика не должна незаметно переопределять смысл уже полученного значения или завершённой фазы. |

Таким образом, запрос доступности имеет побочные эффекты: формальное чтение revision может выполнить произвольный код автозагрузки, загрузить класс, выбросить исключение и изменить поколение. Для постороннего прогретого `make()` эти повторные наблюдения всё ещё перебирают общее для контейнера множество недоступных имён. Одного кеширования метаданных недостаточно, чтобы убрать эту работу: проверка поколения кеша и выполняет опрос.

У текущего поведения есть существенная намеренная часть: отсутствующую аннотацию нельзя навсегда признать незначимой только потому, что она отсутствовала при первом просмотре. Проблему производительности и этот контракт обнаружения нужно решать вместе.

## Обязательная сохраняемая семантика

Эти ограничения следуют из [контрактов расширения/runtime в README](../../README.md#extension-points) и существующих исполнимых сценариев. Они нормативны для любой предложенной по результатам этого аудита оптимизации, сохраняющей поведение.

|---|---|---|

Существующие унаследованные определения атрибутов и псевдонимы должны продолжать работать. | [LateAttributeLoadingTest](../../tests/Contract/LateAttributeLoadingTest.php), включая прогретый `has()`, планы конструктора/callable и фабрики отображаемых DTO. |

| P11 | Класс или псевдоним, объявленный резервной проверкой интерфейса, изменяет доступность в пределах той же проверки. P1–P6 определяют, когда обнаружение должно становиться наблюдаемым; они не устанавливают, что точное число неуспешных вызовов автозагрузки само по себе является поддерживаемым публичным контрактом. Это различие требует проектного решения и не разрешает незаметно менять момент обнаружения.

P11 различает инвариант согласованности в пределах одной проверки и контрольные сценарии двух попыток и исключения резервной попытки, намеренно сохранённые локальным исправлением. В этой редакции обязательны обе части. Если G1 предлагает изменить эти наблюдения автозагрузки, в обновлённой нормативной спецификации должны быть явно указаны затронутые ограничения, ожидания тестов и последствия для совместимости; прототип не может незаметно отменить их. Немедленная инвалидация после фактического обнаружения объявления и согласованность поведения с кешем и без мемоизации остаются требованиями корректности.

Исходные одиннадцать тестовых файлов P1–P8 прошли на обеих версиях runtime; [повторная проверка паритета кеша](../audit/2026-11-12-cache-parity-recheck.md) добавила P9–P10. 13 ноября пятнадцать файлов проверок сохранения поведения прошли и на неизменяемом исходном варианте, и на прототипе A: **117 успешных, два пропуска сценариев, доступных только в PHP 8.5 и 820 утверждений на PHP 8.4; 119 успешных и 828 утверждений на PHP 8.5**. В новом файле P11 до исправления четыре случая падали, а девять контрольных проходили; после исправления прошли все тринадцать. Успешные P1–P10 не доказали эквивалентность произвольных автозагрузчиков: в G1 ниже приведены конкретные контрпримеры. P11 входит в обязательства по сохранению поведения любой будущей оптимизации.

## Принятые ограничения проектирования

Реестр семантических определений остаётся источником истины для зарегистрированной семантики, наблюдаемой доступности и поколения внутри контейнера. Он наблюдает общие для процесса объявления PHP и состояние автозагрузчиков, но не владеет ими и не изолирует их. Закешированные планы атрибутов/объектов/параметров остаются производным состоянием, которым владеют существующие компоненты каждого контейнера. Последовательности выполнения и проверки завершённой работы сохраняют ответственность за порядок и безопасность фаз. Эта проблема не оправдывает ещё один глобальный реестр, постоянный отрицательный кеш или подсистему событий.

Любое будущее разделение синхронизации доступности и чтения поколения должно определить обе операции и одновременно перевести их потребителей. Потребитель кеша не должен видеть поколение, которое выглядит актуальным, если обязательная контрольная точка обнаружения была пропущена. Контракт должен учитывать повторный вход в разрешение, bootstrap, отложенную инициализацию и прямое использование уже доступных API планов/процессора атрибутов; добавить проверку только в `Container::make()` недостаточно.

Этот отчёт не выбирает целевое значение, счётчик, предел повторных попыток, timeout или политику истечения срока отрицательного результата. Ни одна оптимизация не может навсегда игнорировать ещё недоступные атрибуты, повторно выполнять завершённую работу или удерживать созданные для выполнения экземпляры атрибутов ради экономии на материализации. Полная совместимость исходников остаётся PHP `^8.4`; эта работа над производительностью не должна повышать минимальную версию до PHP 8.5.

Ограниченный эксперимент A завершён. Не повторяйте его только ради более выгодного результата задержки. Рассматривать следует не более одного прототипа B2/C и только после определения контракта совместимости и подтверждения, что оставшиеся затраты на уровне приложения оправдывают более широкое изменение. B1 остаётся контрольным вариантом, опровергающим сохранение контракта обнаружения в одном разрешении, а не выбранной по умолчанию архитектурой.

Фиксация недоступных аннотаций после bootstrap, произвольный предел опросов/TTL или использование только изменений `spl_autoload_functions()` как сигнала инвалидации не являются принятыми решениями. Неизменившийся загрузчик может зависеть от изменяемого состояния или недавно появившихся файлов. Явный API уведомлений со стороны приложения изменит ответственность и публичный контракт и потребует отдельного принятого предложения.

## Блокирующие решения и ограниченные эксперименты

### G1 — Какие наблюдения автозагрузчика входят в контракт?

**Статус:** доказательства собраны; решение о совместимости остаётся заблокированным. Готовая к выполнению задача — письменное решение на основе существующих наблюдений, а не ещё одна серия сценариев или исправление рабочего кода.

Репозиторий подтверждает позднюю загрузку классов и защиту завершённой работы. Он не определяет, нужно ли сохранять произвольное поведение загрузчика, зависящее от числа неуспешных попыток, должен ли ставший доступным класс обнаруживаться без обращения к цели, на которой он объявлен, и должно ли каждое текущее чтение `revision` продолжать выполнять загрузчики. Сокращение числа вызовов неизбежно меняет некоторые из этих наблюдений.

**Собранные доказательства:** семь изолированных сценариев и их контрольные случаи с заранее загруженными объявлениями выполнены для исходного варианта `65da4acc` и A на обеих версиях runtime: 56 процессов. Для изменения готовности в пределах одного разрешения повторно использован `ObjectAttributeCacheParityContractTest`. Переносимый [AttributeAvailabilityObservations.php](../audit/reproductions/AttributeAvailabilityObservations.php) воспроизводит изолированные наблюдения; в [доказательствах](../audit/2026-11-13-evidence.json) сохранены точные результаты и происхождение исходников.

G1 считается решённым, когда письменное решение перечисляет сохраняемые наблюдения, любые наблюдения, которые разрешено изменить, последствия для совместимости и соответствующие нормативные ограничения и проверки, требующие обновления. Сохранение исправленного исходного варианта — допустимый результат. Принятие A или более широкой архитектуры не следует из завершения эксперимента. Для определения этой границы решения не требуется дополнительная неограниченная серия сценариев.

### G2 — Где можно безопасно пропустить обновление?

**Статус:** заблокирован до решения G1 и выбора допустимого направления. Существующий перечень контрольных точек завершён как карта влияния; контракт синхронизации для замены ещё не определён.

**Решающие доказательства:** использовать существующую карту чтений revision, границ пользовательского кода и проверок завершённой работы, чтобы обосновать каждый предлагаемый пропуск в рамках выбранного контракта. Использовать сценарии выше вместе с наборами P1–P11. Учесть вложенные `make()`/`call()`, прямое использование API планов/процессора атрибутов, bootstrap и отложенную инициализацию lazy/proxy. Подтвердить, как обновление, которое само загружает другой атрибут или повторно входит в разрешение, достигает согласованного поколения без повторного выполнения.

Проверка исходников 13 ноября дала следующую карту контрольных точек. Это карта влияния для B2/C, а не доказательство того, что любое из перечисленных обновлений уже можно убрать:

| --- | --- | --- |

| `AttributeProcessor::executionPlan` | Прямые точки входа `prepare()` / `hasHandlers()` | Синхронизировать независимо от наличия внешнего вызова Container. |

Чтение поколения без побочных эффектов требует явного владельца синхронизации на каждой применимой границе, включая прямые публичные API. Сама автозагрузка является пользовательским кодом: обход метаданных нельзя просто считать чистой операцией. Оставшаяся проектная работа — выбрать контракт и доказать допустимость каждого пропущенного опроса в его рамках, а не вводить второй реестр.

**Границы:** если после G1 нужны доказательства сверх существующей карты, временное инструментирование ограничивается изолированной копией исходников реестра и потребителей из карты контрольных точек. Подготовить для выбранного контракта таблицу контрольных точек, указав ответственный компонент, запускающую операцию, обязательное наблюдение и передачу ошибок на каждой границе. Сохранить выводы и происхождение исходников; исключить временное инструментирование из области изменений рабочего кода. Остановиться, когда у каждого сохраняемого сценария есть явная контрольная точка, а у каждой пропускаемой проверки — основание в этой карте, затем обновить нормативный контракт синхронизации. Счётчики профилирования и второй путь синхронизации не становятся зависимостями рабочего кода.

Все проверки соответствия исходников прошли; оптимизированная карта классов Composer и автоматически загружаемые функции были перенаправлены на выбранную неизменяемую копию. Точное сокращение счётчика установлено. Показатели задержки включают инструментирование и не оправдывают отказ от P11 или изменение момента возникновения исключений. Реализация B2/C не предпринималась, поскольку G1 уже установил наличие нерешённого выбора совместимости.

**Решающие доказательства:** после решения G1 и G2 использовать в качестве базы сравнения актуальный на тот момент исправленный код, включая P11. Исторический A остаётся доказательством; переносить его на новую базу можно только если выбранный контракт совместимости допускает изменяемые им наблюдения. Сравнить не более одного более широкого кандидата из B2/C. Использовать этот бенчмарк с одинаковыми настройками и целевые наборы проверок сохранения поведения; версии runtime запускать последовательно. В каждое сравнение включать чистый путь и контрольный shared-get. Записывать точное число неуспешных попыток, медианную задержку, диапазон количества вызовов автозагрузки по раундам из измерительной программы и любые дополнительные метаданные, удерживаемые кандидатом. Диапазон количества вызовов автозагрузки не является распределением задержки.

Также сохранить контролируемое сравнение `RuntimeBench.php`, включая повторно используемые и новые замыкания. Последующие исправления согласованности показали увеличение задержки повторно используемого замыкания даже без недоступного атрибута в этом сценарии (см. [измерения повторной проверки](../audit/2026-11-12-cache-parity-recheck.md#controlled-runtime-comparison)). Кандидат должен учитывать обычный путь без мемоизации наряду с бенчмарком отсутствующих имён; удаление проверки revision допустимо только после того, как требуемое наблюдение покрыто принятым контрактом контрольных точек.

**Границы:** только временные копии кандидатов; без изменений рабочего кода или принятия публичного API. Отклонить кандидата при любом нарушении сохраняемого поведения. После этого сравнения остановиться: выбрать минимального удовлетворяющего требованиям кандидата, сохранить исходный вариант с объяснением компромисса или пересмотреть спецификацию целевого состояния, если необходимо изменение контракта. Прототип не становится выбранной архитектурой автоматически.

## Порядок реализации и приёмка

Бенчмарк, исторический ограниченный прототип с доказательствами и независимое исправление корректности P11 — завершённые результаты. В этой редакции нет исполнимого участка оптимизации рабочего кода. Следующий порядок определяет оставшиеся решения и условные задачи сбора доказательств; он не разрешает реализацию в рабочем коде:

1. Сохранить бенчмарк и измеренный исходный вариант как сигнал проблемы. Этот результат готов.
2. Принять решение G1 о совместимости на основе завершённых сценариев. Сохранять текущее поведение, если новый контракт явно не разрешает наблюдаемые изменения. Не выводить исправление рабочего кода только из чисел бенчмарка.
3. Решить G2 для выбранного направления. Записать нормативный контракт синхронизации, включая прямые вызовы API, вложенные вызовы, поведение при ошибках и отложенную работу.
4. Решить G3 в изолированных копиях кандидатов. Обновить этот документ, указав выбранную архитектуру, измеренный компромисс и доказательства приёмки.
5. Только после этого вывести участки реализации из обновлённой нормативной спецификации. В рамках контракта сохранения поведения этой редакции каждый участок должен менять одно согласованное поведение доступности вместе со всеми необходимыми потребителями, сохранять P1–P11 и удалять заменяемый опрос в том же участке после доказательства корректности замены. Любое намеренное изменение совместимости требует явного обновления нормативной части, описанного в G1; его нельзя ввести отдельным участком реализации или успешным бенчмарком. Результат не должен оставлять обе стратегии активными на неопределённый срок.

Для будущей реализации приёмка требует сокращения автозагрузки отсутствующих имён в затронутых случаях бенчмарка, объяснённого результата задержки на обеих версиях runtime, отсутствия новых проверок недоступных имён в чистом/shared-get путях и успешных сценариев P1–P11. Числовая цель пропускной способности не подразумевается. Актуальность и поведение при ошибках важнее ускорения некорректного результата.

Подтверждённая исходниками область изменений — `AttributeDefinitionRegistry::revision`/`definition()`, `AttributePlanBuilder`, `ObjectPipeline::metadata`, `AttributeProcessor`, `ObjectAttributeSequence`, `CompletedAttributeGuard` и `ParametersResolver`, с включением потребителей источников запросов/bootstrap там, где их затрагивает выбранный контракт. Это карта влияния, а не указание изменить каждый файл. Опрос в реестре остаётся неизменным до полного определения контракта его замены и потребителей.

Итоговая сверка должна сопоставить принятый контракт синхронизации с фактическими путями runtime, проверить отсутствие устаревшего пути опроса или скрытого отрицательного кеша и подтвердить, что актуальность пользовательских правил, время жизни ReflectionObject, нативное вычисление аргументов и идентичность общего сервиса не принесены в жертву результату производительности.
