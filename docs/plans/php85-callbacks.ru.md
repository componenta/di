# DI 6: callback-функции PHP 8.5 и детерминированное автовнедрение union-типов

[English version](php85-callbacks.md)

Создано: 2026-11-12. Перепроверено: 2026-11-13 на `71a843082e7850672bc1fef87401e5697d433f66` после нового аудита выпущенной DI 5.0.5 (`a56f3d70dd56bdd62947b6c322aa878e8a76ef4c`). Предыдущая проверка и [исправления корректности от 13 ноября](../audit/2026-11-13-di-audit.md) остаются историческими доказательствами. Новые [нативные доказательства](../audit/2026-11-13-php85-native-evidence.json) содержат точную ревизию исходников, версии бинарных файлов, исходный код fixtures и результаты.

**Статус реализации (2026-11-14):** нативные проверки `Init`, общий callback binder, `Transform`, callback-вариант `SetUp` и автовнедрение простых union-типов реализованы и локально проверены в `refactor/di6-definitions-callbacks`. См. [руководство миграции](../migrations/di6-callbacks.ru.md) и [доказательства реализации](../audit/2026-11-14-di6-refactoring.ru.md). Итоговый выпуск DI 6, обещание поддержки затронутых нативных trait-callable и минимальная patch-версия PHP остаются заблокированы условием E1 в §8. Callback-преобразования request-to-DTO отдельно отложены в §11.

Совместимая работа v5.0.6 остаётся в ветке 5.x с PHP `^8.4`. Эта major-ветка не меняет тот релиз. Пока решение об упаковке платформы открыто, исходники остаются совместимыми с синтаксисом PHP 8.4; это не определяет окончательную минимальную поддерживаемую версию для DI 6. Существующий `Init` сохраняет публичный API и принимает поддерживаемые нативные выражения на PHP 8.5. Описания исходного состояния ниже относятся к проверенной реализации 5.x.

## 1. Цель и восстановленный замысел

Позволить описывать локальное типизированное поведение непосредственно в PHP-атрибутах, сохранив единый конвейер разрешения параметров, единый жизненный цикл объекта и нативную область видимости PHP callback-функций. Добавить детерминированное автовнедрение простых union-типов как независимую возможность DI 6.

Восстановленные обсуждения от 13 августа и 24–25 сентября 2026 года и документ `componenta-php85-callbacks-version-plan.md` фиксируют следующий замысел:

- `SetUp` может получать callback-функцию, первый аргумент которой — созданный экземпляр; остальные зависимости предоставляет DI.
- Повторяемый атрибут `Transform` отвечает за преобразование значения, не добавляя callback-параметр к каждому атрибуту источника.
- Callback-функции в API атрибутов используют `Closure`; существующие представления runtime callable остаются поддерживаемыми.
- Имена и порядок существующих аргументов публичных конструкторов атрибутов сохраняют совместимость. Необязательные аргументы атрибутов, если они нужны в других местах, помещаются в конец; вызывающий код не должен передавать заполняющие аргументы `null`. Миграции инфраструктурных конструкторов в этой major-версии определяются отдельно.
- DI 6 переходит на PHP 8.5. Разрешение union-типа должно выбирать ровно один доступный тип сервиса и отклонять неоднозначность.
- `Init` уже принимает callable. Преобразование request-to-DTO — отдельная возможная последующая задача.

Эта спецификация актуализирует заметки по текущему репозиторию. В старых заметках есть примеры атрибутов со `static fn`, которые PHP 8.5 не компилирует. Они также предшествуют отказу от скомпилированных фабрик и постоянного графа объектов. Ни эти примеры, ни та архитектура не должны переноситься в реализацию.

### Границы работы

Включены: `Transform`, callback-вариант `SetUp`, проверки существующего `Init` на PHP 8.5, автовнедрение простых union-типов, диагностика, контракты жизненного цикла и памяти, документация и руководство по миграции.

Не включены: скомпилированные контейнеры, сериализация замыканий, извлечение исходного кода, новые реестры фабрик, глобальные изменения приоритетов resolver-компонентов, автоматический поиск сервисов для intersection/DNF-типов, callback-параметр в каждом существующем атрибуте и изменения посторонних пакетов Componenta. Для опроса доступности атрибутов существует отдельный [план производительности](attribute-availability-performance.md).

### Необходимость и совместимость каждой возможности

Восстановленный набор возможностей DI 6 остаётся предполагаемой целью выпуска. Из этого не следует, что каждая возможность технически требует PHP 8.5 или major-версии:

| Возможность | Фактическая граница совместимости | Принятое решение |
| --- | --- | --- |
| Существующий `Init` | Публичный API не меняется. Новые inline/static-reference выражения PHP 8.5 уже работают через текущий callable-путь; существующие string/array/invokable-входы остаются допустимыми. | Добавить доказательства и примеры нативного синтаксиса, области видимости и времени жизни, не меняя устройство `Init`. Эти дополнения могут быть совместимы с 5.x. |
| Новый `Transform` | Добавляемые атрибут и handler могут использовать синтаксис реализации, совместимый с PHP 8.4. Значение `Closure` в атрибуте само по себе не требует PHP 8.5; новые inline/reference выражения требуют. | Сохранить его в запланированном наборе DI 6, но признать независимую реализуемость и потенциальную совместимость с minor-релизом, если политика выпуска будет явно изменена. |
| Callback-вариант `SetUp` | Расширение типа публичного свойства `$method` у non-final readonly атрибута ломает подклассы, повторно объявляющие `string $method`, поскольку свойства PHP инвариантны. | Реальное изменение для major-версии. Предпочесть существующего владельца lifecycle `SetUp` с сохранённым именованным аргументом ещё одному публичному setup-атрибуту. |
| Автовнедрение простого union-типа | PHP 8.5 не добавляет необходимой для него возможности языка. Выбор сервиса вместо прежнего default/null или появление ошибок неоднозначности меняет поведение разрешения. | Сохранить это независимое изменение поведения в DI 6. Для callback binder оно не требуется. |
| Callback request-to-DTO | Контракт входа, выхода и provenance ещё не определён. | Отложить отдельно по §11; он не блокирует остальные возможности. |
| Цель PHP `^8.5` | Восстановленное решение о платформе выпуска, отдельное от синтаксиса реализации и минимального patch-релиза с исправлением движка. | Сохранить замысел DI 6; определить фактический минимальный поддерживаемый patch по E1 до выпуска. |

Отдельный атрибут `SetUpCallback` позволил бы не менять существующее свойство в minor-релизе, но создал бы второе публичное представление той же lifecycle-операции. Дополнительный callback-аргумент, требующий заполнителя вместо метода, также нарушил бы восстановленный замысел API. При уже запланированной major-версии расширение `SetUp` даёт меньший и согласованный публичный API. Нельзя сужать `Init` или общие runtime callable API только ради внешнего единообразия сигнатур.

Нативный fixture `runtime_constant_on_php84` доказывает, что уже созданное замыкание в runtime-константе можно передать конструктору атрибута с типом `Closure` на PHP 8.4.23 и 8.5.8. Это доказательство разделения API и платформы, а не рекомендация вводить глобальные константы в конфигурацию приложения.

## 2. Текущие владельцы обязанностей и необходимое расширение

| Обязанность | Текущий владелец | Решение для DI 6 |
| --- | --- | --- |
| Собрать контейнер и закрыть его конфигурацию | `ContainerFactory` | Здесь подключаются новый handler и небольшой внутренний помощник вызова callback-функций. |
| Скомпоновать возможности атрибутов и их порядок | `AttributePlanBuilder`, `AttributeDefinitionRegistry` | Использовать существующие компоненты; зарегистрировать `Transform` как `ValueTransformer` после источников значений. |
| Выполнить handlers параметров | `AttributeParameterResolver` | Использовать существующую упорядоченную цепочку. |
| Разрешить и проверить параметры | `ParametersResolver` | Добавить внутреннюю точку входа с фиксированным первым аргументом, использующую существующий цикл разрешения. |
| Защитить источники mapped request | `ParameterResolutionBoundary`, `MappedRequestParameterSourceGuard` | Передавать внутреннего владельца setup для параметров callback-функций без declaring class; сохранить обычный путь вызова. |
| Вызвать callable с уже разрешёнными аргументами | `PreparedCallable`, `CallableInvokerInterface`, `CallableExecutor` | Использовать существующий контракт подготовленного вызова, включая декораторы. |
| Подготовить значения свойств к записи | `ObjectCreationContext::resolveProperty/readProperty/writeProperty` | Использовать существующие операции; не создавать отдельный механизм записи или проверки типов. |
| Выполнить lifecycle hooks | `SetUpRunner` | Добавить ветвь для замыкания; сохранить ветвь для метода экземпляра. |
| Инициализировать свойства из callable | `Init`, `InitHandler` | Сохранить API и путь выполнения. Добавить контракты и примеры для PHP 8.5. |
| Выполнить автовнедрение по типу | `AutowireByTypeResolver` | Расширить выбор кандидата для простого union-типа у этого владельца. |

Текущий порядок приоритетов: атрибуты → переданное имя/позиция → переданный тип → автовнедрение → PHP default → nullable. Handler не может запросить «то, что вернула бы оставшаяся часть конвейера», не добавив рекурсию или повторную работу. Поэтому `Transform` использует контракт источника из §4, а не рекурсивный вызов resolver.

## 3. Публичный API и синтаксис PHP

### 3.1 `Transform`

Предлагаемое новое объявление:

```php
#[Attribute(
    Attribute::TARGET_PARAMETER
    | Attribute::TARGET_PROPERTY
    | Attribute::IS_REPEATABLE
)]
final readonly class Transform
{
    public function __construct(public Closure $callback) {}
}
```

Отдельных аргументов `default`, `params`, service ID, factory или mapper нет. Атрибуты источников отвечают за получение значения. Callback получает текущее значение как один смысловой аргумент, за которым следуют зависимости, разрешаемые через DI (§5).

### 3.2 `SetUp`

Расширить тип существующего свойства и параметра конструктора, сохранив имя:

```php
public function __construct(
    public string|Closure $method,
    public array $params = [],
) {}
```

Класс остаётся readonly, не-final и повторяемым. Именованный аргумент `method:` остаётся действительным. Строка по-прежнему означает имя метода экземпляра с текущей проверкой public/concrete/non-static. Строка не становится именем глобальной функции или service ID. `Closure` получает созданный экземпляр как первый смысловой аргумент. Возвращаемое значение игнорируется и не может заменить объект.

### 3.3 `Init`

Сохранить `Init(mixed $callable, array $params = [])` и существующие представления callable. Не сужать этот API до `Closure`. Его callable возвращает значение свойства; владелец свойства не передаётся как неявный первый аргумент.

### 3.4 Корректные примеры

Это предлагаемые примеры для DI 6; `Transform` и callback-вариант `SetUp` не входят в DI 5:

```php
final class CustomerInput
{
    public function __construct(
        #[Transform(trim(...))]
        #[Transform(static function (string $value): string {
            return strtolower($value);
        })]
        public string $email,
    ) {}
}

#[SetUp(static function (Application $application, Logger $logger): void {
    $application->setLogger($logger);
})]
final class Application
{
    private Logger $logger;

    public function setLogger(Logger $logger): void
    {
        $this->logger = $logger;
    }
}
```

PHP 8.5 поддерживает `static function (...) { ... }` без захвата переменных в аргументах атрибутов и first-class ссылки вида `trim(...)` или `Formatter::normalize(...)`. Стрелочные замыкания, включая `static fn`, нестатические литералы замыканий и замыкания с `use (...)` там недопустимы. Именованные ссылки сохраняют свою лексическую видимость. Нельзя привязывать статический callback к объекту или менять область его объявления. См. официальные реализованные [RFC замыканий](https://wiki.php.net/rfc/closures_in_const_expr) и [RFC first-class callable](https://wiki.php.net/rfc/fcc_in_const_expr).

Синтаксис first-class callable в constant expressions поддерживает только именованные функции и объявленные статические методы. Динамические выражения ссылок вида `[Formatter::class, 'normalize'](...)`, ссылки на методы объекта и методы, предоставленные исключительно через `__callStatic()`, в аргументах атрибутов не поддерживаются. Это ограничение языка не удаляет существующие runtime-представления string/array/invokable, принимаемые `Init` или обычным исполнением callable. Их текущий контракт нативной диспетчеризации отделён от синтаксиса выражений атрибутов.

Фаза отказа также определяется нативным поведением PHP. Повторная проверка на PHP 8.5.8 подтвердила: динамическое выражение ссылки не проходит компиляцию, а magic-static ссылка в атрибуте разбирается и бросает `Error`, когда `ReflectionAttribute::newInstance()` материализует атрибут. Если компиляция проходит, синтаксические fixtures должны доходить до материализации; одного `php -l` недостаточно.

## 4. Контракт преобразования

### 4.1 Композиция и порядок

Зарегистрировать `Transform` с capability `ValueTransformer`, после `ValueProvider`, в фазе свойств после создания экземпляра. Повторные применения `Transform` выполняются в порядке объявления. `Cast` и `Transform` сохраняют взаимный порядок объявления, если явно зарегистрированное ограничение композиции не требует иного. Существующая диагностика конфликтов композиции и циклов остаётся определяющей.

Каждое применение выполняется не более одного раза за попытку. Поздняя загрузка атрибутов может изменить композицию оставшейся работы; она не должна повторять завершённое преобразование или заново конструировать ожидающий экземпляр атрибута. Несовместимое позднее изменение должно приводить к ошибке через существующие completion guards.

### 4.2 Входное значение параметра

| Состояние при запуске преобразования | Вход callback-функции |
| --- | --- |
| `ParameterAttributeValue` разрешён | Именно это значение, включая явно переданный `null`. |
| Неразрешённый variadic-параметр | Один пустой массив. |
| Неразрешённый параметр с PHP default | Значение, полученное из отражённого default для этой попытки. |
| Неразрешённый nullable-параметр | `null`. |
| Любое другое состояние | Бросить `ResolutionException` до вызова callback-функции. |

Разрешённое значение может поступить из допустимого явного аргумента, provider или предыдущего преобразования. Правила авторитетного источника остаются прежними. Переданное, но недопустимое значение не заменяется default.

Handler не выполняет автовнедрение самого целевого параметра. Чтобы преобразовать новый объект, объявить `Make`; чтобы преобразовать shared service, объявить `EntryId`. Дополнительные зависимости callback-функции по-прежнему могут разрешаться автовнедрением. Пример:

```php
#[Make(Service::class)]
#[Transform(static function (Service $value, Formatter $formatter): Service {
    return $formatter->configure($value);
})]
Service $service
```

Для variadic-цели callback преобразует всю коллекцию один раз. Существующая итоговая проверка проверяет каждый элемент результата и нативный порядок именованных/позиционных аргументов. Неявное перечисление всех подходящих сервисов не добавляется.

### 4.3 Входное значение свойства и присваивание

Следовать текущей модели источника `CastHandler`, исключив его необязательный default на уровне атрибута:

1. Если provider/transformer уже заявил обработку свойства, прочитать ожидающее значение через `ObjectCreationContext::readProperty()`.
2. Иначе вызвать `claimProperty()`. Если результат — false, callback не вызывать.
3. Для впервые заявленного свойства требовать публичный ключ creation context, точно совпадающий с его именем; использовать `array_key_exists()`, чтобы `null` оставался значением.
4. Если ключ отсутствует, бросить `ResolutionException` свойства до вызова callback-функции.
5. Подготовить результат к записи через `writeProperty()`.

Объявленное default изменяемого свойства не является неявным источником для самостоятельного `Transform`. Использовать provider, например `Config`, `Env`, `EntryId`, `Make`, `Init`, либо явное значение контекста. Существующий пропуск уже инициализированных readonly и promoted-свойств сохраняется. Статические свойства и виртуальные свойства только с get сохраняют существующий отказ.

Промежуточные значения остаются вне PHP-свойства. После успеха всей композиции свойства текущий владелец staging записывает итоговое значение один раз. Это поддерживает readonly-инициализацию, виртуальные свойства только с set при наличии ожидающего значения provider и однократный вызов setter hook.

**Не проверять результат свойства по `ReflectionProperty::getType()` до присваивания.** Setter hook может принимать более широкий входной тип, чем getter/свойство, и выполнять собственное преобразование. Нативное присваивание через существующий `writeProperty()` остаётся ответственным за семантику присваивания PHP. Результат параметра, напротив, по-прежнему проходит существующую проверку параметров после всей цепочки атрибутов.

Staging предотвращает промежуточное присваивание этому свойству. Он не отменяет побочные эффекты callback-функции во внешних сервисах, объектах, переданных по идентичности, предыдущих свойствах или приложении в целом.

## 5. Контракт вызова callback-функций

### 5.1 Смысловой аргумент и DI-суффикс

Для `Transform` смысловой аргумент — текущее значение. Для callback-варианта `SetUp` — созданный объект. То, что значение является массивом, никогда не означает разворачивание в несколько аргументов.

- Callback без объявленных параметров разрешён и вызывается без нативных аргументов. Преобразование с нулём параметров всё равно требует источник по §4; оно не становится инициализатором.
- В остальных случаях первый параметр получает смысловой аргумент независимо от имени или default. Он не может быть by-reference или variadic.
- Проверить аргумент по текущим строгим правилам принятия типа параметра. Тип входного значения может отличаться от итогового типа цели.
- Параметры после первого используют существующую DI-цепочку, включая custom resolvers, атрибуты параметров, defaults, nullable fallback, пропуск нативных внутренних defaults и существующую variadic-семантику.
- By-reference параметры остаются неподдерживаемыми на всём пути.
- Контекст разрешения суффикса содержит реальное смысловое значение в `resolved[0]`.
- Результат callback-функции, включая `null`, становится новым преобразованным значением. Объявленные нативные возвращаемые типы проверяет PHP. Возврат `void` обрабатывается как его фактический результат `null`, без особой интерпретации.

### 5.2 Защита первого аргумента

Вызова `$container->call($callback, [0 => $value])` недостаточно: авторитетный атрибут или custom resolver с более высоким приоритетом может заменить этот аргумент. Дополнительная передача имени первого параметра также не защищает его от всей resolver-цепочки.

Добавить один внутренний помощник `Internal\AttributeCallbackInvoker`, который отвечает за reflection callback-функции, проверку ABI/значения первого аргумента и подготовленный итоговый вызов. Проверка DI-метаданных остаётся внутри защищённой границы parameter resolver. Помощник должен:

1. Получить reflection фактического `Closure`, не перепривязывая и не воссоздавая его.
2. Обработать пустую сигнатуру пустым вектором нативных аргументов, всё равно выполнив один подготовленный вызов через существующий invoker и декораторы.
3. Проверить ABI и значение первого параметра. Передать его фактический `ParameterTarget` в точку входа разрешения суффикса только для проверки метаданных. Применения зарегистрированных DI-атрибутов на этом зарезервированном параметре недопустимы; обычные метаданные вне DI, например `SensitiveParameter`, остаются разрешёнными.
4. Подготовить к разрешению только суффикс, сохранив исходные позиции параметров. Первый параметр не должен попадать в `supports()` или `resolveParameter()` custom resolvers либо в handlers атрибутов.
5. Разрешить суффикс через небольшую внутреннюю точку входа в `ParametersResolver`, использующую существующий цикл с начальным префиксом нативных аргументов и состоянием `resolved[0]`.
6. Держать зарезервированную первую цель и завершённые цели суффикса в одном `CompletedAttributeGuard`. Любая новая DI-семантика первой цели или несовместимое изменение завершённого суффикса должны вызывать ошибку до вызова callback. Нельзя выполнять отдельный discovery probe первой цели после возврата из защищённой операции разрешения суффикса.
7. Вызвать существующий invoker с `new PreparedCallable($callback)` и полным вектором нативных аргументов.

Обычная точка входа `resolvePrepared()` должна использовать тот же цикл с пустым префиксом. Нельзя копировать цикл разрешения параметров, использовать скрытые специальные ключи в публичном контексте или синтезировать wrapper closure со скопированными атрибутами. `ParameterResolutionContext` уже поддерживает начальное разрешённое состояние. `PreparedCallable` уже предотвращает второй проход DI и предоставляет исходный callable декораторам, соблюдающим контракт.

Новая граница — внутренняя операция `ParametersResolver`, а не новый extension interface:

Общий внутренний helper создаётся как `AttributeCallbackInvoker(ParametersResolver $parameters, CallableInvokerInterface $invoker)` и предоставляет `invoke(Closure $callback, mixed $argument, array $providedParameters = [], ?string $diagnosticOwner = null): mixed`. `ContainerFactory` создаёт один helper для `TransformHandler` и `SetUpRunner`, передавая контейнер в качестве invoker для сохранения действующих декораторов. Helper не регистрируется как новый публичный сервис и не хранит замыкания или значения отдельных вызовов.

```php
/**
 * @internal
 * @param array<string|int, mixed> $providedParameters
 * @param class-string|null $diagnosticOwner
 * @return array<string|int, mixed>
 */
public function resolvePreparedSuffix(
    PreparedParameterPlan $suffix,
    ParameterTarget $firstTarget,
    mixed $firstArgument,
    array $providedParameters = [],
    ?string $diagnosticOwner = null,
): array;
```

`$suffix` содержит только параметры callback-функции после первого объявления и сохраняет их исходные позиции. `$firstTarget` — фактическое первое объявление в позиции `0`; binder уже проверил его ABI и значение. Точка входа разрешения суффикса строит план его метаданных, отклоняет зарегистрированные DI-применения до выполнения суффикса и записывает принятый пустой DI-план как доказательство зарезервированного аргумента в тот же локальный для вызова guard завершённой работы, который используется при выполнении суффикса. Для этой цели она никогда не классифицирует и не выполняет resolver.

Операция задаёт начальный вектор нативных аргументов `[$firstArgument]` и состояние разрешения `[0 => $firstArgument]`, затем выполняет те же операции обновления, проверки границ, пропуска аргументов, variadic и завершённой работы, что и `resolvePrepared()`. Итоговая проверка стабилизирует оба направления: discovery первой цели может обнаружить изменение уже завершённого суффикса, а discovery суффикса — запрещённые метаданные первой цели. Она записывает план, фактически потреблённый каждым attribute bridge, не заменяя это доказательство более поздним результатом discovery и не повторяя handlers. Использовать существующий механизм guard/revision; не добавлять второй алгоритм проверки завершения или изменяемое состояние последнего вызова.

Операция возвращает полный нативный вектор, включая первое значение. Пустой суффикс допустим и всё равно проверяет зарезервированную цель; ветвь callback-функции без объявленных параметров обходит эту точку входа и не передаёт аргументов. Ни префикс, ни доказательство зарезервированной цели, ни диагностический владелец не становятся общим состоянием плана.

### 5.3 Переданный контекст

`Transform` передаёт суффиксу пустой публичный набор параметров. Его зависимости поступают из DI, собственных атрибутов/resolvers или defaults. Внешний набор параметров DTO/конструктора/request не наследуется по имени, поэтому поле, случайно совпавшее с именем параметра зависимости, не может подменить её. Текущий HTTP request не передаётся неявно.

`SetUp` сохраняет существующий контекст: получить provenance через `ObjectResolutionParameterStore`; развернуть явные значения атрибута; наложить их на окружающие публичные параметры через `ResolutionMetadata::mergePublicPreservingInternal()`; применить к суффиксу существующую parameter boundary.

В callback-ветви удалить из набора привязки ambient-позицию `0` и имя первого параметра. `SetUp::$params` сохраняет существующий набор параметров со строковыми ключами и правила сопоставления переданных параметров. Отклонять любой целочисленный ключ, включая зарезервированную позицию `0`, и любую явную попытку заменить имя первого параметра через `InvalidConfigurationException` до выполнения любого value unwrapper. Существующий ambient-набор публичных параметров по-прежнему может задавать позиции суффикса `1` и выше; их нельзя перенумеровывать. Смысловой объект остаётся доступным в разрешённом состоянии. Нельзя раскрывать приватный request provenance custom resolvers или handlers.

Так сохраняется неизменным `SetUpValueUnwrapperInterface::unwrap(mixed $value, string $key, ?ReflectionParameter $parameter)`. Ключ, совпадающий с именем параметра суффикса, разворачивается с фактическими reflection-метаданными этого параметра. Новая callback-ветвь не добавляет позиционные ключи в unwrapper API и не меняет существующую ветвь строкового метода. У callback-функции без объявленных параметров нет зарезервированного имени параметра; она всё равно отклоняет целочисленные явные ключи и получает ноль нативных аргументов по §5.1.

Остальные публичные строковые ключи, включая неиспользуемые имена и ключи-типы классов, остаются допустимыми. Как и в текущем `SetUpRunner::unwrapParams()`, их значения передаются подходящему unwrapper с reflection-метаданными `null`, а ключи сохраняются при объединении. Далее суффикс применяет существующие правила переданных параметров, включая сопоставление по ключу-типу и проверки границ источников; неиспользованные ключи не становятся дополнительными нативными аргументами. Существующая фильтрация приватных ключей DI сохраняется. Для callback-функции без объявленных параметров проверка строковых ключей и разворачивание значений с метаданными `null` также выполняются до вызова с пустым вектором аргументов. Нельзя вводить белый список объявленных имён параметров callback-функции или пропускать эти unwrappers только потому, что значение не используется параметром суффикса.

Есть одно необходимое расширение source boundary: сейчас `MappedRequestParameterSourceGuard` пропускает цель, у которой `ReflectionParameter::getDeclaringClass()` равен null. First-class callback-функции именованных функций и непривязанные замыкания могут не иметь declaring class. Для callback-варианта `SetUp` передавать созданный класс из `ObjectCreationContext` как внутренний аргумент диагностического владельца через точку входа суффикса и `ParameterResolutionBoundary` в source guard. Отсутствие declaring class не должно отключать проверку конфликтов источников, если этот владелец передан. Сохранять владельца при начальной проверке и проверках обновлённого плана. Нельзя кодировать его публичными ключами параметров или выводить владельца из типа первого параметра callback-функции. Обычный путь `resolvePrepared()` сохраняет существующий контракт, когда такой владелец не передан.

У ветви строкового метода нет зарезервированного первого аргумента; она сохраняет текущую привязку. Расширить reflection-вход `SetUpRunner::providedParameters()` и `unwrapParams()` с `ReflectionMethod` до `ReflectionFunctionAbstract`, чтобы существующие unwrappers получали фактический `ReflectionParameter` суффикса.

### 5.4 Ответственность за ошибки

| Ошибка | Владелец и результат |
| --- | --- |
| Недопустимый ABI первого аргумента или изначально зарегистрированные DI-атрибуты на нём | Binder либо защищённая точка входа parameter resolver бросает `InvalidConfigurationException` до выполнения callback-функции. |
| Поздние DI-метаданные первой цели или несовместимое изменение завершённого суффикса | Существующий `AttributeCompositionException`, подтип `InvalidConfigurationException`; тело callback не вызывается, завершённые handlers не повторяются. |
| Runtime-вход несовместим с первым параметром | `ResolutionException` параметра, дополненный контекстом соответствующей границы преобразования, свойства или lifecycle. |
| Ошибка зависимости или параметра суффикса | Существующая диагностика resolver и иерархия исключений Componenta. |
| Стороннее исключение внутри `Transform` | Существующая граница параметра/свойства создаёт `ResolutionException` и сохраняет причину. |
| Стороннее исключение внутри callback-варианта `SetUp` | Существующая граница объекта/lifecycle нормализует ошибку создания и сохраняет причину. |
| Цель явного обычного `container->call()` бросает исключение | Существующее поведение сохраняется: throwable из тела цели передаётся без изменения. |

Нельзя глобально менять обработку исключений `CallableInvoker`. Нельзя повторять выполнение callback-функции ради восстановления значения или улучшения диагностики. Уже принадлежащие Componenta исключения сохраняют идентичность согласно текущим границам. Неудачное преобразование свойства не должно фиксировать его ожидающее значение; неудачный setup не должен публиковать объект как успешно созданный shared service.

## 6. Детерминированное автовнедрение union-типов

Это независимое расширение resolver, а не предварительное условие базового callback-синтаксиса PHP 8.5.

### 6.1 Поддерживаемые кандидаты

Расширить `AutowireByTypeResolver` для не-variadic простых union-типов, все ветви которых — именованные типы. Собрать все non-builtin service IDs классов/интерфейсов, включая `Closure`, разрешить контекстные имена существующими type helpers и удалить эквивалентные имена типов без учёта регистра. Сохранить фактический ID каждого кандидата для существующего поиска в контейнере; это не вводит приведение регистра непрозрачных ID регистраций сервисов.

Нельзя разворачивать intersection в независимые альтернативы. Intersections и DNF unions с intersection-ветвями остаются вне неявного автовнедрения этого релиза; переданные значения по-прежнему проходят полную существующую проверку типа. Обычный именованный тип сохраняет существующее поведение. Отдельного запрета корректного явного binding `Closure::class` только для union-пути нет.

### 6.2 Алгоритм выбора

1. Сохранить существующие приоритеты resolver-компонентов. Применимые явные значения, атрибуты источников и более ранние custom resolvers завершаются до автовнедрения. Существующая семантика авторитетных источников сохраняется.
2. Запросить `container->has()` для каждого отдельного service ID кандидата. Это существующий контракт доступности, который может запускать автозагрузку; он не обещает отсутствия побочных эффектов или успешного создания.
3. Нет доступных кандидатов: вернуть вызывающему коду неразрешённое состояние. Создание через reflection и обычный DI-aware вызов callable затем используют существующий путь PHP-default, nullable и ошибки. Явные вызовы `ClassDefinition` сохраняют другой контракт пропуска аргументов, описанный в §6.3.
4. Доступен ровно один кандидат: один раз вызвать `get()` для его ID. В `AutowireByTypeResolver` потребовать, чтобы возвращённое значение реализовывало выбранный класс/интерфейс, затем сохранить полную проверку целевого типа. Совпадения с другой ветвью union недостаточно: выбранный binding `Service::class`, возвращающий замыкание, недопустим, хотя целевой тип — `Closure|Service`.
5. Доступно несколько кандидатов: бросить `ResolutionException` со стабильным отсортированным списком IDs кандидатов до вызова `get()` для любого из них. Нельзя выбирать по порядку объявления, анализировать тела фабрик или создавать всех кандидатов для сравнения идентичности объектов.
6. Если создание выбранного кандидата завершается ошибкой, передать его обычную ошибку разрешения. Нельзя молча пробовать другую ветвь, переходить к `null` или использовать default после начала создания.

Два разных ID интерфейсов, являющиеся aliases одной реализации, всё равно создают неоднозначность. Для вывода об идентичности разрешение не должно требовать исполнения фабрик. Явные аргументы или provider устраняют неоднозначность.

`supports()` классифицирует только форму объявленного типа. Доступность кандидатов и победитель вычисляются заново в `resolveParameter()` при каждом вызове; выбранный сервис никогда не кешируется в подготовленном плане параметров. Существующие runtime-мутации, изменения aliases и владения внешним контейнером должны быть видимы после прогрева плана. Опрашивать кандидатов в стабильном отсортированном порядке, чтобы порядок отражённых ветвей сам по себе не становился правилом выбора; сохранить существующий контракт ошибок `has()`, не анализируя фабрики сервисов.

Для `Closure|Service` явно зарегистрированный `Closure::class` участвует по тому же правилу `has()`, что и `Service`: две доступные ветви создают неоднозначность, одна доступная ветвь побеждает, отсутствие доступных ветвей оставляет параметр неразрешённым. Для `Closure|string` зарегистрированное замыкание — единственный возможный сервис-кандидат; `Closure` без binding не создаётся неявно. Явно переданные аргументы-замыкания остаются допустимыми через более ранний путь предоставленных значений. Enums, абстрактные классы и интерфейсы без binding также считаются доступными только по существующему `has()`. Исключение `Closure` только из union-пути в предыдущем проекте не опиралось на восстановленное требование или доказанную необходимость и удалено.

### 6.3 Общий resolver, разные контракты входа

Необязательное автовнедрение конструктора и настроенных публичных методов `ClassDefinition` также использует `AutowireByTypeResolver` через `FactoryResolver::arguments()`; проверить оба варианта по одним правилам выбора union-кандидата. Этот путь не выполняет цикл проверки результатов `ParametersResolver`, поэтому проверка совместимости выбранного кандидата принадлежит самому общему autowire resolver. Нативный вызов и существующие границы вызывающего кода сохраняются. Явные definitions сохраняют строгий lifecycle: никакой новой обработки атрибутов, неявной setup-фазы или автовнедрения, если оно не включено в definition.

Когда доступного кандидата нет, путь definition оставляет отсутствующий аргумент пропущенным. PHP может применить фактически объявленный default; обязательный nullable-параметр без default по-прежнему вызывает существующую ошибку отсутствующего аргумента. Нельзя добавлять в явные definitions неявный nullable fallback reflection-конвейера. Например, обязательный `Left|Right|null $value` без binding остаётся неразрешённым в `ClassDefinition`, тогда как `$value = null` может использовать нативный default. Паритет здесь означает одинаковый выбор кандидата, а не новый общий fallback или lifecycle-контракт.

При необходимости добавить отдельный type helper для допустимых кандидатов простого union-типа. Нельзя целиком менять назначение `TypeHints::classNames()`: сейчас он разворачивает intersections для обработки переданных ключей-типов, а это другая обязанность. Нельзя попутно менять приоритет `ArrayTypedResolver`.

## 7. Инварианты области видимости, времени жизни и кешей

Существующий `AttributeUsage::newInstance()` материализует атрибут во время выполнения. Планы хранят reflection-метаданные и композицию, а не runtime-результаты callback-функций или новые экземпляры атрибутов. Эту границу необходимо сохранить.

[Переносимый генератор](../audit/reproductions/Php85Callbacks.py) нового аудита и [запись точных fixtures и результатов](../audit/2026-11-13-php85-native-evidence.json) охватывают 14 сценариев на PHP 8.4.23 и 8.5.8. Два fixtures текущего `Init` перед наблюдениями DI проверяют пути исходников класса и внутренней функции относительно checkout. Чистые проверки движка не загружают DI. На PHP 8.5.8 наблюдалось:

| Происхождение callback-функции в аргументе атрибута | Повторная материализация | Поведение состояния |
| --- | --- | --- |
| Inline `static function` | Новое замыкание при каждой материализации атрибута. | Статические локальные переменные начинают новое состояние для этой материализации. |
| First-class ссылка на именованную функцию/статический метод | Новый wrapper-объект замыкания. | Статическое состояние принадлежит исходной функции/методу и разделяется между вызовами. |
| Константа класса, содержащая замыкание | Повторно использует объект замыкания из константы. | Состояние разделяется согласно времени жизни константы. |

Для четырёх последовательных материализаций вызовы в порядке первый/первый/второй/третий/четвёртый возвращают `[1, 2, 1, 1, 1]` для inline callback и `[1, 2, 3, 4, 5]` для ссылок на именованную функцию/статический метод и замыкания из константы. Слабые ссылки очищаются для освобождённых inline-замыканий и wrappers именованной функции/статического метода; константа класса закономерно сохраняет своё замыкание. Этот контроль отделяет идентичность wrapper от времени жизни состояния исходной функции.

Текущий `Init` даёт одинаковые результаты с кешированием и с no-op composition rule на трёх вызовах `make()`: inline-счётчики начинаются заново, счётчики именованной функции и константы продолжают расти, приватный статический helper получает DI-зависимость, а shared `get()` сохраняет идентичность. Объект в inline static local становится недостижим после создания. Lazy-инициализация выполняется только при первом доступе к свойству. Это проверенное существующее поведение, а не результаты прототипа предлагаемых `Transform` или callback-варианта `SetUp`.

Библиотека должна сохранять нативное поведение, а не обещать универсальную изоляцию всех callback-функций. Материализация атрибута может запускать автозагрузку или бросать исключение; пересборка guard и исходные причины ошибок должны сохраняться. Повторные разрешения, неудачные попытки и отложенная lazy-инициализация не должны удерживать через общие кеши метаданных runtime callback, смысловое значение, объект зависимости или `ReflectionObject`, которые иначе были бы недостижимы.

Нельзя кешировать callback по файлу/строке или `spl_object_id()`, извлекать его исходный код, сериализовать или воссоздавать его область видимости. Использовать стабильные метаданные классов/методов там, где это уже безопасно. Ноябрьское исправление изоляции кеша `ReflectionObject` — обязательная регрессия, которую нужно сохранить.

Последующий [аудит паритета кеша](../audit/2026-11-12-cache-parity-recheck.md) добавляет исполняемые контрольные сценарии этой границы. [ObjectAttributeCacheParityContractTest](../../tests/Contract/ObjectAttributeCacheParityContractTest.php) сравнивает обычные планы с публичным контролем через no-op composition rule, включая fixture `Init` со static local в inline closure, включаемый только на PHP 8.5. Повторная материализация должна сохранять нативное поведение PHP с новым замыканием, а каждый вызов — видеть текущую зависимость. Использовать этот контроль для `Transform` и callback-варианта `SetUp`; сравнивать значения, принадлежность исключений, число вызовов callback/handler и время жизни объектов, а не только итоговый scalar-результат.

Сохранить уточнённые границы discovery и classification у существующих владельцев. Обнаружение атрибутов, handlers объектов и классификация подготовленных параметров должны завершаться на согласованной ревизии реестра до публикации. Сохранить [регрессию исполнения и потребления параметров](../../tests/Contract/ParameterExecutionRevisionContractTest.php) нового аудита: согласованные slots и планы до выполнения, затем доказательство фактически потреблённого плана bridge. Новая граница разрешения суффикса не должна обходить эту стабилизацию или кешировать выбранное значение зависимости. Runtime-мутации должны сохранять идентичность незатронутых shared объектов наряду с инвалидацией изменённых bindings.

## 8. Версия PHP и совместимость релиза

Цель выпуска: DI 6 на PHP 8.5 с branch alias `6.0.x-dev`. Итоговое Composer-ограничение должно использовать проверенный минимальный patch из E1; широкое `^8.5` не является принятым обещанием, что каждый runtime этого диапазона выполняет нативный trait-контракт. Текущая ветка 5.x сохраняет PHP `^8.4`; ни одно исправление аудита не повышает её минимальную версию.

Пользователь разрешил реализацию в отдельной major-ветке; публичные изменения `SetUp` и union-поведения находятся в `refactor/di6-definitions-callbacks`. Пока E1 ожидает подтверждения, определённая здесь реализация библиотеки может оставаться синтаксически совместимой с PHP 8.4; проверять её через создание callback-функций, совместимое с PHP 8.4, и доступные fixtures нативных выражений PHP 8.5. Итоговый выбор платформы выпуска — отдельное последующее условие. Eval/subprocess fixtures с проверкой версии также могут оставаться в 5.x, если PHP 8.4 может разобрать содержащие их файлы и пропускает неподдерживаемый синтаксис до его вычисления. Диагностика известного дефекта движка не является успешно пройденной проверкой поддержки этой нативной формы.

Одно ограничение upstream отдельно от корректности DI. На PHP 8.5.8 атрибут, объявленный в trait с `self::who(...)`, возвращает результат первого класса-потребителя для обоих потребителей; `parent::who(...)` даёт соответствующую ошибку родительской области видимости. Ссылка на именованный приватный метод в trait также ошибочно сохраняет успешный результат проверки видимости для первого потребителя. Контроль с нативным inline static closure корректно разрешает каждого потребителя. Наблюдения получены из реальных attribute expressions, без DI и общих reflection-кешей, в приведённых выше переносимых доказательствах.

Исправление upstream — [php-src `44a2a2c3`](https://github.com/php/php-src/commit/44a2a2c3db9e4e06c41a0603c3826fac3b1b99f3) от 3 ноября 2026 года. Его [официальное сообщение и regression cases](https://news-web.php.net/php.cvs/143271) указывают **ветку PHP-8.6** и объясняют кеширование scope и видимости. Само это сообщение не доказывает backport в какой-либо релиз PHP 8.5. [Официальное объявление от 5 ноября](https://news-web.php.net/php.internals/133012) описывает 8.5.13RC1 как тестовый выпуск, а 19 ноября — как ожидаемую дату релиза. На дату этой перепроверки официальный стабильный релиз ветки 8.5 — [PHP 8.5.12](https://www.php.net/releases/8_5_12.php). Ни RC, ни будущая дата в NEWS, ни коммит в PHP-8.6 не доказывают, что PHP 8.5.13 уже выпущен или будет содержать нужное исправление.

Ограниченная проверка [исходников выпущенного `php-8.5.12`](https://github.com/php/php-src/blob/php-8.5.12/Zend/zend_ast.c#L1092-L1151) подтверждает отсутствие этой коррекции: ветвь static-call повторно использует закешированный `fptr` и по-прежнему записывает его безусловно, без новых ограничений `ZEND_FETCH_CLASS_DEFAULT` и `ZEND_ACC_PUBLIC`. [Официальный changelog](https://www.php.net/ChangeLog-8.php#8.5.12) датирует этот выпуск 22 октября 2026 года. Обычный набор DI CI проходит на PHP 8.5.12, но не выполняет эти переносимые trait fixtures; результат запуска trait-проверок на бинарном 8.5.12 здесь не заявлен. Проверка исходников оставляет E1 открытым для обещания поддержки затронутых форм.

### E1 — Проверить минимальный выпущенный patch PHP

**Заблокированная область:** итоговое объявление поддерживаемого patch-релиза DI 6 и обещание при выпуске, что все поддерживаемые runtime корректно реализуют затронутые trait first-class-reference формы. Binder, `Transform`, callback-вариант `SetUp`, реализация union-типов, тесты незатронутых нативных форм и работа над миграцией не заблокированы этой задачей получения платформенных доказательств. Числовой минимум patch-релиза здесь не выдумывается.

**Ограниченная задача получения решающих доказательств:** найти официально выпущенный patch PHP 8.5; проверить наличие исправления движка в исходниках его тега; выполнить upstream fixtures для trait `self::`/`parent::`, видимости именованного класса и двух классов-потребителей, а также примеры attribute expressions на этом точном бинарном файле. Зафиксировать релиз/тег, версию бинарного файла и результаты. Release candidate может дать сведения для исследования, но не выполняет условие стабильного релиза. Нельзя расширять задачу до обхода дефекта движка или нового механизма callback scope в DI.

**Условие завершения и снятия блокировки:** когда выпущенный patch проходит эти fixtures, обновить раздел фактическим минимумом, доказательствами по исходникам тега и соответствующей целью Composer/CI. Если ни один выпущенный patch не удовлетворяет доказательствам, затронутое условие платформы/выпуска остаётся заблокированным, а независимо готовая работа над библиотекой может продолжаться. Нельзя заявлять полную корректность trait-relative callbacks на проверенном runtime 8.5.8. Inline static closure без захватов или полностью квалифицированная ссылка на публичный helper — временная альтернатива на уровне приложения в пределах проверенной области; DI не должен эмулировать или перепривязывать нативный lexical scope.

| Работа или обещание | Готовность |
| --- | --- |
| Примеры нативных выражений существующего `Init` и совместимые regression fixtures | Готово; фактическое текущее поведение записано. |
| Общий binder, `Transform`, callback-вариант `SetUp`, простое union-поведение | Реализовано в разрешённой major-ветке; проверены поддерживаемые формы, E1 остаётся открытым. |
| Корректные trait-relative/mixed-visibility first-class references на минимальном поддерживаемом runtime | Заблокировано E1; PHP 8.5.8 доказанно не проходит проверку. |
| Итоговый Composer floor DI 6, CI поддерживаемых runtime и релиз, обещающий этот scope-контракт | Заблокировано доказательством выпущенного patch-релиза, затем обычными условиями реализации и выпуска. |
| Callback request-to-DTO | Независимо заблокирован семантическими решениями §11. |

Проверка совместимости должна охватить существующие подклассы `SetUp` и именованные аргументы, string/array/invokable-входы `Init`, определения extension handlers, декорированные сервисы `CallableInvokerInterface`, ограничения связанных пакетов и приложения, включающие автовнедрение `ClassDefinition`. Перед предложением согласованных повышений версий использовать реальные manifests и test suites потребляющих пакетов. Добавление здесь синтаксических тестов само по себе не требует релиза постороннего пакета.

Для подклассов `SetUp` есть конкретная миграция major-версии: подкласс, повторно объявляющий или продвигающий через constructor promotion `public string $method`, должен расширить свойство до такого же типа `string|Closure` либо удалить повторное объявление. Инвариантность свойств PHP отвергает более узкое повторное объявление после изменения родителя. Параметр конструктора типа `string`, который только передаётся родителю и не объявляет свойство повторно, может остаться более узким. Эти случаи нужно документировать и проверить; нельзя описывать расширение типа как безусловно совместимое с исходным кодом.

Прямое создание инфраструктурного handler `SetUpRunner` меняется в этой major-версии: конструктор принимает `CallableInvokerInterface`, `ObjectResolutionParameterStore`, затем общий `AttributeCallbackInvoker`, после которого идут существующие variadic-экземпляры `SetUpValueUnwrapperInterface`. Единственное место создания внутри репозитория — `ContainerFactory`; внешние прямые потребители вставляют helper перед своими unwrappers. Это не меняет имена и порядок аргументов конструктора атрибута и не добавляет legacy-путь handler.

## 10. Производный план реализации

**Участки библиотеки 1–5 реализованы в разрешённой major-ветке. Участок 6 содержит оставшиеся проверки, документацию и условия выпуска.** E1 блокирует обещание поддержки затронутых нативных форм и итоговое решение о платформе. Эти изменения не добавляют возможности задним числом в опубликованную ветку 5.x.

Каждый завершённый срез должен пройти review и проверки, быть закоммичен и отправлен в ветку. Срезы 3 и 4 зависят от binder из среза 2; работа с union в срезе 5 от этого binder независима. Ни один срез не должен оставлять два конкурирующих алгоритма разрешения. Требования доказательств ниже определяют завершённость; подготовка выпуска по-прежнему зависит от E1.

### Срез 1 — Зафиксировать нативное поведение и контроли существующего `Init`

Файлы: `README.md`, новый каталог fixtures PHP 8.5 и `tests/Contract/Php85AttributeCallableContractTest.php`; сохранить переносимый reproduction аудита как историческое доказательство.

Добавить fixtures синтаксиса/scope/lifetime и end-to-end случаи `Init` на существующей реализации. Fixtures ошибок компиляции держать вне обычного обнаружения тестов и подтверждать пути исходников при использовании установленного Composer-графа. Разделить проверенные нативные формы и диагностику известной ошибки trait; после разрешения E1 выполнять последнюю как регрессию корректного поведения на минимальной поддерживаемой версии. Нельзя менять манифест только ради начала этой работы или добавлять в DI обходной путь для дефекта движка.

Готово, когда проверенные нативные примеры выполняются через реальный контейнер, прежние представления `Init` по-прежнему проходят проверки, нативные контроли состояния/времени жизни совпадают, а нерешённый вопрос минимального patch явно выделен в E1.

### Срез 2 — Добавить границу смыслового первого аргумента

Файлы: новый `src/Internal/AttributeCallbackInvoker.php`; `src/Resolver/Parameter/ParametersResolver.php`; `src/Internal/Resolver/Parameter/ParameterResolutionBoundary.php`; `src/Internal/Resolver/Parameter/Request/MappedRequestParameterSourceGuard.php`; новый целевой `tests/Contract/AttributeCallbackInvocationContractTest.php`.

Зависит от нативного baseline и контракта §5, а не от E1. Выделить только существующий цикл сборки аргументов в общую приватную реализацию, принимающую начальный префикс/разрешённое состояние и доказательство зарезервированной цели. Добавить внутреннюю точку входа суффикса; не проводить первый параметр через классификацию. Держать проверку только его метаданных и завершённые параметры суффикса в одном guard до итоговой стабилизации. Передавать необязательного внутреннего диагностического владельца через начальные и обновлённые source-boundary checks, чтобы суффиксы setup без declaring class оставались защищёнными. Binder использует существующие строгие правила принятия типов и вызывает через `PreparedCallable` и существующий invoker. Новый публичный configuration key или extension interface не нужен.

Готово, когда попытки подмены первого слота отклоняются или игнорируются согласно контракту, extensions суффикса видят корректное состояние, декораторы видят один подготовленный вызов, сохраняется нативный пропуск default и проходят lifetime-регрессии. Поведение обычного callable suite не должно измениться.

### Срез 3 — Добавить `Transform` с существующей композицией и staging

Файлы: новый `src/Attribute/Transform.php`; новый `src/Resolver/Attribute/Handler/TransformHandler.php`; `src/ContainerFactory.php`; новый `tests/Contract/TransformContractTest.php` и fixtures property hooks.

Зависит от среза 2. Подключить один binder, общий для двух новых потребителей. Зарегистрировать capability/порядок, реализовать точный fallback источника, использовать существующие pending reads/writes свойств и добавить диагностику на владеющей цели. Нельзя менять семантику присваивания `ObjectCreationContext` или порядок глобальной resolver-цепочки.

Готово, когда строки параметров/свойств из §9 проходят проверки, callback выполняется один раз на применение, порядок смешанных преобразований стабилен, а случаи setter/readonly с ошибками демонстрируют одну итоговую запись.

### Срез 4 — Расширить `SetUp`, сохранив путь метода

Файлы: `src/Attribute/SetUp.php`; `src/Resolver/Entry/SetUpRunner.php`; `src/ContainerFactory.php`; новый `tests/Contract/SetUpCallbackContractTest.php`; существующие регрессии setup/environment/provenance.

Зависит от среза 2 и major-ветки. Расширить тип конструктора/свойства, не переименовывая его. Добавить диспетчеризацию замыкания через binder с созданным классом как приватным диагностическим владельцем, расширить reflector, принимаемый при unwrapping, сохранить приватное хранилище контекста и правило merge, отклонять явные целочисленные ключи или подмену имени первого параметра до unwrapping. Сохранить ambient-позиции суффикса и существующий unwrapper interface с именованными ключами. Сохранить проверку строки и существующее поведение вызова метода. Проверить полный mapped-request путь как с callback именованной функции, так и с class-scoped closures.

Готово, когда callbacks выполняются после инъекции свойств, повторные hooks идут по порядку, возвращаемый объект не может заменить entry, а setup через метод и request source guards сохраняют прежние результаты.

### Срез 5 — Независимо расширить выбор union-кандидата

Файлы: `src/Resolver/Parameter/AutowireByTypeResolver.php`; при необходимости небольшой helper в `src/Resolver/TypeHints.php`; `tests/Contract/UnionAutowiringContractTest.php`; contract tests `ClassDefinition`.

Зависит от §6 и major-ветки, а не от callback binder или E1. Реализовать сбор кандидатов и проверку их количества до `get()`, а после него — проверку совместимости выбранного кандидата в общем resolver. Применять существующие правила доступности одинаково к `Closure` и другим именованным ветвям. `supports()` должен оставаться независимым от изменяемой доступности сервисов; сохранить приоритет, обработку переданных ключей-типов, поведение intersection/DNF и opt-in семантику definition. Добавить стабильную диагностику неоднозначности, мутации прогретого плана и случаи ошибки выбранной фабрики для создания через reflection и явных definitions конструктора/метода.

Готово, когда счётчики фабрик доказывают, что неоднозначность не вызывает `get()` кандидатов, ровно один кандидат создаётся один раз, а explicit values/default/null/definition случаи соблюдают §6.

### Срез 6 — Проверить стоимость, миграцию и итоговую подготовку релиза

Файлы: `README.md`; документация миграции; целевые дополнения существующих benchmark harnesses только для новых путей; `composer.json` и `.github/workflows/ci.yml` для итогового решения о поддерживаемой платформе.

Документация и измерения могут продвигаться по мере завершения соответствующих срезов. Сравнить обычное поведение get/make/call/build с зафиксированным коммитом до добавления возможностей, а также ноль/одно/несколько преобразований, callback setup и разное число union-кандидатов. Только после разрешения E1 установить проверенный минимальный patch PHP и alias `6.0.x-dev`, согласовать CI поддерживаемых runtime и зафиксировать точную проверенную платформу в документации миграции. Выполнить применимую CI matrix, текущие тесты связанных workspaces и проверки зависимостей. Подтвердить, что минимальный выпущенный patch проходит engine fixtures. Зафиксировать команды и результаты; не выводить пропускную способность приложения из microbenchmarks. Tag/release — отдельное действие после завершения реализации и всех условий проверки. Незавершённый E1 нельзя переименовывать в production readiness затронутых нативных форм.

## 11. Отложенная работа и ограниченные задачи принятия решений

### Callback request-to-DTO — возможная версия 6.1

Восстановленные заметки предлагали последний необязательный аргумент `transform` у `MapRequest` и его source-specific подклассов. Он не нужен для `Transform` или `Init` и в этой спецификации не готов к реализации.

До реализации определить, преобразует ли он mapped array или готовый DTO; прежний замысел — mapped array до создания DTO. Сохранить текущий конкретный порядок: валидация raw request, затем операции mapper `map → cast → defaults → sort → exclude`, затем новый callback всего массива, затем существующие проверки именованных ключей/конфликтов источников и создание DTO. Требовать массив в результате и сохранять provenance исходных полей. Нельзя обходить валидацию или раскрывать приватные transport metadata зависимостям callback-функции.

Ограниченный следующий шаг: проверить конструкторы каждого подкласса `MapRequest` и текущие места вызова `RequestMapper`/`RequestAttributeHandler`, составить точную таблицу сигнатур и provenance, проверить удаление/переименование raw keys, числовые ключи, конфликтующие source attributes, ошибки callback и создание вложенных DTO. Только после этого подготовить отдельные срезы реализации. Спекулятивные изменения сигнатур не входят в этот аудит.

### Производительность недоступных атрибутов

Рассматривать измеренную проблему повторной автозагрузки по отдельному [плану производительности availability](attribute-availability-performance.md). Callback-синтаксис не требует ослаблять гарантии поздней загрузки, вводить сроки опроса или новый постоянный кеш.

### Зафиксированные политики и проверка соответствия

Следующие положения — нормативные решения для предлагаемой цели, а не открытые вопросы: callbacks с пустой сигнатурой разрешены; DI-метаданные первого параметра запрещены и проверяются вместе с суффиксом; суффикс `Transform` не получает ambient-набор публичных параметров; явные `SetUp::$params` callback-варианта используют строковые ключи с существующими правилами сопоставления переданных параметров; самостоятельному преобразованию свойства нужен источник; автовнедрение распространяется только на простые unions; `Closure` использует те же правила доступности, что и другие ветви сервисных типов; разные service IDs остаются неоднозначными даже при совпадении целей aliases. Если решение меняется, до реализации пересмотреть владеющий контракт и строки приёмки. E1 блокирует обещание поддержки затронутой платформы при выпуске, а отдельные вопросы request-to-DTO блокируют только эту отложенную возможность.

При сверке реализации сравнить код, wiring, публичные заметки миграции и наблюдаемое поведение с §§2–9. Устранить отсутствующее, частичное, противоречащее или незапрошенное поведение у его владельца. В частности, убрать дублирование цикла разрешения аргументов, непреднамеренную передачу публичных метаданных, постоянный альтернативный callback-путь, изменение поведения строкового метода или расширение union/DNF-политики. Одного прохождения тестов недостаточно, чтобы утверждать, что реализована именно эта архитектура.
