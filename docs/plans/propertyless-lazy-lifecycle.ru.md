# Ленивое создание классов без сохраняемых свойств экземпляра

**Статус:** D1/A реализовано. Стандартный нативный `ProxyFactory` отклоняет класс без сохраняемых свойств экземпляра до выделения объекта. Этот документ сохраняет обоснование, границы совместимости и критерии приёмки.

[English version](propertyless-lazy-lifecycle.md)

## 1. Подтверждённый дефект и его значение

Привязанные к проверенному commit исходные границы: [`ProxyFactory::makeLazy()` L21](https://github.com/componenta/di/blob/897f8b10ca6537e7b2f96d20b2e00ed52571ff6f/src/ProxyFactory.php#L21) и [`makeProxy()` L40](https://github.com/componenta/di/blob/897f8b10ca6537e7b2f96d20b2e00ed52571ff6f/src/ProxyFactory.php#L40); deferred-контракты [`LazyObjectFactoryInterface` L20](https://github.com/componenta/di/blob/897f8b10ca6537e7b2f96d20b2e00ed52571ff6f/src/LazyObjectFactoryInterface.php#L20) и [`VirtualProxyFactoryInterface` L20](https://github.com/componenta/di/blob/897f8b10ca6537e7b2f96d20b2e00ed52571ff6f/src/VirtualProxyFactoryInterface.php#L20); отложенный lifecycle [`ObjectPipeline::lazy()` L296](https://github.com/componenta/di/blob/897f8b10ca6537e7b2f96d20b2e00ed52571ff6f/src/Object/ObjectPipeline.php#L296) и [`proxy()` L343](https://github.com/componenta/di/blob/897f8b10ca6537e7b2f96d20b2e00ed52571ff6f/src/Object/ObjectPipeline.php#L343); фабрика продукта [`MakeHandler::create()` L213](https://github.com/componenta/di/blob/897f8b10ca6537e7b2f96d20b2e00ed52571ff6f/src/Resolver/Attribute/Handler/MakeHandler.php#L213); делегирование выбранному адаптеру [`Container::makeLazy()` L293](https://github.com/componenta/di/blob/897f8b10ca6537e7b2f96d20b2e00ed52571ff6f/src/Container.php#L293) и [`makeProxy()` L298](https://github.com/componenta/di/blob/897f8b10ca6537e7b2f96d20b2e00ed52571ff6f/src/Container.php#L298).

В исходной точке аудита `ProxyFactory::makeLazy()` и `makeProxy()` возвращали результат нативного метода PHP, не проверяя, остался ли созданный объект ленивым. Для классов, допустимых для нативной ленивости, PHP намеренно возвращает обычный объект, если нет сохраняемых свойств экземпляра (*backed instance properties*). Это классы совсем без свойств, только со статическими свойствами либо только с виртуальными property hooks. Инициализатор или фабрика целевого объекта в таком случае не вызываются вообще. Последующий вызов `ReflectionClass::initializeLazyObject()` ситуацию не исправляет.

В результате reflection-путь DI успешно возвращает и сохраняет как shared-сервис объект с `#[Lazy]` или `#[Proxy]`, у которого не выполнены конструктор и `#[SetUp]`. `#[NoConstructor]` не делает результат правильным: конструктор действительно следует пропустить, но настроенный setup по-прежнему должен выполняться. Точка внедрения `#[Make('id'), Proxy(Target::class)]` может вернуть объект, ни разу не вызвав зарегистрированную фабрику продукта. Это ошибка жизненного цикла, а не просто неработающая оптимизация.

Публичные интерфейсы уже обещают отложенный callback и относят его последующую ошибку к самому callback. [`Lazy`](../../src/Attribute/Lazy.php) обещает выполнение конструктора для reflection-сервисов; [`NoConstructor`](../../src/Attribute/NoConstructor.php) сохраняет внедрение свойств и setup. Успешный возврат с молчаливым пропуском не соответствует этим контрактам. Эксплуатируемая уязвимость конкретного приложения не установлена; проверки или регистрация, которые приложение поместило в конструктор, могут быть пропущены.

## 2. Почему немедленный eager fallback не является безопасной локальной правкой

Очевидный на первый взгляд вариант — немедленно вызвать callback, если нативное создание вернуло уже не ленивый объект. У него три существенных последствия:

1. Меняется явное обещание отложенного callback. Его ошибка перемещается с последующего обращения к свойству на вызов создания. Текущий `catch` внутри `ProxyFactory` также начнёт нормализовать ошибки, которые раньше принадлежали вызывающему deferred callback.
2. Для proxy фабрика создаёт или возвращает второй объект. Возвращение этого объекта меняет identity публичного результата: вместо обёртки возвращается непосредственно продукт фабрики. Возвращение прежней заготовки теряет состояние и identity фабричного объекта.
3. У обычной заготовки работает деструктор. Прототип в воспроизведении получает `constructor, destructor` **до освобождения возвращённого продукта**, а после его освобождения — ещё один деструктор. Один вызов фабрики вызывает два события уничтожения, одно из них — на объекте с невыполненным конструктором. У корректного нативного proxy используется деструктор целевого объекта.

Прототип реализован отдельной функцией воспроизводящего скрипта и не меняет `src/`. Удерживание заготовки только откладывает лишний деструктор и добавляет проблемы владения и времени жизни. `resetAsLazy*()` не превращает класс без сохраняемых свойств в ленивый. Искусственное свойство или сгенерированный подкласс меняют форму/identity класса и не работают универсально с final-классами. Такие обходные пути нельзя добавлять молча.

## 3. Решение D1 и варианты

| Вариант | Публичный результат | Владение и совместимость | Оценка |
|---|---|---|---|
| **A. Отказ до нативного выделения** | DI-исключение сообщает класс и стратегию; целевой экземпляр не выделяется, callback не вызывается | Ограничением владеет стандартный нативный адаптер; deferred-контракты и пользовательские реализации сохраняются | **Принятый целевой контракт** |
| B. Eager fallback в высокоуровневых object/factory-путях DI | Конструктор, setup или фабрика выполняются сразу, без лишней proxy-заготовки | Нужно явно выбрать время выполнения, различие высокоуровневого и прямого API, identity и обработку ошибок; несколько callers меняются согласованно | Не выбран; отдельный проект, если потребуется позже |
| C. Универсальный eager fallback внутри `ProxyFactory` | Callback вызывается сразу с выделенной заготовкой | Нарушает deferred-контракт и даёт доказанный лишний деструктор | Отклонить |
| D. Сохранить успешный пропуск и описать его | Внешне успешный, но не полностью инициализированный сервис | Не выполняет требования жизненного цикла | Отклонить |

**D1 разрешён в пользу A, и этот контракт реализован.** Первоначальный аудит обоснованно оставил выбор отказа либо eager-выполнения открытым: оба варианта меняют наблюдаемое поведение. После рекомендации и объяснения компромиссов инструкция пользователя завершить работу приняла A. Реализация следует разделам 4–6; незакрытого подтверждения выбранного поведения нет. B не входит в это изменение; C и D остаются отклонёнными по причинам выше.

## 4. Установленные требования и сохраняемое поведение

- **R1:** успешное создание DI не должно молча терять конструктор/setup или переданную фабрику из-за превращения нативного ленивого выделения в обычное.
- **R2:** исправление не должно выделять лишнюю обычную заготовку, деструктор которой создаёт дополнительный прикладной эффект.
- **P1:** классы с допустимыми сохраняемыми свойствами экземпляра сохраняют deferred-время вызова, повторные попытки, порядок жизненного цикла отдельной попытки и нативные identity ghost/proxy.
- **P2:** `NoConstructor` пропускает только конструктор, сохраняя setup и property handlers.
- **P3:** ограничения стандартного нативного адаптера нельзя глобально переносить на пользовательский `ProxyFactoryInterface`, который может поддерживать другие механизмы. Сам интерфейс допускает альтернативные реализации.
- **P4:** `ClassDefinition` остаётся eager и не исполняет атрибуты класса/свойств/параметров. Обычная прикладная фабрика по-прежнему отвечает за инициализацию своего продукта. Дефект затрагивает reflection-стратегии, явное proxy-внедрение и фабрики, которые сами обращаются к API ленивого создания. Один атрибут `#[Proxy]` на классе не переопределяет работу непрозрачной фабрики.
- **P5:** автозагрузка класса и прежние эффекты расширений before-instantiation не откатываются. Исправление предотвращает **новое выделение целевого экземпляра и эффекты callback** на границе нативного адаптера; оно не обещает полную атомарность произвольного разрешения.

## 5. Принятое целевое поведение варианта A

Этот раздел определяет принятый контракт D1/A. Реализация должна оставаться в границе стандартного адаптера и сохранять требования раздела 4.

### Владелец и граница

Стандартный [`ProxyFactory`](../../src/ProxyFactory.php) владеет проверкой возможности до выделения для обоих методов: `makeLazy()` и `makeProxy()`. Сохранить два существующих публичных интерфейса. Одну private-проверку переиспользовать внутри адаптера; новый реестр допустимости, capability-сервис, feature flag, стратегия или кеш не нужны.

`Container::makeLazy()/makeProxy()`, `ObjectPipeline::lazy()/proxy()`, `MakeHandler::create()` и потребители `LazyServiceFactoryInterface` продолжают вызывать выбранную фабрику через существующие интерфейсы. DI-исключение адаптера проходит через действующие правила сохранения исключений. Пользовательские фабрики не попадают под проверку стандартного адаптера вследствие текущего выбора реализации, а не благодаря новому глобальному выключателю.

### Правило нативной возможности

До вызова `newLazyGhost()` или `newLazyProxy()` проверить класс и всю цепочку наследования. Объявленное свойство может дать нативный ленивый слот, только если оно **не static** и **не virtual**. Учитывать private-свойства каждого предка, даже когда их нет в `getProperties()` конечного класса. Backed-свойство с get/set hooks подходит; виртуальное — нет. Readonly и promoted backed-свойства подходят. Для проверки нельзя читать значения свойств, вызывать hooks, создавать экземпляр или вычислять аргументы пользовательских атрибутов.

Если допустимый для нативного механизма пользовательский класс не имеет ни одного такого слота, отклонить запрос до выделения. Для `stdClass` и его потомков применять то же правило: потенциальная возможность добавить dynamic properties не делает пустой объект ленивым. Пользовательский подкласс `stdClass` с backed-свойством остаётся допустимым.

Сохранить приоритет прежних нативных ошибок. Несуществующий класс по-прежнему отклоняется при создании `ReflectionClass`. Interface, trait, abstract, enum и внутренний класс кроме `stdClass`, включая пользовательских потомков неподдерживаемого внутреннего класса, обходят новую проверку отсутствия слотов и попадают в прежний нативный вызов с его нормализацией исключения. Определять эту границу reflection-флагами вида класса и всей цепочкой внутренних предков, без пробного выделения объекта. Не заменять её `isInstantiable()`: private/protected-видимость конструктора — отдельное ограничение, не эквивалентное допустимости нативной ленивости. Эталон приёмки — ошибка соответствующего `newLazyGhost()` / `newLazyProxy()`: адаптер сохраняет её нативный `previous`, не подменяя новым сообщением об отсутствии слота. Наличие backed-слота не делает неподдерживаемый внутренний класс допустимым.

Это необходимое условие стандартного адаптера, а не обещание, что PHP примет все остальные сочетания свойств и флагов. Для прочих ограничений нативное выделение остаётся источником истины. Постоянный кеш до измерений не нужен; обход свойств выполняется при запросе новой обёртки, а не на shared-попадании `get()` или каждом чтении свойства.

### Контракт ошибки

Выбрасывать `ResolutionException`, устанавливая `serviceId` в каноническое имя целевого класса. Использовать сообщение `Cannot create native %s for class "%s": no backed instance properties; use eager construction instead.`, подставляя стратегию `lazy ghost` либо `virtual proxy` и каноническое имя класса. Новый отдельный подкласс исключения не нужен. Намеренный отказ допустимости не содержит искусственного нативного `previous`. Диагностические поля не должны удерживать callback, reflection-объект или сервис.

Владение данными DI-диагностики нужно отличать от нативного trace исключения PHP. При `zend.exception_ignore_args=0` сохранённое исключение может удерживать аргумент-callback через trace. Этот контракт не очищает trace и не обещает сборку captures при таком режиме, пока исключение сохранено. Lifetime-тест с сохранённым исключением должен временно установить `zend.exception_ignore_args=1` и восстановить исходное значение; другой допустимый вариант — освободить и исключение, и ссылки вызывающей стороны до проверки сборки.

Инициализатор, фабрика продукта, конструктор целевого объекта, setup, setter и деструктор целевого объекта не должны вызываться **из-за выделения адаптером** при таком отказе. Неуспешное разрешение контейнера не публикует shared-значение; последующее обычное eager-создание или явно выбранная пользовательская фабрика может успешно работать. Для поддерживаемых ленивых классов прямые callbacks по-прежнему выбрасывают свои последующие исключения при инициализации с исходной identity; не оборачивать callback только ради этой проверки.

### Совместимость и выигрыш

Приложения, запрашивающие нативную ленивость для таких классов, получают определённую ошибку вместо неполноценного успешного сервиса. Для eager-создания через reflection убрать соответствующий lazy/proxy-атрибут класса или точки внедрения. Замена `get()` на `make()` сама по себе не отключает атрибуты и не выбирает eager-создание. Reflection-путь сохраняет обычное внедрение свойств и setup; `NoConstructor` по-прежнему пропускает только конструктор.

Другой вариант — явная обычная прикладная фабрика или `ClassDefinition`. Фабрика отвечает за инициализацию своего результата; `ClassDefinition` немедленно вызывает конструктор и явные инструкции `call()`, игнорируя DI-атрибуты, включая `SetUp`. Необходимую инициализацию следует перенести в выбранную фабрику либо явные вызовы. Один `#[Proxy]` на классе не оборачивает продукт непрозрачной фабрики. Допустима и пользовательская реализация `ProxyFactoryInterface` с отдельно проверенным поддерживаемым механизмом, сохраняющая контракты отложенных callbacks. Добавлять бессмысленное свойство только ради появления lazy-триггера не рекомендуется.

Выигрыш — корректный жизненный цикл и диагностируемая граница нативной возможности. Ускорение не является целью. Production-правка локальна; объём интеграционных проверок шире, потому что адаптер обслуживает несколько публичных путей. Численное ускорение или сокращение памяти не заявляется.

| Явная фабрика продукта | `Make + Proxy` для свойства и параметра; неподдерживаемый класс не возвращает заготовку; обычная eager-фабрика сохраняет свой вызов и результат |
| P3: расширения | Существующая fixture пользовательской фабрики/декоратора получает запрос; глобальная проверка не блокирует поддерживаемый сценарий альтернативной реализации |
| P4: явные definitions | Тот же класс без свойств через `ClassDefinition` создаётся eager по действующему контракту |
| Диагностика и lifetime | В полях DI-диагностики только метаданные класса/стратегии; после освобождения caller проверять сборку captures при сохранённом исключении только с временным `zend.exception_ignore_args=1` либо освобождать и исключение; очистка trace не обещается |
| Проверка реализации | Целевой RED/GREEN на PHP 8.4/8.5; полный существующий suite, PHPStan max, стиль; применимая CI matrix, включая Windows |

Проверка реализации охватывает R1–R2 и P1–P5: время проверки до выделения, делегирование пользовательским фабрикам и отсутствие eager fallback. [Отчёт об исправлении](https://github.com/componenta/di/blob/80cb69a59f001a7d9c49af6e254ff3f58ffa8504/docs/audit/2026-11-16-propertyless-lazy-fix.ru.md) фиксирует целевые RED/GREEN-доказательства и регрессионные проверки. Новые проверки наблюдают публичное поведение, не используют private-счётчики кеша или произвольные временные пороги.

## 7. Статус и дальнейшие изменения

D1/A завершено в [`299ee93`](https://github.com/componenta/di/commit/299ee93f6be6d91e3a4fc1372389f1fff953d61b); все пять обязательных jobs прошли в [CI 43774753909](https://github.com/componenta/di/actions/runs/43774753909). Контрактные тесты остаются частью обычного набора проверок библиотеки.

Вариант B не выбран. Возможная будущая поддержка eager-создания требует отдельного решения о поведении прямого и высокоуровневого API, identity, моменте конструктора и setup, исключениях, повторной попытке и пользовательских адаптерах. Eager-путь должен выбираться до выделения placeholder и использовать существующий object pipeline или фабрику приложения. Проверки `isUninitializedLazyObject()` после выделения для этого недостаточно.
