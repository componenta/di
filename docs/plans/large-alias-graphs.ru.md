# Холодное построение больших графов alias

[English version](large-alias-graphs.md)

**Статус на 2026-11-20:** сохранённое условное предложение по производительности. Переписывание графа, ограничение alias или новый публичный контракт не выбраны. Работа начинается только при подтверждённой существенной стоимости построения alias в профиле реального потребителя. Это отдельная тема относительно [B2](attribute-availability-performance.ru.md) и уже исправленной инвалидации семейств alias в [архитектуре владения definitions](definition-owner-lifecycle.ru.md).

## 1. Проблема и исторические доказательства

Четвёртый полный повторный аудит отметил зависимость стоимости холодного построения от порядка вставки: проверка очередного alias может снова проходить уже собранную цепочку его цели. Для цепочки, заданной от ближайшего к конечной цели alias, сумма проходов может быть квадратичной относительно длины цепочки. Успешное разрешение отдельно использует сжатие путей; наблюдение о построении не описывает прогретый lookup. Пятый аудит сохранил отдельное условное предложение проверки графа целиком.

## 2. Почему требуется отдельное проектирование

Предполагаемый выигрыш — сокращение работы при запуске для подтверждённой большой конфигурации alias. Выигрыш прогретого shared retrieval этим предложением не установлен. В большинстве приложений граф может быть небольшим или неглубоким; новый алгоритм и временное состояние без измеренной необходимости добавят стоимость сопровождения и памяти без установленной пользы пользователю.

Изменение порядка проверки способно изменить первую наблюдаемую ошибку. Быстрый обход должен сохранить выбранные правила неверных ID, self-reference и циклов, а также детерминированную диагностику цепочки. Одного обнаружения существующего цикла недостаточно, если потребитель полагается на документированную диагностику или порядок отказа.

Пути допуска ID нужно различать: числовая строка, допустимая для runtime API со строковым аргументом, не равна integer array key после приведения ключа PHP в карте конструктора. Текущий конструктор отклоняет целочисленные ключи alias. Предложение сохраняет эти границы, а не объявляет все числовые ключи допустимыми.

Начальная массовая проверка и последующие мутации имеют разные границы публикации. `AliasResolver::set()`, используемый `Container::alias()`, не должен публиковать отклонённый вариант или инвалидировать прежний допустимый кеш. Успешная мутация сохраняет существующие правила инвалидации потомков/отложенных потребителей, публикации и освобождения. Оптимизация конструктора не должна случайно переписать эти гарантии.

## 3. Варианты и рекомендация

| Вариант | Возможный выигрыш | Цена и решение |
|---|---|---|
| Сохранить текущее построение и разрешение | Совместимость не меняется; имеющийся прогретый путь остаётся. | Рекомендуется без прикладного подтверждения существенной холодной стоимости. |
| Первичная проверка всего графа с visited/color-состоянием | Цель O(V+E) для графа из V ID и E alias-рёбер; не повторяются полные проходы по уже проверенным цепочкам. | Нужны явный порядок диагностики, ограниченная временная память и отдельный контракт публичной мутации. Условный кандидат. |
| Переупорядочить конфигурацию самого приложения | Может уменьшить конкретный исторический худший случай. | Требуется сохранить семантику прикладной конфигурации; это не прозрачная гарантия библиотеки и не замена проверкам корректности. Только для конкретного потребителя. |
| Ввести произвольный предел длины цепочки или запрет больших графов | Ограничивает одну синтетическую форму входа. | Меняет допустимую конфигурацию без установленной потребности. Не выбрано. |
| Переписать прогретые кеши или добавить новый слой графа сервисов | Польза из имеющихся данных о холодном построении не установлена. | Расширяет объём изменений и затрагивает requested-ID, identity и инвалидацию. Не обосновано этим предложением. |

**Рекомендация:** сохранить реализацию до подтверждения потребности реальным профилем. При выполнении этого условия исследовать один вариант массовой проверки внутри существующего владельца alias. Наличие синтетического худшего случая само по себе не выбирает новый графовый слой, persistent compiler или произвольный предел размера.

## 4. Условный план реализации

1. **Установить нагрузку потребителя.** Зафиксировать размер, глубину, ветвление и порядок графа, частоту построения и долю alias в общей стоимости запуска. Сохранить репрезентативную конфигурацию либо обезличенный структурный fixture. Отличать однократный startup от пересоздания на каждом запросе.
2. **Разделить измеряемые фазы.** Отдельно измерить конструктор, первое разрешение, повторное разрешение со сжатием путей и публичное построение контейнера на одинаковом runtime/окружении. Исторический общий интервал оставить историческим сравнением, не объявлять новым baseline конструктора. Включить небольшие обычные графы.
3. **Задать проверку совместимости.** Зафиксировать приоритет malformed/empty ID, self-reference и нескольких циклов. Определить детерминированный выбор диагностической цепочки для порядка вставки. Сохранить допустимые непрозрачные и числовые строковые ID, конечные ID без alias, общий terminal нескольких alias и семантику delegators requested-ID. Намеренное изменение диагностики требует явного решения о миграции.
4. **Подготовить один вариант начальной проверки.** Состояние обхода исключает повторное посещение завершённых путей; цель — O(V+E) посещений и временная память, ограниченная размером графа. Описать, как длинные цепочки обходятся без неограниченной рекурсии стека. Готовая исходная карта публикуется только после всех обязательных проверок.
5. **Сохранить транзакционность runtime-мутации.** Массовая проверка не подставляется незаметно вместо `set()`, если меняются состояние после отказа, владелец кеша или порядок callbacks. Неуспешная публичная мутация сохраняет прежнюю карту и допустимые identity; успешная сохраняет инвалидацию потомков/отложенных потребителей и освобождение. Используются существующие владельцы без второй authority.
6. **Проверить поведение до timing.** Выполнить матрицу ниже через нужные публичные API; прямые проверки alias использовать там, где нужно отличить построение от разрешения. Проверять ошибки, identity и восстановление без привязки к расположению приватного кеша.
7. **Измерить выбранный вариант.** Ограниченные последовательные парные запуски, точное происхождение source, все samples, неизменные зависимости и явные настройки OPcache/runtime. Отдельно время и память, включая большие отклонённые конфигурации и небольшие обычные. Бюджет определяется потребностью запуска потребителя, не универсальным процентом.
8. **Публиковать только после обоих условий.** Контракт совместимости сохраняется, а целевая прикладная нагрузка улучшается достаточно, чтобы оправдать состояние/сложность. Иначе оставить baseline и записать причину отклонения кандидата.

## 5. Матрица приёмки

| Область | Обязательное доказательство |
|---|---|
| Допустимые графы | Пустая карта, один alias, цепочки в обоих порядках, неглубокие/глубокие ветви, общий terminal, несвязанные компоненты и конечные ID без definitions. |
| ID | Текущие допустимые непрозрачные/числовые строковые формы и все отклоняемые; без случайного приведения array keys или нового предела длины. |
| Порядок отказа | Empty/self-reference, циклы разной длины, несколько независимых циклов, malformed entries до/после циклов; выбранные владелец ошибки и детерминированная цепочка. |
| Разрешение | Одинаковый канонический результат до/после сжатия путей, незатронутые shared identity и pipeline delegators requested-ID. |
| Runtime-мутация | Отклонённый `Container::alias()` сохраняет прежнее поведение; успешная замена инвалидирует затронутых потомков/отложенных потребителей и сохраняет остальные identity. |
| Reentry и lifetime | Существующие проверки вложенных мутаций, приостановленных попыток и retirement сохраняются там, где alias участвует в этих контрактах. Временный обход не удерживает графы сервисов постоянно. |
| Сложность | Инструментированные посещения показывают требуемое масштабирование независимо от шума времени. Длинная цепочка не создаёт неограниченный рекурсивный PHP-стек. |
| Производительность | Конструктор, холодное/прогретое разрешение и полное построение показаны отдельно; небольшие/репрезентативные большие графы и отказы с ограничениями времени/памяти. |

Документ сохраняет предыдущее архитектурное предложение. Он не делает оптимизацию обязательной, не заявляет новый дефект корректности и не обещает ускорить прогретый lookup.
