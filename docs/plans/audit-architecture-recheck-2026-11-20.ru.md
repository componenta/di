## Исправленный выбор mutation workers

Новый тест холодного завершения фабрики обнаруживал удаление завершающего `$container->get(Config::class);` при явном запуске на обеих PHP. Штатный прогон Pest показал, что это ещё не гарантирует выбор теста обычным worker. Completion case исполняет нужный код в отдельном нативном процессе, а соседний empty-factory case останавливается раньше. Для завершающей строки parent coverage содержал 1928 measured test IDs и 256 class selectors, но `ContainerFactoryCompletionContractTest` среди них отсутствовал.

Полный прогон до исправления выбирал только `src/ContainerFactory.php`: **289 мутаций, 271 обнаружена, 18 выжили, таймаутов и uncovered нет**. Удаление завершающего вызова выживало. Его ID в изолированном checkout — `328ca16401db272d`; он соответствует историческому `7069809929e0cf70` по относительному пути, mutator и точному diff. SHA-256 исходника — `d37bad58b22479acf4b94ab3a488f05771c4edf33d65aebac19db86002d925d9`. Mutation ID включает абсолютный путь, поэтому разные ID здесь не означают разные ошибки.

Парный эксперимент использует изолированный исходный набор тестов и шесть новых проверок поведения ядра; после исправления к ним добавлено расширение selector policy. Другие двенадцать проверок поведения из основного checkout в этот эксперимент не входят. Это сопоставимый mutation-прогон одного файла, отдельный от окончательных полных обычных suites ниже.

Исправление добавляет в существующую subprocess policy привязку `ContainerFactory.php` к `ContainerFactoryCompletionContractTest`. Она действует только при регистрации этого test file в suite. Выбор посторонних исходников, записи `[]` и `null`, исходный input и маска измеренного покрытия сохраняются. Исправлена тестовая инфраструктура без вымышленных coverage hits и без изменения runtime. Policy и её границы описаны в [мутационном тестировании](../../tests/mutation-testing.ru.md).

До исправления selector regression падал из-за отсутствующего selector на обеих PHP. После исправления зарегистрированный набор проходит **10 тестов / 26 assertions**, изолированная policy — **2 теста / 10 assertions** на каждом runtime. Независимый review проверил изоляцию исходников, регистрацию, сохранение измеренного покрытия и обе языковые версии документации. Завершённый штатный прогон после исправления дал **289 мутаций, 272 обнаружены, 17 выжили, таймаутов и uncovered нет** (Pest score 94,12%). Удаление завершающего вызова теперь обнаруживается; остальные 288 исходов совпадают. У отчётов одинаковые SHA исходников, версии PHP и инструментов, выбранные mutation IDs и аргументы запуска. Реальные снимки coverage до и после расширения сохраняют одну полную карту классификации строк; для завершающей строки добавлен ровно completion selector.

## Безопасность и производительность

Проверенная граница доверия считает конфигурацию, autoloaders, фабрики, обработчики атрибутов и custom providers прикладным PHP-кодом. Request mapping не должен превращать входные значения в эту конфигурацию или позволять подменять внутреннее происхождение данных. Проверены фильтрация внутреннего контекста, конфликты источников, выбор request sources, видимость callbacks, снимки аргументов и поздняя замена providers. Поиск опасных операций в production-дереве не нашёл `eval`, unserialization, запуска shell/process или чтения/записи содержимого файлов в `src`; этот поиск дополняет анализ потока исполнения и не доказывает универсальную безопасность.

Доступность callable следует lexical context целевого вызова; есть отрицательные контроли для недоступных child/private и внутренних DI-методов. Снимки маршрутизации отделяют ссылки вызывающей стороны и сохраняют ожидаемое живое состояние бизнес-объектов. Собственные исключения сохраняют identity, внешние ошибки на границах — исходную причину. Отделённые диагностические payload не удерживают runtime reflectors и request objects; аргументы нативного Throwable trace и редактирование логов приложения — отдельные вопросы. Новая удалённо эксплуатируемая уязвимость этим проходом не подтверждена.

Кеши проверены на revision, принадлежность контейнеру, запрет поздней записи старого результата, слабое владение и инвалидацию после runtime-изменений. Shared `get()` сохраняет отдельный быстрый путь. Свежий availability smoke воспроизвёл **24** вызова loader неизвестного имени на затронутое создание при одном отслеживаемом недоступном атрибуте и **192** при восьми; shared hits в этом примере таких вызовов не делают. Прежнее парное сравнение задержек и замеры холодных aliases сохраняют указанное в отчётах историческое происхождение. Тайминги параллельного smoke не превращены в заявление об оптимизации.

## Оставшиеся решения

Наиболее значимый проект исправления корректности — [очистка и публикация bootstrap](bootstrap-finalization-boundaries.ru.md): воспроизведение возвращает кешированный объект с устаревшим состоянием, зависящим от metadata. [Владение внешнего provider](external-provider-ownership.ru.md) требует явной стабильности или протокола изменений до расширения инвалидации. Оба отчёта описывают отказ, identity, повторный вход, момент деструкторов, цену совместимости и критерии приёмки.

[Стоимость доступности атрибутов](attribute-availability-performance.ru.md) и [большие alias-графы](large-alias-graphs.ru.md) остаются предложениями, зависящими от нагрузки. Постоянный отрицательный кеш metadata или дополнительный слепой опрос не становятся допустимыми ради синтетического выигрыша. Для [relative callable](relative-callable-context.ru.md), [политики standalone API](standalone-api-surface.ru.md), [атомарности нормализации](configuration-normalization-contract.ru.md) и [публикации lazy между Fibers](native-lazy-fiber.ru.md) сначала нужны гарантии потребителя, перечисленные в соответствующих планах. Аудит не превращает ни один из этих вопросов в неявное несовместимое изменение.
