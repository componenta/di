## 1. Наблюдение и границы доказательств

Его исходная версия — `af9eac7f7619a717e1b914bae4ef259ade03ea36`; сводный аудит подготовлен для `22ea0c4f4e8bb1763f77b4448673aed5383bb653`. Review фиксирует одинаковое наблюдение на PHP 8.4.28 и 8.5.13:

| Один объект, пока его initializer приостановлен | Прямой нативный PHP | Путь DI | После успешного продолжения исходного initializer |
|---|---|---|---|
| Ghost | Другой контекст исполнения читает промежуточное значение свойства. | То же. | Свойство содержит завершённое значение. |
| Virtual proxy | Другой контекст исполнения получает нативный `Error` неинициализированного свойства. | То же. | Свойство содержит завершённое значение. |

Исторический fixture меняет `value` с `default` на `starting`, приостанавливается внутри конструктора, затем записывает `ready`. Fiber начинает инициализацию чтением `value`; основной контекст читает тот же уже выданный объект во время приостановки и затем возобновляет Fiber. Это одно конкретное чередование кооперативного исполнения, а не утверждение обо всех свойствах, initializers, patch-версиях runtime или политиках планировщика.

### Переносимое воспроизведение четырёх маршрутов

Сохраните полный блок ниже как `native-lazy-fiber-reproducer.php` вне checkout с установленными development-зависимостями. Выполните его в **новом процессе PHP 8.4+**, передав путь репозитория:

```sh
php native-lazy-fiber-reproducer.php /absolute/path/to/di
```

[`tests/bootstrap.php`](../../tests/bootstrap.php) и [`ContainerBuilder`](../../tests/Support/ContainerBuilder.php) создают обычный контейнер через публичный путь. Нативные маршруты выделяют `Product`; пути DI — его подклассы `Ghost` и `Virtual` с атрибутами. Во всех четырёх используются одинаковые реализация конструктора, backed property и последовательность suspend/read/resume; подклассы DI наследуют конструктор. В fixture нет setup hooks или дополнительных handlers; наблюдаемый паритет относится к этой последовательности, а не ко всем возможным эффектам lifecycle DI.

```php
<?php
declare(strict_types=1);

use Componenta\DI\Attribute\Lazy;
use Componenta\DI\Attribute\Proxy;
use Componenta\DI\Tests\Support\ContainerBuilder;

$repository = realpath($argv[1] ?? getcwd());
if ($repository === false) {
    throw new LogicException('Pass the checked-out DI repository as the first argument.');
}
require $repository . '/tests/bootstrap.php';

class Product
{
    public string $value = 'default';

    public function __construct()
    {
        $this->value = 'starting';
        Fiber::suspend('constructing');
        $this->value = 'ready';
    }
}

#[Lazy]
class Ghost extends Product {}

#[Proxy]
class Virtual extends Product {}

$rows = [];
foreach (['native-ghost', 'native-proxy', 'di-ghost', 'di-proxy'] as $mode) {
    $reflection = new ReflectionClass(Product::class);
    $container = null;
    $entry = match ($mode) {
        'native-ghost' => $reflection->newLazyGhost(static fn($object) => $object->__construct()),
        'native-proxy' => $reflection->newLazyProxy(static fn() => new Product()),
        default => ($container = (new ContainerBuilder())->build())->get(
            $mode === 'di-ghost' ? Ghost::class : Virtual::class,
        ),
    };
    $fiber = new Fiber(static fn() => $entry->value);
    $first = $fiber->start();
    try {
        $during = $entry->value;
    } catch (Throwable $error) {
        $during = $error::class . ': ' . $error->getMessage();
    }
    $fiber->resume();
    $rows[$mode] = [
        'first' => $first,
        'during' => $during,
        'after' => $entry->value,
        'fiberResult' => $fiber->getReturn(),
    ];
}
echo json_encode($rows, JSON_PRETTY_PRINT | JSON_UNESCAPED_SLASHES), "\n";
```

Это **статическая адаптация исторического исходника, а не новая выполненная проверка**. Старый абсолютный bootstrap-путь заменён аргументом checkout, форматирование развёрнуто; четыре маршрута и порядок наблюдений сохранены. Исходник задаёт ожидаемое успешное расписание: `first = constructing`, `after = ready` и `fiberResult = ready`; это ожидания, выведенные из кода, а не отдельно сохранённые исходные результаты. Исторический review описывает промежуточное значение ghost и нативный `Error` неинициализированного свойства proxy во время приостановки. Точный текст ошибки зависит от runtime. При будущей квалификации нужно сохранить фактический вывод, точную PHP и выбранный коммит исходников, а не выдавать адаптацию за текущий успешно выполненный тест.

## 2. Почему изоляция создания не сериализует последующий доступ

Состояние отдельной попытки DI, владение Fiber и проверки ревизий кеша защищают разрешение и публикацию через контейнер. Успешно возвращённый нативный lazy-объект затем может храниться и использоваться напрямую кодом приложения. Такое чтение свойства входит в нативный механизм PHP без нового вызова `Container::get()` или resolver параметров.

Поэтому защита фабрики или проверка кеша контейнера не перехватывает каждое обращение к уже выданному объекту. Блокировка внутри initializer также сама по себе не доказывает ожидание при втором прямом чтении свойства: это обращение должно действительно попасть в управляемую границу ожидания. Прямой нативный контроль существенен именно потому, что то же поведение существует без кешей и планов DI.

Разным попыткам lazy-инициализации по-прежнему нужно изолированное состояние lifecycle. Эта изоляция не добавляет синхронизации всех потребителей одного общего нативного экземпляра. Исправление D1/A касается другого сбоя: для неподдерживаемого класса нативное выделение молча пропускало initializer. Отказ до выделения реализован и остаётся действующим; сериализация Fiber для поддерживаемых классов им не обещается.

## 3. Необходимость, выигрыш и варианты

Приложению может требоваться, чтобы ни один потребитель не видел сервис до завершения конструктора и setup. Приостанавливающийся initializer и ранняя публикация одного экземпляра способны нарушить это прикладное требование. Исторический probe устанавливает границу, но не доказывает наличие конкретного потребителя новой возможности DI или достижимость внешним атакующим.

| Вариант | Выигрыш | Цена и условия | Статус |
|---|---|---|---|
| Сохранить и описать нативное поведение | Явная существующая гарантия конкуренции без нового владельца runtime-состояния и скрытой политики приостановки. | При возможной приостановке initializer приложение управляет совместным использованием. | Рекомендуемый исходный вариант. |
| Завершать инициализацию до прикладной публикации | Потребитель получает завершённый экземпляр по правилу публикации приложения. | Инициализация происходит раньше относительно sharing; ошибки и планирование принадлежат приложению. Все пути доступа должны соблюдать эту границу. | Существующий прикладной подход, выбираемый конкретным потребителем. |
| Прикладной accessor или асинхронный facade | Можно явно задать ожидание, ошибку, отмену и retry вокруг управляемой операции. | Меняет получение/использование сервиса и зависит от scheduler приложения. Произвольные прямые чтения свойства прозрачно не меняются. | Условный проект потребителя. |
| Добровольно выбранный альтернативный lazy adapter с протоколом синхронизации | Может предоставить повторно используемую более сильную гарантию нужной интеграции. | Требуется доказать перехват доступа, совместимость типа/identity, интеграцию scheduler, reentry, исключения, lifetime и поведение custom adapters. | Реализация не выбрана. |
| Автоматически добавить глобальный lock или scheduler контейнера | Для прямых обращений к уже выданному нативному объекту выигрыш не установлен. | Новая глобальная семантика, риск deadlock/cancellation, задержка и недоказанная граница перехвата. | Из этих доказательств не рекомендован. |

Удаление соответствующего lazy/proxy-маркера выбирает обычное reflection-создание; замена `get()` на `make()` сама по себе маркер не отключает. Явная фабрика и `ClassDefinition` сохраняют собственные контракты lifecycle. Выбирающее их приложение явно организует необходимый setup там, где выбранный жизненный цикл этого требует.

Измеренное ускорение или сокращение памяти не заявляется. Возможный выигрыш более сильного решения — определённое завершение до использования для конкретного контракта потребителя. Ради него может намеренно измениться отложенность работы и конкуренция.

## 4. Условный порядок проектирования

1. **Описать реальную публикацию.** Назвать общий сервис, точку возможной приостановки initializer, всех прямых потребителей свойств/методов и владельца scheduler. Разделить один общий объект, независимые результаты `make()` и ещё не завершившийся lookup.
2. **Выбрать публичное поведение.** Решить, ожидает ли конкурентный потребитель, немедленно получает определённую ошибку либо такой доступ запрещён прикладным контрактом. Определить reentry владельца, рекурсивную инициализацию, передачу ошибок, отмену, retry и сохранение identity у вызывающей стороны.
3. **Доказать управляемость границы до проектирования lock.** Воспроизвести native/DI ghost/proxy на точных поддерживаемых runtime. Показать, что каждая операция обещанного контракта проходит через accessor/adapter. Если прямое нативное чтение свойства не перехватывается, сузить гарантию либо использовать явный прикладной API.
4. **Локализовать владение синхронизацией.** Предпочесть прикладную публикацию/доступ или явно выбранный adapter. Описать lifetime owner token, ожидающего Fiber и сохранённого исключения/результата; request values и runtime receivers не должны попадать в общие metadata-планы. Обычное попадание в кеш контейнера не должно получать глобальную зависимость от scheduler.
5. **Реализовать только выбранный контракт.** Сохранить обещанное время lazy-вызова для допустимых классов, ошибки callback, делегирование custom adapters и отсутствие replay завершённых конструктора/setup. Описать намеренные миграции eager-времени, типа или identity. Откат произвольных эффектов callbacks не подразумевается.
6. **Проверить корректность и стоимость.** До широкой интеграции выполнить матрицу ниже. Отдельно измерить неинициализированный доступ, инициализированный доступ, создание без конкуренции и определённую конкурентную нагрузку. Зафиксировать удерживаемое состояние ожидания и cleanup; исторический probe не задаёт целевой throughput.

## 5. Приёмка и условие остановки

| Область | Обязательное доказательство для будущего усиленного контракта |
|---|---|
| Runtime baseline | Прямые и DI ghost/proxy, точная PHP, происхождение исходников и сохранённый вывод; промежуточные и итоговые результаты отдельно. |
| Один общий объект | Исходное расписание с приостановленным initializer соблюдает выбранное wait/fail/publication правило. Проверить охваченные им свойства и методы. |
| Независимые попытки | Разные объекты и Fibers не разделяют данные вызовов, owner tokens или доказательство завершения неудачной попытки. |
| Эффекты и identity | Счётчики конструктора/setup/factory исключают непредусмотренный replay; identity wrapper/backing и вызывающей стороны соответствуют контракту. |
| Ошибка и retry | Ошибка исходного initializer, отказ ожидающего потребителя, отмена и последующая попытка имеют явных проверенных владельцев и время. |
| Reentry | Рекурсия владельца и циклы зависимостей между Fibers получают определённый исход; зависший тест не считается успехом. |
| Lifetime | После завершения, ошибки и отмены освобождаются ожидающие Fibers, захваты callback и графы сервисов при отсутствии прикладных/нативных владельцев. Trace исключения отделяется от утечки metadata. |
| Существующие контракты | Отказ propertyless-классу, приоритет нативных ошибок, обычные eager-пути и custom adapter delegation сохраняются, если явная миграция не меняет их. |
| Стоимость | Ограниченные последовательные замеры незатронутых путей и выбранной интеграции; сохраняются все samples, стоимость синхронизации отделяется от работы приложения. |

Без конкретного требования усиленной синхронизации публикация этого отчёта закрывает задачу архитектурного документирования границы. Она не открывает обязательный проект scheduler, не блокирует принятый объём DI 6 и не переименовывает нативное поведение в локальный дефект для автоматической правки.
