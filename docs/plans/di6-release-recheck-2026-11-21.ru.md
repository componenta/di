# Повторная проверка готовности DI 6

## Состояние перед исправлениями

Стабильный релиз был отложен. Штатные сценарии прошли локальную матрицу, но bootstrap допускал публикацию общего сервиса с устаревшим выбором источника параметра. При отображении HTTP‑данных последняя проверка происхождения аргументов конструктора проходила раньше последней применимой проверки композиции.

Проверено рабочее дерево `refactor/di6-definitions-callbacks` поверх `9fb0750` после [исправлений предыдущего аудита](di6-audit-2026-11-21.ru.md#исправления-архитектурных-дефектов). Снимок зафиксирован до написания отчёта. Сверены хеши 171 файла `src`, повторно проверены 18 файлов, изменённых или добавленных со времени построчного прохода, и сквозные пути регистрации, поиска, владения кешем, разрешения параметров и передачи HTTP‑данных.

## Выявленные дефекты

### Высокая серьёзность — bootstrap теряет результат классификации резолвера

Bootstrap сохраняет список зарегистрированных резолверов до победителя. Этот список включает резолверы, которые вернули `false` из `supports()`. Финальная проверка пропускает всех участников списка. Поздняя доступность объявленного атрибута может изменить ответ уже зарегистрированного резолвера. Отдельная проверка после освобождения временных ссылок различает только атрибуты с `AttributeDefinition`, хотя пользовательский `supports()` вправе читать нативные атрибуты через `ParameterTarget`. [Запись выбора](../../src/Resolver/Parameter/ParametersResolver.php#L403-L440) · [Финальная проверка](../../src/Internal/BootstrapResolutionGuard.php#L107-L183) · [Контракт расширений](../../README.ru.md#точки-расширения)

На PHP 8.4.28 и 8.5.13 в обеих сборках контейнера `create()` возвращал успех, `get()` сохранял значение по умолчанию, а `make()` использовал пользовательский резолвер. Это происходило при объявлении метаданных в очередной фабрике расширения и при освобождении временных ссылок bootstrap. Контроль с несвязанным атрибутом дал одинаковый результат.

**Решение.** Сохранять исход классификации до победителя и проверять его по итоговым метаданным. Для именованных целей проверять выбор после освобождения ссылок с помощью заново полученного рефлектора. Для целей замыканий нужна отдельная внутренняя модель наблюдений, учитывающая срок жизни захватов и публичный доступ к рефлектору. Покрыть позднюю загрузку атрибута для уже зарегистрированного резолвера, завершение разрешения в Fiber и освобождение захватов. По‑прежнему принимать несвязанные декларации и выполнять только проверки метаданных, без повторного создания зависимостей.

### Средняя серьёзность — последний этап создания DTO теряет проверку источника

Документация требует завершить DTO ошибкой при несовместимом позднем изменении источника. Перед конструктором сверяются и происхождение HTTP‑значений, и план DI‑атрибутов. После конструктора и финальной настройки сверяется только план. Анализ кода показывает, что объявленный приложением атрибут с `ParameterSourceAttributeInterface`, ставший доступным на этом этапе без регистрации `AttributeDefinition`, может остаться вне итоговой проверки. Условие зависит от поздней загрузки прикладного атрибута. [Контракт](../../README.ru.md#L290-L298) · [Вызов конструктора](../../src/Resolver/Entry/InstanceCreator.php#L92-L105) · [Возврат и lazy‑инициализация](../../src/Object/ObjectPipeline.php#L270-L365)

**Решение.** Удерживать приватное происхождение уже потреблённых аргументов до успешного возврата объекта или окончания lazy/proxy‑инициализации. Повторять проверку загруженных деклараций на границе публикации. Покрыть конструктор, итоговый callback и контроль с несвязанной декларацией. Сохранять момент получения отложенных параметров и однократное выполнение прикладного кода.

### Средняя серьёзность — мутационный порог может зачесть отказ запуска worker

При рассогласованных временных файлах Pest workers завершались до выполнения тестов из‑за отсутствия файла подстановки. Инструмент сообщил 120 из 120 обнаруженных мутаций. После восстановления чистого кеша тесты обнаружили 102 из 120, ещё 4 завершились по тайм‑ауту и 14 выжили. Текущая проверка обычного worker проходит без файла подстановки и пропускает эту ошибку. [Проверка worker](../../tests/Support/MutationFallback.php#L27-L43) · [Отчёт](../../tests/Support/MutationReport.php)

**Решение.** Проверять доступность файлов подстановки перед запуском workers, пересоздавать повреждённый кеш и отражать сбои запуска отдельно от падений тестов. Добавить контрольный прогон по тому же пути с неизменённым исходником как подстановкой.

### Средняя серьёзность — публикация может опередить проверку нативного минимума

Прежний релизный workflow ждал обычные тесты, установку для потребителя и coverage с мутационным порогом. Нативная проверка trait‑callables на закреплённом PHP 8.5.13 запускалась в отдельном workflow. Обычный suite уже проходил на затронутом PHP 8.5.12, где нативная проверка проходила только 2 из 10 сценариев. [Проверка E1](../../.github/workflows/ci.yml#L115-L125) · [Публикация](../../.github/workflows/release.yml#L150-L159) · [Контроль PHP 8.5.12](php85-callbacks.ru.md#8-версия-php-и-совместимость-релиза)

**Решение.** Сделать закреплённую проверку общим заданием и включить её в зависимости публикации того же SHA.

## Проверки кандидата

- PHP 8.4.28 — `composer check`, 2 633 теста, 21 пропуск, 40 385 утверждений. Покрытие строк PCOV — 95,5%. PHPStan на максимальном уровне и проверка стиля прошли.
- PHP 8.5.13 — 2 652 теста, 2 пропуска, 40 514 утверждений. Нативная проверка E1 прошла 10 из 10. Все 171 файла `src` прошли проверку синтаксиса на обеих версиях.
- Собранный архив установлен без dev‑зависимостей в отдельных проектах с минимальным и актуальным наборами пакетов. Потребительский smoke‑тест прошёл на обеих версиях PHP. Composer Audit не сообщил advisories для обоих наборов или для проверенного dev‑lock. Проверка безопасности кода проведена вручную по границам доверия, поскольку средство Deep Security Scan недоступно.
- Выборочный mutation‑прогон охватил `BootstrapResolutionGuard`, `AliasGraphBuilder` и `CallableDependencyLookup`. Чистый результат Pest — 88,33% с включёнными в счёт четырьмя тайм‑аутами. Удаление выхода после проверки завершившегося Fiber пережило тесты, поэтому стоит добавить проверку освобождения его временных ссылок через `WeakReference`.
- Прежний [прогон GitHub CI](https://github.com/componenta/di/actions/runs/44802942305) относится к `9fb0750`. Полный mutation‑каталог, Windows и проверка потребителя на PHP 8.6 для текущих исходников остаются релизными проверками.

## Производительность

Сравнение со снимком DI 6 перед предыдущими архитектурными исправлениями. Отдельные процессы на одном ядре с чередованием порядка запуска, четыре пары для `RuntimeBench`, две для остальных сценариев. Относительные значения — медианы парных изменений времени операции.

| Сценарий | PHP 8.4.28 | PHP 8.5.13 |
|---|---:|---:|
| `get()`, прогретый сервис | +0,7% | −1,3% |
| `make()`, автовнедрение | +0,9% | +3,1% |
| `call()`, переиспользуемое замыкание | +1,8% | +5,1% |
| DTO с callback отображения | +4,5% | +3,6% |

| Адресное обнаружение при восьми недоступных декларациях на других целях | 112 → 15,6 мкс | 130 → 16,3 мкс |

У `get()` и `make()` знак менялся между парами. Замедление `call()` и DTO повторилось во всех четырёх парах на обеих версиях. Адресный режим сократил число вызовов автозагрузчика на операцию со 192 до нуля в этом сценарии. Обычный режим сохранил 192 вызова. Граф алиасов дополнительно совпал с простым эталоном на 128 000 добавлений и 384 000 проверок маршрута на каждой версии PHP. [RuntimeBench](../../benchmarks/RuntimeBench.php) · [AliasGraphBench](../../benchmarks/AliasGraphBench.php) · [AttributeAvailabilityBench](../../benchmarks/AttributeAvailabilityBench.php)

В отдельной копии упростил построение плана для целей без деклараций. Оно пропускает вызов обхода пустого списка, сохраняя порядок опроса реестра и освобождения рефлекторов. `call()` с переиспользуемым замыканием стал быстрее во всех четырёх парах. Медианное ускорение относительно кандидата составило 4,0% и 4,6%. Обе полные серии тестов и PHPStan прошли на прототипе. Для DTO устойчивого выигрыша на обеих версиях не получено. ## Исправления

- Bootstrap сохраняет исход `supports()` для резолверов перед выбранным. При появлении декларации перепроверяет классификацию именованного параметра или живого замыкания. Слабая ссылка на исходное замыкание учитывает нативный рефлектор, созданный из метода. Для освобождённых рефлекторов проверка семантических DI-атрибутов использует сохранённые имена деклараций. [Bootstrap](../../src/Internal/BootstrapResolutionGuard.php) · [Тесты](../../tests/Contract/BootstrapProofRetirementContractTest.php)
- Проверка provenance использует приватный снимок уже потреблённых аргументов при возврате eager-объекта или завершении lazy/proxy-инициализации. Повторная проверка использует уже загруженные объявления. [Пайплайн объектов](../../src/Object/ObjectPipeline.php) · [Тесты](../../tests/Contract/CompletedConstructorArgumentsContractTest.php)
- Мутационный кеш восстанавливает подстановки по исходнику. Порог принимает результаты workers, которые подтвердили установку подстановки. Контроль запускается по тому же пути с исходным файлом. [Кеш подстановок](../../tests/Support/MutationArtifactCache.php) · [Проверка worker](../../tests/Support/MutationWorkerCheck.php) · [Тесты](../../tests/Contract/MutationWorkerIntegrityContractTest.php)
- CI и Release запускают общий скрипт с закреплённой версией и контрольной суммой PHP 8.5.13. Публикация зависит от этой проверки. [Скрипт](../../.github/scripts/check-native-trait-callables.sh) · [Release](../../.github/workflows/release.yml)
- Обход пустого списка атрибутов пропускается на пути `AttributePlanBuilder::build()`. [Построение плана](../../src/Attribute/Composition/AttributePlanBuilder.php)

## Перепроверка оптимизаций и кеша параметров

### Исправлено — поздний алиас атрибута оставлял устаревшую классификацию

`ParameterTarget::hasAttribute()` и `firstAttribute()` могут найти уже объявленный атрибут по имени, которое позднее становится его PHP-алиасом. До исправления прогретые `make()` и `call()` именованной функции продолжали подставлять значение по умолчанию, тогда как свежий контейнер и вызов замыкания выбирали пользовательский резолвер. Дефект воспроизводится на снимке до оптимизаций и в обеих сборках контейнера. В bootstrap тот же пробел мог сохранить неверный источник у общего сервиса. [Резолвер параметров](../../src/Resolver/Parameter/ParametersResolver.php) · [Контрактные тесты](../../tests/Contract/ParameterResolverAliasedAttributeContractTest.php)

Классификация запоминает отсутствующие имена, запрошенные через `ParameterTarget`. Появление такого имени запускает повторный выбор резолверов для затронутой цели. Проверка доступности использует только уже загруженные символы. Bootstrap учитывает имена, замеченные при первоначальном разрешении, при итоговой проверке и при освобождении записей с доступным рефлектором. Тесты охватывают совпадающий и несвязанный алиас, порядок поздней загрузки, замыкания и прерванные Fiber. [Наблюдение имён](../../src/Resolver/Target/ParameterTarget.php) · [Bootstrap](../../src/Internal/BootstrapResolutionGuard.php) · [Проверка освобождения](../../tests/Contract/BootstrapProofRetirementContractTest.php)

### Средняя серьёзность — проверка теряет классификацию уничтоженного замыкания

Фабрика расширения получает общий сервис, созданный вызовом временного замыкания с аннотированным параметром. Во время освобождения записей bootstrap деструктор захвата объявляет алиас, который меняет выбор пользовательского резолвера для этого параметра. Исходное замыкание к моменту проверки уже уничтожено. В обеих сборках `create()` завершился успешно, `get()` сохранил значение по умолчанию, а новый `make()` получил значение резолвера. При алиасе постороннего атрибута и при резолвере, который игнорирует результат поиска, `get()` и `make()` совпали. Результаты воспроизведены на PHP 8.4.28, 8.5.13 и 8.6.0. Поведение совпало с предшествующим снимком. [Проверка после освобождения](../../src/Internal/BootstrapResolutionGuard.php) · [Срок жизни рефлекторов](bootstrap-finalization-boundaries.ru.md#почему-требуется-решение-по-жизненному-циклу)

**Решение для DI 6.** Зафиксировать порядок объявления метаданных перед первым зависимым разрешением и уточнить границу итоговой проверки. Для интеграции, которой нужны поздние объявления, спроектирован отдельный `AttributeMatchingParameterResolver` с полностью декларативной применимостью. Критерии включают идентичность сервиса, однократное выполнение фабрики, освобождение захвата до публикации и успешную сборку при несвязанных изменениях. [Решение и результаты прототипа](bootstrap-finalization-boundaries.ru.md#5-решение-для-di-6)

### Средняя серьёзность — кеш пропускает зависимость, прочитанную через Reflection

Пользовательский `supports()` может проверить наличие загруженного имени через `class_exists($alias, false)` и прочитать атрибут через `ReflectionParameter::getAttributes()` с `IS_INSTANCEOF`. На PHP 8.4.28, 8.5.13 и 8.6.0 после объявления совпадающего алиаса прогретые `make()` и вызов именованной функции возвращали значение по умолчанию. Свежий контейнер и вызов замыкания выбирали резолвер. Оба режима обнаружения атрибутов дали один результат. Имя, использованное в запросе к нативному рефлектору, известно самому резолверу. [Публичный рефлектор](../../src/Resolver/Target/ParameterTarget.php) · [Кеш классификации](../../src/Resolver/Parameter/ParametersResolver.php)

**Рекомендуемое решение.** Позволить расширению явно передать имена, от доступности которых зависит классификация, или выбрать пересчёт для целей с динамическими метаданными. Обе возможности должны быть опциональными. Приёмка требует совпадения свежего и прогретого результата после объявлений, сохранения вызовов автозагрузчиков для обычного режима и замера путей с расширениями. [Контракт классификации](../../src/Resolver/Parameter/ParameterResolverInterface.php)

### Подтверждённые проблемы

- **Средняя серьёзность — ранняя запись при вложенной обработке свойства.** `ObjectCreationContext::resolveProperty()` хранит промежуточное значение по ключу свойства. Повторный вход для того же свойства заменяет запись внешнего вызова и публикует внутреннее значение. На трёх версиях PHP значение оставалось в объекте после ошибки внешнего обработчика. Первым шагом стоит отклонять повторный вход для того же свойства до изменения состояния. В прототипе исходное значение сохранялось. [Контекст создания объекта](../../src/Resolver/Entry/ObjectCreationContext.php#L170-L189)
- **Низкая серьёзность — управление наблюдением параметра открыто расширению.** `beginAttributeQueries()` и `endAttributeQueries()` используют идентификатор выполнения, общий для вложенных наблюдений. Вызов завершения с идентификатором внешнего наблюдения снимал внутреннее. Стоит заменить пару одной операцией, которая сама закрывает свой scope в `finally`. Прототип сохраняет результаты вложенной классификации и исходные исключения. [Стек наблюдений](../../src/Resolver/Target/ParameterTarget.php#L163-L195)
- **Низкая серьёзность — подготовленный план публикует идентификатор владельца.** Обычный план другого резолвера отклоняется. План, собранный вручную с владельцем и ревизией из штатного плана, принимается как текущий. Стоит закрыть поле владельца и проверять его в начале разрешения. Обновлённые планы создаёт тот же резолвер. Прототип подтвердил отказ для вручную созданного плана и выполнение штатного. [Структура плана](../../src/Internal/Resolver/Parameter/PreparedParameterPlan.php#L9-L23) · [Проверка владельца](../../src/Resolver/Parameter/ParametersResolver.php#L476-L490)
- **Средняя серьёзность — разделяемое состояние при прямой сборке.** При передаче одного `EntryCache` в два контейнера второй вернул значение, записанное первым. Прямое изменение переданного `AliasResolver` оставило прогретый `get()` на прежней цели. Оба сценария выходят за документированный режим использования. Предмет отдельного решения — проверка владельца при сборке и доступ к мутациям, с сохранением публикации начальных значений в переданный кеш. Проверку владельца можно расположить на границе присоединения, сохранив текущий путь прогретого `get()`. [Прямое создание контейнера](../../docs/migrations/di6-definitions.ru.md#прямое-создание-контейнера) · [Владение компонентами](../../src/Container.php#L92-L114)

У `CompositeResolver` уже есть проверка владельца привязки и полномочий контейнера для публикации и удаления. Автономный `setDefinition()` и выбор fallback относятся к его публичной роли. Разделение имеет смысл при появлении отдельного объекта записи, доступного только владельцу контейнера. Порядок подготовки, публикации, инвалидации и освобождения старых ссылок должен сохраниться. [Резолвер](../../src/Resolver/Entry/CompositeResolver.php#L118-L191) · [Публикация контейнера](../../src/Container.php#L254-L291)

### Подтверждённые дефекты и исправления

- **Средняя серьёзность — подмена атрибута при обновлении плана.** Подкласс рефлектора может вернуть другой конкретный атрибут в той же позиции с той же семантической регистрацией. Пайплайн принимал устаревший выполненный префикс или передавал обработчику экземпляр, созданный по прежней декларации. Проверка сравнивает имя конкретного атрибута и при обновлении сверяет также сохранённый экземпляр. Оба сценария отклоняются до продолжения создания, а новая попытка с актуальной декларацией проходит. [Проверка порядка](../../src/Internal/AttributeExecutionOrder.php) · [Регрессия](../../tests/Contract/ObjectCrossTargetPrefixContractTest.php)
- **Средняя серьёзность — позднее обнаружение источника параметра `SetUp`.** DTO мог вернуться успешно, если уже начавшийся `SetUp` или следующий шаг объявлял источник параметра, которому были переданы HTTP-данные. Для выполненных методов и замыканий `SetUp` сохраняются имена недоступных деклараций, относящихся к переданным ключам. Проверка выполняется после вызовов `SetUp` и перед завершением текущей попытки создания или инициализации. Она использует загруженные символы и удерживает только строки. Обработчики вызываются однократно. ### Архитектурные вопросы

- **Средняя серьёзность — классификация уничтоженного замыкания.** На трёх версиях PHP заново воспроизведено расхождение `get()` и `make()`, когда деструктор захвата загружает совпадающий алиас на финальной границе bootstrap. Контроли с посторонним алиасом и с резолвером, игнорирующим совпадение, согласованы. Для DI 6 уточнена граница проверки. Для поздних деклараций подготовлен опциональный класс с текущим интерфейсом. [Решение для DI 6](bootstrap-finalization-boundaries.ru.md#5-решение-для-di-6)
- **Средняя серьёзность — прямое чтение метаданных в `supports()`.** В обоих режимах обнаружения подтверждено расхождение прогретых и свежих планов после объявления алиаса, прочитанного через `ReflectionParameter`. Рекомендуемый путь — зарегистрировать в расширении имена зависимых деклараций или явно отключать кеширование для такой классификации. [Контракт резолвера](../../src/Resolver/Parameter/ParameterResolverInterface.php) · [Предыдущий разбор](#средняя-серьёзность--кеш-пропускает-зависимость-прочитанную-через-reflection)
- **Средняя серьёзность при ошибочной ручной сборке — разделяемые `EntryCache` и `AliasResolver`.** Два контейнера с одним кешем видят общие записи, прямое изменение переданного резолвера алиасов оставляет прогретый маршрут. Документированный контракт требует независимые runtime-компоненты и мутации через `Container`. Рекомендуемый путь — добавить контроль владения при присоединении, сохранив текущий порядок публикации и освобождения начальных значений. - На PHP 8.4.28 прошло 2 700 тестов и 40 680 утверждений при 20 ожидаемых пропусках. Покрытие строк PCOV — 95,8%. На PHP 8.5.13 и 8.6.0 прошло по 2 719 тестов и 40 809 утверждений. На 8.5 один пропуск, на 8.6 прежнее предупреждение Pest при пропуске. PHPStan, проверка стиля 525 файлов, `actionlint`, `composer validate --strict` и синтаксис всех 172 исходных файлов прошли.
- Совпали публичные сигнатуры 139 типов и результаты 5 224 сценариев алиасов, реестра, планов и маршрутизации на каждой версии PHP. В двух режимах обнаружения совпали результаты для позднего алиаса, запрошенного через `ParameterTarget`. Четыре контрольные подстановки вызвали падения новых регрессионных сценариев.
- Кандидат установлен отдельно с минимальным и актуальным графом production-зависимостей на каждой из трёх версий PHP. Прошли consumer smoke и проверка требований платформы. Composer Audit не сообщил advisories или abandoned-пакетов для этих графов и dev-lock. Нативный тест дал 10 из 10 на PHP 8.5.13 и 8.6.0, на 8.6 оценивалась семантика.
- Выборочный Pest-прогон применил три вида мутаций к восьми изменённым файлам. Из 150 мутаций тесты обнаружили 143, две выжили в прежней логике второго прохода проверки источников, пять завершились по тайм-ауту. Контроль запуска workers прошёл. Релизные проверки Windows и полного mutation-каталога требуют итогового SHA. [Релизный workflow](../../.github/workflows/release.yml)

### Производительность итогового снимка

Задержка сравнивалась со снимком до текущего прохода. Значения для штатных путей — медианы четырёх парных запусков в отдельных CLI-процессах на одном ядре. Для `SetUp` приведена повторная серия из шести пар. [RuntimeBench](../../benchmarks/RuntimeBench.php)

| Сценарий | PHP 8.4.28 | PHP 8.5.13 |
|---|---:|---:|
| `get()`, прогретый сервис | −7,15% | −0,15% |
| `make()`, автовнедрение | −0,09% | +0,74% |
| `call()`, переиспользуемое замыкание | +0,43% | +0,27% |
| DTO без `SetUp` | −1,28% | −0,49% |
| DTO с `afterMap` | −0,81% | +0,27% |
| DTO с `SetUp` | +2,82% | +1,36% |

В первой серии прогретый `get()` показал +4,13% и +0,95%, поэтому знак изменения на этом пути зависит от серии. Для DTO с `SetUp` на PHP 8.4 первая и повторная серии дали +3,19% и +2,82%. Медианы процессов во второй серии были 59,28 и 60,11 мкс. На PHP 8.5 знак менялся между сериями. Прототип переиспользования рефлектора метода дал +0,97% и +3,59% для DTO с `SetUp` относительно исправления. В проходе по параметрам убрана повторная проверка уже определённого приоритета источника.

## Проверка после внедрения резолвера

### Исправления

- **Средняя серьёзность — позднее совпадение после освобождения замыкания.** Добавлен опциональный `AttributeMatchingParameterResolver` на текущем интерфейсе. Сборка отклоняется, когда сохранённые декларации совпали с условием резолвера, стоящего перед уже выбранным. Проверка использует загруженные символы. В обоих режимах подтверждены поздний алиас, позднее объявление самого атрибута, обнаружение на втором проходе, освобождение захвата, однократное создание сервиса, посторонние объявления и приоритет явного аргумента. [Резолвер](../../src/Resolver/Parameter/AttributeMatchingParameterResolver.php) · [Контрактные тесты](../../tests/Contract/BootstrapProofRetirementContractTest.php)
- **Средняя серьёзность — повторно используемая цель с производным рефлектором сохраняла устаревший список резолверов.** После изменения `getAttributes()` разрешение той же цели возвращало прежний fallback для функции и метода. Кеш классификации применяется к стабильным нативным декларациям. Пригодность вычисляется при создании `ParameterTarget` с уже полученным рефлектором, поэтому прогретый путь читает готовый флаг. [Цель параметра](../../src/Resolver/Target/ParameterTarget.php) · [Регрессия](../../tests/Contract/DerivedParameterReflectionContractTest.php)

### Архитектурные решения

- **Средняя серьёзность — прямой запрос к Reflection.** Предложен опциональный `ParameterTarget::watchAttributeAvailability()`, который объявляет имя без автозагрузки и использует текущую адресную инвалидацию. Прототип восстановил совпадение прогретых и свежих разрешений для совпавшего алиаса. Посторонний алиас сохранил fallback. Оба режима проверены на трёх версиях PHP. [Спецификация](attribute-availability-performance.md#explicit-observation-for-native-parameter-reflection)
- **Средняя серьёзность при ручной сборке — общее runtime-состояние.** Два контейнера с одним `EntryCache` получили один прогретый результат, а второй заменил core-значение первого. Предложены единое присоединение компонентов до публикации core и проверка полномочий для прямой записи в присоединённый `AliasResolver`. Прототип отклонил повторное присоединение, сохранил первый контейнер и позволил повторить сборку с тем же композитом и независимыми компонентами. Поддерживаемая мутация `Container::alias()` обновила прогретый маршрут. [Спецификация](definition-owner-lifecycle.md#ownership-of-collaborators-supplied-to-the-container)

Оба решения проверены в изолированных копиях. В рабочем коде из публичных типов добавлен `AttributeMatchingParameterResolver`. Сигнатуры всех 139 прежних публичных типов совпали.

### Производительность после внедрения

Шесть чередующихся пар CLI-процессов на одном ядре для каждой версии PHP. База — снимок рабочего дерева перед внедрением. Значения ниже показывают медианы парных изменений задержки. [RuntimeBench](../../benchmarks/RuntimeBench.php)

| Сценарий | PHP 8.4.28 | PHP 8.5.13 |
|---|---:|---:|
| Сборка по умолчанию | −1,66% | +1,36% |
| Прогретый `get()` | 0,00% | −2,90% |
| `make()` с автовнедрением | −3,06% | −4,24% |
| `call()` с массивом метода | −3,50% | −7,10% |
| `call()` с переиспользуемым замыканием | −1,62% | −3,72% |
| Метод `SetUp` | +0,82% | −0,06% |
| DTO с `afterMap` | −3,80% | −1,22% |

В этой серии `make()` с автовнедрением и `call()` с массивом метода на PHP 8.5 ускорились во всех шести парах. Для сборки, `get()`, замыкания, `SetUp` и DTO знак менялся между парами. Отдельный микрозамер прогретого `resolverSlotsFor()` сравнил предварительное вычисление пригодности с исправлением, которое проверяет тип рефлектора при каждом обращении. Задержка снизилась с 310 до 198 нс и с 323 до 206 нс. Медианное парное снижение составило 37,25% и 36,31%. [Классификация](../../src/Resolver/Parameter/ParametersResolver.php) · [Метаданные цели](../../src/Resolver/Target/ParameterTarget.php)

С опциональным резолвером и 32 временными целями, которые ждут объявления имени, пик выделенной памяти на обеих версиях составил 220 904 байта против 214 624 у эквивалентного пользовательского резолвера. До уплотнения записей прототип занимал 243 176 байт. Для одной цели дополнительный пик в этой серии не вырос. С зарегистрированным резолвером медианы времени сборки изменились на +4,12% и +0,53% для одной цели, на +0,90% и −1,19% для 32. Диапазоны всех этих пар пересекали ноль.

Удаление промежуточных копий массива callable проверено отдельно. Медианы для вызова метода изменились на −1,08% и −4,41%, а на PHP 8.4 знак менялся между парами. Рабочий путь сохранил текущие границы владения массивом. [Подготовка вызова](../../src/CallableExecutor.php)
