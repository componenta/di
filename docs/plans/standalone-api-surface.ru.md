## Проблема и происхождение

Третий полный аудит выявил пробел в политике поддержки: публичный или protected-метод может иметь внешних потребителей, даже когда текущий pipeline контейнера его не вызывает. Удаление такого метода как неиспользуемого и тестирование каждой детали реализации только ради mutation coverage молча выбирают противоположные контракты совместимости. Исходный [английский отчёт](https://github.com/componenta/di/blob/80cb69a59f001a7d9c49af6e254ff3f58ffa8504/docs/audit/2026-11-15-di6-full-reaudit-round3.md#architecture-decisions-and-implementation-plans) и [подробный русский план](https://github.com/componenta/di/blob/80cb69a59f001a7d9c49af6e254ff3f58ffa8504/docs/audit/2026-11-15-di6-full-reaudit-round3.ru.md#6-решения-по-архитектуре-и-план-действий) явно перенесены в четвёртый аудит. Этот документ сохраняет решение, но не выдаёт исторический состав тестов за текущий.

Вопрос касается трёх связанных поверхностей. Он отделён от уже реализованного контракта standalone composite и владения definitions в [definition-owner-lifecycle](definition-owner-lifecycle.ru.md).

| Поверхность | Текущее поведение и имеющиеся доказательства | Оставшееся решение |
|---|---|---|

## Почему требуется решение

Высокоуровневый pipeline и самостоятельный caller владеют разной работой. Pipeline передаёт policy callbacks и guards; прямой caller выбирает collaborators и может не передавать callback. Контракт должен явно распределить attribute phases, validation, request-source checks, allocation и оборачивание ошибок. Одного названия метода для этого недостаточно.

Если молча превратить `prepare()` в no-op, изменится момент ошибки некорректной композиции. Если начать eager materialization аргументов атрибутов, шаг подготовки metadata получит дополнительные пользовательские эффекты. Аналогично вызов ранее отсутствовавшего callback при инициализации объекта без конструктора добавит эффект. Такие изменения требуют выбранного контракта и наблюдаемого потребителем regression- либо migration-сценария.

## Варианты и рекомендация

| Вариант | Выигрыш | Цена и совместимость |
|---|---|---|
| Явно поддержать выбранные standalone-методы | Потребитель получает документированные lifecycle- и error-гарантии для низкоуровневой интеграции; тесты защищают реальные расширения. | Каждое обещание должно переживать внутренние оптимизации; нужны сопровождение примеров и регрессий. |
| Сохранить отдельные методы как implementation API с переходом | Внутренние планы и кеши можно развивать без обещания поддерживать каждую доступную функцию как постоянный extension point. | Нужны consumer inventory, явная документация и совместимый deprecation/migration-путь. Аннотация `@internal` не устраняет существующего пользователя. |
| Сразу удалить wrapper или снизить видимость, поскольку pipeline его не использует | Видимая поверхность уменьшается. | Вариант отклонён без фактического основания: callers репозитория не равны всем downstream-потребителям. |

**Рекомендация:** сохранить поведение и завершить целевой inventory. Если известные интеграции используют уже полезные и проверенные standalone-маршруты, предпочтительно документировать их. Не вводить новый facade или дублирующий pipeline только ради устранения неоднозначности документации. Ограничение либо deprecation требует конкретной замены и обоснования совместимости.

Ускорение, снижение памяти или security hardening от этой работы не заявляются. Выигрыш — проверяемая граница совместимости и тесты, защищающие поведение реальных приложений.

## План после выбора контракта

1. **Собрать потребителей.** Учесть README, migration-примеры, опубликованное API-описание, тесты репозитория и известных Composer consumers. Недоступный downstream-код отметить как неизвестный. Пустой поиск по этому репозиторию не означает отсутствие потребителей.
2. **Опубликовать матрицу поддержки на двух языках.** Для каждого метода определить входы, обязательных collaborators, момент validation, handler execution, владельца callback, exceptions и lifetime. Отделить прямое создание от полного lifecycle контейнера: direct API не должен обещать функции, которых не выполняет.
3. **Выбрать семантику подготовки.** Определить немедленные гарантии `prepare()`, последствия новой availability revision и обязанности последующего `process()`. Сохранить late discovery и completed-prefix checks; успешная подготовка не должна навсегда замораживать отсутствующий атрибут.
4. **Выбрать семантику callback.** Описать наличие/отсутствие callback для создания и инициализации с конструктором и без него. Указать точное число вызовов и положение до allocation либо constructor invocation. Сохранить уже установленные request-source checks, identity и wrapping исключений.
5. **Внести только нужное изменение реализации.** Сохранить общий prepared-маршрут. При выборе deprecation сначала документировать замену и доказать её на реальном сценарии потребителя. Этот документ сам по себе не удаляет protected hooks и не меняет visibility.
6. **Добавить недостающие публичные witnesses.** Использовать прямой API или реальный subclass с публичным extraction-методом. Не обращаться к private caches, внутренним счётчикам или случайному тексту сообщений ради увеличения MSI.
7. **Обновить примеры и migration.** Явно отметить реализованные и предлагаемые обещания. Для runtime-изменения выполнить затронутые тесты и обычные gates PHP 8.4/8.5. Для уточнения документации нужны проверка ссылок и примеров, а не вымышленный performance-выигрыш.

## Критерии приёмки

| Сценарий | Требуемое наблюдение по выбранному контракту |
|---|---|
| Прямые `create()` / `initialize()` с зависимостями и явными значениями | Корректные значения, defaults и один вызов конструктора; initialization сохраняет identity переданного объекта. Имеющиеся доказательства сохраняются. |
| Создание/инициализация без конструктора, callback передан/пропущен | Число вызовов и момент определены; callback не переигрывается ради сходимости. |
| Ошибка prepared-параметра | Конструктор/allocation и callback следуют выбранной границе; DI-исключения и foreign causes сохраняют владельца диагностики. |
| `prepare()` с некорректной композицией | Момент ошибки соответствует выбранной eager-validation либо warmup-политике. |
| Late availability после prepare, cold/warm и direct/pipeline | Последующая поддерживаемая работа использует текущие metadata; завершённая работа не считается выполненной задним числом и не переигрывается. |
| Custom mapper subclass | Сохраняются выбранные request attributes/files, null, конфликты источников, transformation и актуальные значения последовательных requests. |
| Reentrant- или Fiber-вызовы | Invocation values и экземпляры атрибутов изолированы; shared plan не удерживает request/receiver. |
| Миграция downstream при deprecation | Для каждого учтённого поддерживаемого использования есть исполняемый пример замены; release notes описывают совместимость. |

План завершён, когда опубликована матрица поддержки, проверен consumer inventory и есть тесты выбранных гарантий. Сам по себе рост mutation score вопрос не закрывает.

## Дополнительная граница политики: условный тип результата для class-name ID

### Статус, область и нынешний контракт

**Доказательство добавлено 20 ноября 2026 года, проход 23:** условный PHPDoc методов [`Container::get()` / `make()`](../../src/Container.php) и [`FactoryInterface::make()`](../../src/FactoryInterface.php) обещает `T` для аргумента `class-string<T>`. API регистрации рассматривает обычный ID как имя: ID, совпадающий с именем класса, может обозначать посторонний объект, а `get()` может вернуть scalar. Подтверждено расхождение безусловного статического вывода с допустимой конфигурацией. Оно не доказывает runtime-дефект разрешения и не выбирает изменение API. Пример ниже проверен на [`748357f`](https://github.com/componenta/di/tree/748357fa00c108ab5be0d29f46eb1185c547eb42), PHP 8.4.28, PHP 8.5.13 и PHPStan 2.3.5 с максимальным уровнем.

Точная область — PHPDoc конкретного `Container::get()` и PHPDoc `make()` у класса и интерфейса. Нативные сигнатуры уже возвращают соответственно `mixed` и `object`. Метод PSR-11 `ContainerInterface::get()` не получает generic-обещание конкретного контейнера. Решение о поддержке standalone creator выше и [решение о типах нормализации конфигурации](configuration-normalization-contract.ru.md) остаются отдельными вопросами.

[Нынешнее runtime-поведение](../../README.ru.md#поведение-во-время-выполнения) позволяет локальному definition выбрать свой продукт. `make()` требует только объект: разрешает локальное definition либо fallback и обходит shared values, внешние контейнеры и delegators. `get()` дополнительно допускает заранее переданные или заменённые значения, aliases, внешний результат и результат delegator pipeline запрошенного ID. У обычных ID нет общей проверки subtype продукта только потому, что написание ID является именем PHP-класса. Ограничение совместимыми продуктами изменило бы множество принимаемых приложений, а не только исправило аннотацию. У защищённых core identities уже есть собственные правила; они исключены из этого предложения.

### Воспроизводимый пример потребителя

После загрузки Composer autoloader пакета пример использует только публичные API конфигурации и фабрики:

```php
use Componenta\Config\Config;
use Componenta\Config\ConfigKey;
use Componenta\Config\DependencyDefinitions;
use Componenta\Config\Environment;
use Componenta\DI\Container;
use Componenta\DI\ContainerFactory;
use Componenta\DI\Definition\ClassDefinition;

class Expected {}
final class Actual {}

function expected(Container $container): Expected
{
    return $container->make(Expected::class);
}

$container = (new ContainerFactory())->create(
    new Config([], new Environment([])),
    new DependencyDefinitions([
        ConfigKey::FACTORIES => [
            Expected::class => new ClassDefinition(Actual::class),
        ],
    ]),
)->container;
if (!$container instanceof Container) {
    throw new RuntimeException('Unsupported container implementation.');
}

$actual = $container->make(Expected::class); // Runtime-продукт: Actual.
expected($container); // Нативный return-type TypeError в expected().
```

Функция потребителя проходит PHPStan с `level: max`, в том числе с настройкой репозитория `treatPhpDocTypesAsCertain: false`. Замена только вызова на `get(Expected::class)` также проходит. Wrapper, принимающий `FactoryInterface` и вызывающий `make(Expected::class)`, тоже проходит. Во время исполнения все три wrapper отказывают на постороннем binding; прямые `get()` и `make()` успешно возвращают `Actual`. Ошибка принадлежит нативной декларации результата потребителя, за границей уже завершённого разрешения DI. Холодный и прогретый shared `get()` показывают одинаковое поведение.

Независимые controls отделяют расхождение от общей ошибки анализатора или DI:

| Контроль | Наблюдение на обеих PHP |
|---|---|
| Обычный autowire `Expected` | Все три типизированных wrapper возвращают `Expected`; shared identity у `get()` и fresh identity у обычного `make()` сохранены. |
| Явное `ClassDefinition` для наследника `Expected` | Все типизированные wrapper возвращают совместимого наследника. |
| Factory под `Expected::class`, возвращающая `7` | Прямой `get()` возвращает `7`; типизированный wrapper получает нативный `TypeError` на холодном и прогретом вызове. Объектный результат scalar `make()` не заявляется. |
| Opaque ID с definition постороннего объекта | Wrapper с `mixed` для `get()` и `object` для `make()` проходит static analysis и возвращает объект. Scalar service под opaque ID также работает с `mixed` wrapper. |
| Нативная функция, возвращающая параметр `object` или `mixed` как `Expected` | PHPStan сообщает `return.type`; совместимый объект проходит runtime, посторонний объект и scalar вызывают такой же нативный `TypeError`. Ignore, cast и asserted type не используются. |

Пример доказывает свойство объявленного generic inference. Это не новая цель для mutation score; постоянный тест, требующий от анализатора всегда принимать небезопасный wrapper, не нужен.

### Варианты и цена совместимости

| Вариант | Выигрыш | Цена и обязательства |
|---|---|---|
| A. Точно описать unrestricted lookup: `mixed` для `get()`, `object` для `make()` | Статический результат соответствует каждой ныне поддерживаемой регистрации. Runtime-входы, разрешение и identities можно сохранить. | Исчезает удобный вывод типов обычного autowire класса и совместимых interface bindings. Потребителям может понадобиться явное проверенное сужение; нужны release notes, примеры и downstream inventory. Даже изменение одних аннотаций может существенно нарушить статическую совместимость. |
| B. Добавить явно проверяемую типизированную операцию рядом с точно описанным unrestricted lookup | Обещание результата `T` для `class-string<T>` можно установить проверкой фактического результата до возврата. Отдельный ожидаемый класс мог бы поддержать и opaque ID. | Появляется сопровождаемая публичная операция либо facade. Нужно определить имя, class/interface inputs, mismatch exception, эффекты autoload и связь запрошенного ID с ожидаемым типом. Операция выполняет ровно один underlying lookup/creation, сохраняет identity успешного продукта и не переигрывает factories, delegators либо callbacks. Добавлять только при доказанном спросе потребителя. |
| C. Сохранить условный вывод как явное допущение приложения | Сохраняет нынешнее удобство static analysis и не требует немедленной миграции приложений с совместимыми class-name bindings. | Документировать обязанность приложения сохранять subtype invariant при регистрации, aliases, mutation, delegates и providers на соответствующих путях. Нынешние API не дают анализатору доказать этот invariant, а документация не делает unrestricted-обещание корректным. Принимать как сознательную политику либо переход с точными примерами и явно указанным ограничением. |

Молчаливое добавление `instanceof`/`is_a` в нынешние `get()` или `make()` исключено из этой документальной работы: оно отвергло бы допустимую регистрацию opaque ID и ограничило произвольные delegated/external values для `get()`. Молчаливое ослабление трёх PHPDoc выбрало бы A без оценки потребителей. Ни то ни другое не следует автоматически из доказательства.

**Рекомендация и условие начала:** собрать consumer inventory до выбора статической политики API. Приоритет повышается, когда реальная интеграция использует class-name ID с посторонним продуктом, принимает изменяемые либо plugin-provided registrations или полагается на generic-результат при входе в типизированную границу. Для гарантии, охватывающей каждую допустимую конфигурацию, базой должны быть точные unrestricted return types; проверяемая типизированная операция нужна только при доказанной пользе для потребителя. Если проект сохраняет допущение приложения, явно опубликовать ограничение и не называть его runtime-проверкой принадлежности классу. На время выбора это предложение сохраняет нынешнее поведение и аннотации.

### Последовательность реализации и приёмка

1. **Учесть три места декларации и их потребителей.** Включить вызовы конкретного контейнера, вызовы через `FactoryInterface`, обычный autowire, совместимые interface bindings, class-name aliases, factories, raw services и изменяемые регистрации. Недоступный downstream-код остаётся неизвестным. Явно сохранить bypass delegators/external containers в `make()`.
2. **Выбрать и опубликовать гарантию на двух языках.** Решить, является ли class-name inference безусловным, явно проверяемым либо зависящим от invariant приложения. Определить migration и release compatibility до изменения PHPDoc или добавления операции.
3. **Сохранить runtime-контракт существующих методов.** Статическая политика не должна попутно запрещать допустимые bindings, менять shared/fresh identity, добавлять replay lookup либо переносить callbacks приложения. Отдельному ограничению нужны собственные доказательство и решение.
4. **Реализовать минимально выбранную поверхность и примеры.** Для проверяемой операции определить один lookup и одну последующую проверку результата: interfaces, subclasses, посторонние объекты, scalars и null. Определить владельца ошибки и её момент, не меняя исключения нынешнего generic lookup. Для политики допущения показать конфигурации, которые его соблюдают и нарушают.
5. **Проверить матрицу реального потребителя.** Запустить узкие PHPStan fixtures максимального уровня без ignores, casts и ложных assertions вместе с runtime controls поддерживаемых PHP 8.4/8.5. При точных результатах непроверенный wrapper `Expected` больше не проходит. У проверяемой операции обещание `T` выполняется либо до возврата возникает документированная mismatch error. При политике допущения нынешний counterexample остаётся явно указанным ограничением, а не закрытым дефектом корректности.

Приёмка также требует холодных/прогретых shared результатов, относящихся к `get()` переходов aliases и mutations, положительных autowire/compatible-binding/opaque-ID случаев. Delegated/external mismatch проверяется лишь у операции, которая действительно использует эти пути. Для успешного проверяемого lookup сохраняются один вызов и identity объекта. Нативный контракт PSR-11, protected core identities, validation аргументов конструктора, доверие прикладному коду, низкоуровневые prepared callbacks и правила совместного использования standalone collaborators не меняются этим решением. Security- или performance-выигрыш не заявляется.
