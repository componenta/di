# Самостоятельное создание объектов, обработка атрибутов и request helpers

[English version](standalone-api-surface.md)

**Статус на 20 ноября 2026 года:** сохранённый архитектурный план, частично покрытый последующими контрактными тестами. Удаление методов, изменение видимости или новая runtime-политика не выбраны. Остаётся определить поддерживаемые самостоятельные низкоуровневые API и точные гарантии подготовки и callbacks. Текущая точка исходников: [`43c4641`](https://github.com/componenta/di/tree/43c464187f80c95802fc36191350ae68b70a469e).

## Проблема и происхождение

Третий полный аудит выявил пробел в политике поддержки: публичный или protected-метод может иметь внешних потребителей, даже когда текущий pipeline контейнера его не вызывает. Удаление такого метода как неиспользуемого и тестирование каждой детали реализации только ради mutation coverage молча выбирают противоположные контракты совместимости. Исходный [английский отчёт](https://github.com/componenta/di/blob/80cb69a59f001a7d9c49af6e254ff3f58ffa8504/docs/audit/2026-11-15-di6-full-reaudit-round3.md#architecture-decisions-and-implementation-plans) и [подробный русский план](https://github.com/componenta/di/blob/80cb69a59f001a7d9c49af6e254ff3f58ffa8504/docs/audit/2026-11-15-di6-full-reaudit-round3.ru.md#6-решения-по-архитектуре-и-план-действий) явно перенесены в четвёртый аудит. Этот документ сохраняет решение, но не выдаёт исторический состав тестов за текущий.

Вопрос касается трёх связанных поверхностей. Он отделён от уже реализованного контракта standalone composite и владения definitions в [definition-owner-lifecycle](definition-owner-lifecycle.ru.md).

| Поверхность | Текущее поведение и имеющиеся доказательства | Оставшееся решение |
|---|---|---|
| [`InstanceCreator`](../../src/Resolver/Entry/InstanceCreator.php) `create()` / `initialize()` | Оба метода используют подготовленное разрешение параметров. [`InstanceCreatorContractTest`](../../tests/Contract/InstanceCreatorContractTest.php) проверяет явные аргументы, зависимости с атрибутами, defaults, однократный конструктор, объекты без конструктора и нативные ошибки выделения. | Опубликовать, является ли direct construction поддерживаемым extension API, каковы его lifecycle-границы и какие prepared-методы предназначены для downstream. Эти пути уже не являются непокрытыми. |
| `createPrepared()` / `initializePrepared()` и `beforeConstructor` | Object pipeline использует prepared-маршрут. [`RequestConstructorSourceContractTest`](../../tests/Contract/RequestConstructorSourceContractTest.php) и [`RequestConstructorMetadataContractTest`](../../tests/Contract/RequestConstructorMetadataContractTest.php) защищают соответствующие финальные проверки до вызова конструктора. | Указать число вызовов callback и его положение относительно разрешения аргументов и allocation, включая отсутствие конструктора. Сейчас `createPrepared()` вызывает callback для класса без конструктора; `initializePrepared()` в таком случае возвращается без него. Унификация этого различия требует решения совместимости, а не автоматического исправления бага. |
| [`AttributeProcessor::prepare()`](../../src/Resolver/Attribute/AttributeProcessor.php) и прямой processing | `prepare()` строит execution plan, но не исполняет handlers; при этом возможны autoload и вызовы composition rules. Гарантии чистоты или отсутствия пользовательского кода нет. [`StandaloneAttributeProcessorContractTest`](../../tests/Contract/StandaloneAttributeProcessorContractTest.php) проверяет независимые before/after-фазы, повторное создание и эффекты записи свойства без bootstrap collaborator. [`AttributeProcessorRevisionContractTest`](../../tests/Contract/AttributeProcessorRevisionContractTest.php) защищает refresh доступности. | Решить, обещает ли подготовка eager validation именно в этой точке либо является необязательным прогревом с изменяемым моментом validation. Определить, что late discovery всё ещё может инвалидировать после успешной подготовки. |
| Protected [`ExtractsRequestData::extractSharedData()`](../../src/Attribute/ExtractsRequestData.php) | [`RequestAttributeProtocolContractTest`](../../tests/Contract/RequestAttributeProtocolContractTest.php) уже вызывает helper через `SharedSourceMapper::extract()`: selection, transformation, новые значения request и конфликты источников. Custom mappers поддержаны в [примерах mapping](request-mapping-examples.ru.md). | Указать, поддерживается ли конкретный protected helper как hook для subclass либо обещание относится только к публичному extraction/mapping-протоколу. На время решения сохранить проверенное поведение. |

Это поверхность совместимости, а не доказанная уязвимость. Из наблюдений не следует, что все публичные collaborators нужно удалить или объявить внутренними. Существующий набор тестов также не доказывает, что все downstream-формы вызова уже учтены.

## Почему требуется решение

Высокоуровневый pipeline и самостоятельный caller владеют разной работой. Pipeline передаёт policy callbacks и guards; прямой caller выбирает collaborators и может не передавать callback. Контракт должен явно распределить attribute phases, validation, request-source checks, allocation и оборачивание ошибок. Одного названия метода для этого недостаточно.

Если молча превратить `prepare()` в no-op, изменится момент ошибки некорректной композиции. Если начать eager materialization аргументов атрибутов, шаг подготовки metadata получит дополнительные пользовательские эффекты. Аналогично вызов ранее отсутствовавшего callback при инициализации объекта без конструктора добавит эффект. Такие изменения требуют выбранного контракта и наблюдаемого потребителем regression- либо migration-сценария.

## Варианты и рекомендация

| Вариант | Выигрыш | Цена и совместимость |
|---|---|---|
| Явно поддержать выбранные standalone-методы | Потребитель получает документированные lifecycle- и error-гарантии для низкоуровневой интеграции; тесты защищают реальные расширения. | Каждое обещание должно переживать внутренние оптимизации; нужны сопровождение примеров и регрессий. |
| Сохранить отдельные методы как implementation API с переходом | Внутренние планы и кеши можно развивать без обещания поддерживать каждую доступную функцию как постоянный extension point. | Нужны consumer inventory, явная документация и совместимый deprecation/migration-путь. Аннотация `@internal` не устраняет существующего пользователя. |
| Сразу удалить wrapper или снизить видимость, поскольку pipeline его не использует | Видимая поверхность уменьшается. | Вариант отклонён без фактического основания: callers репозитория не равны всем downstream-потребителям. |

**Рекомендация:** сохранить поведение и завершить целевой inventory. Если известные интеграции используют уже полезные и проверенные standalone-маршруты, предпочтительно документировать их. Не вводить новый facade или дублирующий pipeline только ради устранения неоднозначности документации. Ограничение либо deprecation требует конкретной замены и обоснования совместимости.

Ускорение, снижение памяти или security hardening от этой работы не заявляются. Выигрыш — проверяемая граница совместимости и тесты, защищающие поведение реальных приложений.

## План после выбора контракта

1. **Собрать потребителей.** Учесть README, migration-примеры, опубликованное API-описание, тесты репозитория и известных Composer consumers. Недоступный downstream-код отметить как неизвестный. Пустой поиск по этому репозиторию не означает отсутствие потребителей.
2. **Опубликовать матрицу поддержки на двух языках.** Для каждого метода определить входы, обязательных collaborators, момент validation, handler execution, владельца callback, exceptions и lifetime. Отделить прямое создание от полного lifecycle контейнера: direct API не должен обещать функции, которых не выполняет.
3. **Выбрать семантику подготовки.** Определить немедленные гарантии `prepare()`, последствия новой availability revision и обязанности последующего `process()`. Сохранить late discovery и completed-prefix checks; успешная подготовка не должна навсегда замораживать отсутствующий атрибут.
4. **Выбрать семантику callback.** Описать наличие/отсутствие callback для создания и инициализации с конструктором и без него. Указать точное число вызовов и положение до allocation либо constructor invocation. Сохранить уже установленные request-source checks, identity и wrapping исключений.
5. **Внести только нужное изменение реализации.** Сохранить общий prepared-маршрут. При выборе deprecation сначала документировать замену и доказать её на реальном сценарии потребителя. Этот документ сам по себе не удаляет protected hooks и не меняет visibility.
6. **Добавить недостающие публичные witnesses.** Использовать прямой API или реальный subclass с публичным extraction-методом. Не обращаться к private caches, внутренним счётчикам или случайному тексту сообщений ради увеличения MSI.
7. **Обновить примеры и migration.** Явно отметить реализованные и предлагаемые обещания. Для runtime-изменения выполнить затронутые тесты и обычные gates PHP 8.4/8.5. Для уточнения документации нужны проверка ссылок и примеров, а не вымышленный performance-выигрыш.

## Критерии приёмки

| Сценарий | Требуемое наблюдение по выбранному контракту |
|---|---|
| Прямые `create()` / `initialize()` с зависимостями и явными значениями | Корректные значения, defaults и один вызов конструктора; initialization сохраняет identity переданного объекта. Имеющиеся доказательства сохраняются. |
| Создание/инициализация без конструктора, callback передан/пропущен | Число вызовов и момент определены; callback не переигрывается ради сходимости. |
| Ошибка prepared-параметра | Конструктор/allocation и callback следуют выбранной границе; DI-исключения и foreign causes сохраняют владельца диагностики. |
| `prepare()` с некорректной композицией | Момент ошибки соответствует выбранной eager-validation либо warmup-политике. |
| Late availability после prepare, cold/warm и direct/pipeline | Последующая поддерживаемая работа использует текущие metadata; завершённая работа не считается выполненной задним числом и не переигрывается. |
| Custom mapper subclass | Сохраняются выбранные request attributes/files, null, конфликты источников, transformation и актуальные значения последовательных requests. |
| Reentrant- или Fiber-вызовы | Invocation values и экземпляры атрибутов изолированы; shared plan не удерживает request/receiver. |
| Миграция downstream при deprecation | Для каждого учтённого поддерживаемого использования есть исполняемый пример замены; release notes описывают совместимость. |

План завершён, когда опубликована матрица поддержки, проверен consumer inventory и есть тесты выбранных гарантий. Сам по себе рост mutation score вопрос не закрывает.
