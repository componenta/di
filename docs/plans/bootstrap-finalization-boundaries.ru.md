# Завершение bootstrap: доступность атрибутов и освобождение ссылок

[English version](bootstrap-finalization-boundaries.md)

## Перепроверка после сохранения отчёта

Последующая [перепроверка доказательств](audit-architecture-recheck-2026-11-20.ru.md) содержит новые исполнения на PHP 8.4.28 и 8.5.13 после сохранения отчётов и [машиночитаемый вывод](audit-architecture-recheck-2026-11-20.json). Исторические коммиты и указания на отсутствие повторного запуска при первоначальном сохранении остаются историческими; новый отчёт добавляет последующее доказательство. Архитектурный вариант этой проверкой не реализован.

**Статус: предложено; не реализовано.** Отчёт сохраняет две подтверждённые границы ветки рефакторинга DI 6 и предлагает отдельные решения по контрактам. Он не вводит API уведомления о доступности, новую фазу очистки или гарантию обнаружения скрытой готовности автозагрузчика. Локальные исправления сходимости и обнаружения сохраняются.

**Рекомендация:** влияющие объявления атрибутов должны быть доступны до того, как bootstrap-зависимости используют их семантику. Проектировать добровольный явный сигнал доступности следует только при реальной потребности интеграции в динамической готовности. Отдельно предлагается завершающая фаза освобождения ссылок с консервативным отказом при наблюдаемом изменении метаданных до успешной публикации контейнера. Она меняет поведение при ошибках и требует отдельного архитектурного решения.

### Завершённые локальные исправления остаются обязательными

[`162072e346a6b369e491e310df404ec31a756df4`](https://github.com/componenta/di/commit/162072e346a6b369e491e310df404ec31a756df4) исправил сходимость и обнаружение при повторном входе. [`43c4641`](https://github.com/componenta/di/commit/43c464187f80c95802fc36191350ae68b70a469e) добавил регрессионные проверки через публичные пути. В проверенном коде:

- [`BootstrapResolutionGuard::finish()`](../../src/Internal/BootstrapResolutionGuard.php) сохраняет учёт активным до конца проверки. Проверка повторяется при изменении наблюдаемого поколения либо числа наблюдений параметров, которым ещё требуется доказательство. Разрешение с полным окончательным префиксом резолверов не создаёт бесконечную новую обязанность проверки.
- [`AttributeDefinitionRegistry::revision`](../../src/Attribute/Composition/AttributeDefinitionRegistry.php) обрабатывает имена, обнаруженные при повторном входе в ходе этого опроса. Каждое отсутствующее имя получает существующие попытки автозагрузки класса/интерфейса один раз за этот опрос. Итоговая проверка с отключённой автозагрузкой замечает объявления более ранних имён, сделанные последующими callbacks.
- Необъявленное имя не опрашивается бесконечно лишь потому, что его загрузчик может стать готов позднее. Стабильное разрешение при повторном входе и постоянные missing markers должны завершаться. Для произвольного пользовательского графа callbacks, непрерывно добавляющего новые имена, общей гарантии завершения нет.

Эти исправления покрывают наблюдаемые объявления и новые наблюдения, действительно требующие проверки. Ни одно из них не обеспечивает видимость закрытой готовности и не проверяет изменения, вызванные освобождением самой проверки. [План доступности атрибутов](attribute-availability-performance.ru.md) описывает измеренную стоимость опроса и отдельное предложение синхронизации B2.

## 2. Граница A: закрытая готовность после последнего опроса имени

### Проблема и самостоятельное воспроизведение

Загрузчик получает запрос `First` и возвращает miss. Позднее в том же опросе реестра он получает `Later`; этот callback меняет состояние приложения так, что теперь `First` можно загрузить. Он не объявляет `First`, не меняет список автозагрузчиков и не уведомляет реестр. Итоговая проверка реестра не видит нового объявления. Следующий самостоятельный опрос снова вызывает загрузчик и обнаруживает `First`.

В checkout репозитория с установленными зависимостями сохраните пример в PHP-файл и выполните его из корня репозитория на PHP 8.4+ в **новом процессе**. Используются только Composer autoload и публичные методы реестра; закрытая рефлексия и изменённые исходники не нужны. Пространство имён должно быть изолировано от других воспроизведений.

```php
<?php
declare(strict_types=1);

namespace Audit21HiddenReadiness;

require getcwd() . '/vendor/autoload.php';

use Componenta\DI\Attribute\Composition\AttributeDefinitionRegistry;
use Componenta\DI\Attribute\Inject;

$registry = new AttributeDefinitionRegistry();
$first = __NAMESPACE__ . '\\First';
$later = __NAMESPACE__ . '\\Later';
$registry->definition($first);
$registry->definition($later);
$before = $registry->revision;
$ready = false;
$loads = [$first => 0, $later => 0];
$loader = static function (string $name) use ($first, $later, &$ready, &$loads): void {
    if (array_key_exists($name, $loads)) {
        ++$loads[$name];
    }
    if ($name === $first && $ready) {
        class_alias(Inject::class, $first);
    } elseif ($name === $later) {
        $ready = true; // No declaration and no notification.
    }
};
spl_autoload_register($loader);
try {
    $firstPoll = $registry->revision;
    $declaredAfterFirst = class_exists($first, false);
    $secondPoll = $registry->revision;
    echo json_encode([
        'before' => $before,
        'first_poll' => $firstPoll,
        'readiness_changed' => $ready,
        'declared_after_first' => $declaredAfterFirst,
        'second_poll' => $secondPoll,
        'declared_after_second' => class_exists($first, false),
        'loader_calls' => $loads,
    ], JSON_THROW_ON_ERROR), "\n";
} finally {
    spl_autoload_unregister($loader);
}
```

Сохранённый результат:

```json
{"before":0,"first_poll":0,"readiness_changed":true,"declared_after_first":false,"second_poll":1,"declared_after_second":true,"loader_calls":{"Audit21HiddenReadiness\\First":3,"Audit21HiddenReadiness\\Later":4}}
```

Исходное выполненное воспроизведение выбирало неизменяемые снимки через автозагрузчик бенчмарков репозитория с переназначением исходников. Пример выше заменяет только эту подготовку загрузки на Composer autoload текущего checkout. Результат устанавливает границу наблюдаемости реестра. Риск использования другой семантики при последующем разрешении следует из поддерживаемого позднего обнаружения; сам этот небольшой пример не доказывает отдельный полный сбой порядка bootstrap.

### Почему ещё один цикл опроса не является полным исправлением

В конечной последовательности непрозрачных callbacks всегда есть последний вызов. Он может изменить готовность более раннего имени, не объявляя его. Ещё один безусловный проход перемещает последнюю такую возможность; он не доказывает устойчивость произвольного состояния приложения. Неограниченные повторы не завершаются на обычных постоянных misses и могут повторять пользовательские эффекты. Промежуточный подход к bootstrap в [`4abca4a`](https://github.com/componenta/di/commit/4abca4a5eb03643fe4c0f01778e0f0f59f580010) уже потребовал исправления сходимости в `162072e`; расширение условия цикла не должно возвращать тот дефект.

Архитектурный вопрос — какое событие делает доступность определённой и кто обязан его опубликовать. У закрытого флага загрузчика такого события в текущем интерфейсе нет. `supports()` — существующий классификатор, а не неявный механизм уведомления.

### Варианты, рекомендация и совместимость

| Вариант | Гарантия / выигрыш | Цена и совместимость |
|---|---|---|
| Фактическая предварительная загрузка до использования bootstrap-зависимостей | Влияющие объявления существуют до использования их семантики; конечное проверяемое правило порядка. | Приложениям нужно перенести объявления или подготовку интеграции раньше. Одной регистрации загрузчика или закрытого ready-флага недостаточно. |
| Добровольное явное уведомление о доступности | Согласованные переходы готовности изменяют наблюдаемое монотонное поколение. Итоговая проверка обнаруживает изменение без произвольного вызова загрузчика при чтении поколения. | Новый контракт интеграции: владелец, переход, порядок, ошибки и повторный вход. У неучаствующих загрузчиков остаётся нынешняя граница. |
| Фиксация семантики при первом использовании | Поздняя доступность больше не меняет выбранную семантику цели. | Широкое изменение нынешних late discovery и свежего `make()`; также требуется определить область и срок действия такой фиксации. |
| Сохранение текущей границы с её документированием | Runtime и интеграции не меняются. | Более сильной гарантии для закрытой готовности нет; порядок остаётся ответственностью приложения. |

**Рекомендуемый минимум:** документировать фактическую предварительную загрузку как поддерживаемую подготовку bootstrap-зависимостей. Рассматривать добровольный сигнал только при конкретной потребности динамической интеграции. Не добавлять глобальный реестр, постоянный отрицательный кеш или полный сброс кеша контейнера. Сохранить позднее обнаружение на поддерживаемых runtime-путях и идентичность общего сервиса.

### Условный план реализации

1. Указать в EN/RU документации расширений и миграции, что должно быть объявлено до использования bootstrap-зависимости фабрикой расширения. Различить фактическое объявление, новое отслеживаемое имя и закрытую готовность уже отслеживаемого имени.
2. Если выбраны уведомления, назначить одного владельца доступности на контейнер и определить, как общие для процесса объявления/состояние загрузчиков отражаются в каждом участвующем контейнере. Решить, кто может сигнализировать и как интеграция получает доступ к владельцу; форму нового публичного API этот отчёт не выбирает.
3. Сигнал должен монотонно записывать фактический переход до того, как зависимое разрешение сможет его наблюдать. Не увеличивать счётчик на каждом miss или чтении revision. Определить порядок вокруг callbacks и приостановки Fiber; чтение установленного поколения не должно вызывать пользовательский код.
4. Включить сигнал в semantic proof и инвалидацию планов. Уведомлённый несовместимый переход во время bootstrap должен привести к отказу до успешной публикации; завершённые обработчики, конструкторы и разрешённые значения не выполняются повторно.
5. До сокращения существующих обновлений учесть прямые API реестра/процессора, вложенные вызовы, ошибки, вход lazy/proxy и взаимодействие с B2. Сохранять нынешний опрос до совместной реализации всех обязательств его замены.

### Критерии приёмки

- Предварительно загруженные влияющие атрибуты дают согласованное поведение bootstrap/свежего создания и сохраняют тот же общий экземпляр.
- Согласованный уведомлённый несовместимый переход отклоняется до успешной сборки с диагностикой, объясняющей способ исправления.
- Постоянный missing marker и стабильный reentrant `make()` завершаются; реальные объявления последующими загрузчиками и имена, обнаруженные в ходе опроса, остаются видимыми в этом опросе.
- Классы, псевдонимы, интерфейсы, исключение резервной попытки, холодные/прогретые случаи, прямые API и Fiber сохраняют выбранный контракт.
- Конструкторы, обработчики и значения конкретного вызова выполняются однократно для исходной работы; сброс кеша не пересоздаёт уже выданный общий сервис.
- Отсутствие и объявления, и уведомления остаётся явно указанной границей. Успешный тест уведомления нельзя описывать как решение произвольной закрытой готовности.

## 3. Граница B: изменение метаданных при освобождении bootstrap records

### Проблема и самостоятельное воспроизведение

Bootstrap создаёт и кеширует `Owner`, пока `LateInject` недоступен, поэтому зависимость остаётся `null`. Последующий вызов принимает замыкание, захватившее `Token`. Запись проверки удерживает runtime-контекст рефлексии параметра, а через него — замыкание и token. После итоговой проверки семантики освобождение записей освобождает token; его destructor объявляет `LateInject` как псевдоним `Inject`. Сборка успешна. Закешированный owner сохраняет прежнюю зависимость, а новый получает `stdClass`.

Следующий пример использует публичные пути `ContainerFactory`, `Container::get()`, `call()` и `make()`. Сохраните его в PHP-файл и запустите из корня checkout с установленными зависимостями в **новом процессе PHP 8.4+**:

```php
<?php
declare(strict_types=1);

namespace Audit21BootstrapCleanup;

require getcwd() . '/vendor/autoload.php';

use Componenta\Config\Config;
use Componenta\Config\ConfigKey;
use Componenta\Config\DependencyDefinitions;
use Componenta\Config\Environment;
use Componenta\DI\Attribute\Composition\AttributeDefinition;
use Componenta\DI\Attribute\Inject;
use Componenta\DI\Container;
use Componenta\DI\ContainerFactory;

#[\Attribute(\Attribute::TARGET_ALL)]
final class Extra {}

final class Owner
{
    #[LateInject]
    public ?\stdClass $dependency = null;
}

final class Trace
{
    public static array $events = [];
    public static ?\WeakReference $token = null;
}

final class Token
{
    public function __destruct()
    {
        Trace::$events[] = 'destructor';
        class_alias(Inject::class, __NAMESPACE__ . '\\LateInject');
    }
}

try {
    $definitions = new DependencyDefinitions([
        ConfigKey::ATTRIBUTE_DEFINITIONS => [
            static function (Container $container): AttributeDefinition {
                $container->get(Owner::class);
                $token = new Token();
                Trace::$token = \WeakReference::create($token);
                $callback = static fn(string $value = 'ready'): string => $value . ':' . $token::class;
                $container->call($callback);
                unset($callback, $token);
                Trace::$events[] = Trace::$token->get() === null
                    ? 'released inside factory' : 'retained until proof';

                return new AttributeDefinition(Extra::class);
            },
        ],
    ]);
    $container = (new ContainerFactory())->create(
        new Config([], new Environment([])),
        $definitions,
    )->container;
    if (!$container instanceof Container) {
        throw new \RuntimeException('Unexpected container implementation.');
    }
    echo json_encode([
        'status' => 'accepted',
        'events' => Trace::$events,
        'released' => Trace::$token?->get() === null,
        'cached' => get_debug_type($container->get(Owner::class)->dependency),
        'fresh' => get_debug_type($container->make(Owner::class)->dependency),
    ], JSON_THROW_ON_ERROR), "\n";
} catch (\Throwable $exception) {
    echo json_encode([
        'status' => 'failed',
        'events' => Trace::$events,
        'exception' => $exception::class,
        'message' => $exception->getMessage(),
    ], JSON_THROW_ON_ERROR), "\n";
}
```

Сохранённый результат:

```json
{"status":"accepted","events":["retained until proof","destructor"],"released":true,"cached":"null","fresh":"stdClass"}
```

Выполненное воспроизведение использовало [`Tests\Support\ContainerBuilder`](../../tests/Support/ContainerBuilder.php), передающий такую же секцию определений и пустую конфигурацию в публичный `ContainerFactory::create()`. Переносимый пример разворачивает этот helper и использует Composer autoload текущего checkout. Эти изменения подготовки задокументированы и не выдаются за ещё один выполненный замер.

### Почему требуется решение по жизненному циклу

[`BootstrapResolutionGuard`](../../src/Internal/BootstrapResolutionGuard.php) проверяет семантику, затем отключает учёт и очищает записи в `finally`. Проверка и освобождение принадлежащих ей объектов находятся по разные стороны фактической границы завершения. Обнулить массивы недостаточно: локальная переменная `foreach` может удерживать последнюю запись до выхода из метода.

Сохранение исходных рефлекторов ради ещё одной проверки снова откладывает тот же destructor. Восстановление цели замыкания по имени функции теряет runtime-контекст; пользовательские классификаторы могут зависеть от переданного объекта рефлексии. Пересоздание закешированного сервиса или повтор завершённых обработчиков меняет идентичность и повторяет пользовательские эффекты. Отказ сборки, прежде завершавшейся успешно, является решением о совместимости даже при закрытии подтверждённого пробела согласованности.

Предполагаемая гарантия должна ограничиваться синхронной очисткой, принадлежащей созданию контейнера. Произвольные будущие GC, destructors или действия Fiber после публикации нельзя сделать атомарными с более ранним возвратом `create()`. Контейнер также не должен бесконечно удерживать runtime-замыкания ради откладывания проблемы.

### Варианты и рекомендация

| Вариант | Польза | Цена / ограничение |
|---|---|---|
| Документировать запрет изменения метаданных при очистке proof | Небольшое изменение документации без нового runtime-состояния. | Нарушение по-прежнему даёт наблюдаемую успешную, но несогласованную сборку. |
| Явная завершающая очистка с последующей проверкой без пользовательских callbacks | Обнаруживает наблюдаемые изменения от синхронного освобождения до успеха; сохраняет shared identity и исключает повтор работы. | Консервативный отказ может затронуть посторонние изменения. Нужны граница жизненного цикла/публикации и определённая политика ошибок. |
| Отделённые описания семантики с точной повторной проверкой после освобождения | Позволяет потенциально принимать посторонние изменения и точно сообщать изменённую завершённую семантику. | Более широкое перепроектирование записей proof и контрактов пользовательских классификаторов; нужно сохранять смысл контекста замыкания без удержания самих замыканий. |

**Рекомендуемое минимальное строгое поведение:** завершающая фаза очистки с консервативным отказом. Принятие посторонних изменений в этой фазе — отдельное расширение, требующее доказательства, что отделённые описания могут установить их нерелевантность. Существующее разрешение посторонних объявлений при обычном выполнении нельзя молча трактовать как разрешение в новой завершающей фазе; различие следует документировать.

### Условный план реализации

1. Определить фазы: активный учёт, semantic proof, освобождение ссылок proof, итоговое наблюдение, публикация. Для успеха и ошибки указать владельца удаления записей и передачи исключений.
2. После успешного proof оставить только скалярные данные поколения/контрольной точки, нужные для завершения. Отключить учёт и освободить все сильные ссылки, принадлежащие только proof: записи атрибутов, цели параметров, временные ссылки резолверов и последние локальные переменные циклов. Выйти из удерживавшего их scope до завершающего наблюдения.
3. Добавить внешнюю проверку в [`ContainerFactory`](../../src/ContainerFactory.php) после возврата из этого scope. Она должна наблюдать уже объявленные отслеживаемые классы/интерфейсы с отключённой автозагрузкой и поколение выбранных явных уведомлений. Обычного чтения `revision` недостаточно: оно может вызывать загрузчики и создавать новую границу пользовательского кода.
4. При наблюдаемом изменении доступности во время освобождения выбросить `InvalidConfigurationException` до успешного возврата `ContainerValue`. Если исключение возникает в самой очистке, сохранить исходную причину. Не сбрасывать shared cache, не подменять уже выданные объекты и не повторять их создание.
5. Перенести всю потенциально эффектную подготовку перед итоговой контрольной точкой либо доказать, что оставшаяся работа не выполняет пользовательский код и не освобождает значимые временные ссылки. Явно проверить нынешний `get(Config::class)` после `finish()`, создание возвращаемого значения и освобождение scope фабрики. Итоговая проверка должна предшествовать успешной публикации и следовать за всей очисткой, которую обещает покрывать.
6. До широкой реализации обновить EN/RU документацию жизненного цикла/миграции и целевые контракты. Если добровольные сигналы готовности не выбраны, указать, что эта фаза видит только реальные объявления и существующие изменения поколения; границу A она не решает.

### Выигрыш, цена и совместимость

Выигрыш — конкретная гарантия публикации: наблюдаемое несовместимое изменение, вызванное собственным синхронным освобождением ссылок контейнера, больше не скрывается за успешной сборкой. Захваченные замыкания освобождаются до возврата, shared identity сохраняется, пользовательская работа не повторяется.

Минимальная строгая политика отвергает любое наблюдаемое изменение поколения при очистке, включая потенциально постороннее. Это намеренно консервативнее точного сравнения семантики. Документация должна назвать затронутые приложения и способ перехода: объявлять влияющие атрибуты до использования bootstrap-зависимостей и не менять доступность из callbacks освобождения. Этот отчёт не устанавливает числового выигрыша задержки или памяти. Проверка отслеживаемых отсутствующих имён добавляет работу; удержание или копирование runtime proof state не является допустимым обходным решением.

Отказ не откатывает произвольные эффекты приложения и не отзывает ссылку на контейнер, которую расширение уже передало наружу. Гарантия формулируется как отсутствие успешного возврата фабрики; исключения очистки должны документироваться согласованно с существующим оборачиванием исключений фабрикой.

### Критерии приёмки

- Воспроизведение очистки завершается ошибкой до успешной публикации `create()`. При добавлении счётчика создания `Owner` создаётся один раз; обработчики и разрешение значений не повторяются.
- Destructor без изменения метаданных, включая обычный reentrant `get()`, допускает успешную сборку с тем же общим объектом.
- Сценарий, в котором последняя локальная запись цикла — последний владелец, освобождает захваченный token до итогового наблюдения. Одного обнуления массивов недостаточно для прохождения этого теста.
- Слабые ссылки подтверждают отсутствие удержания замыканий/целей, принадлежащих proof, после успеха и ошибки. Отложенные callbacks сохраняют только срок жизни, требуемый их собственным поддерживаемым контрактом.
- Класс, псевдоним или интерфейс, объявленный во время очистки, замечается без вызова автозагрузчиков. Если выбраны явные сигналы, уведомлённые переходы при очистке также замечаются.
- Исключения очистки сохраняют причину и полезный контекст bootstrap. После провала итоговой проверки наружу не выходит успешный результат.
- Консервативный отказ при постороннем наблюдаемом изменении покрыт и задокументирован. Любое последующее ослабление имеет отдельное доказательство точности.
- PHP 8.4/8.5, вложенные bootstrap-вызовы, стабильный повторный вход и соответствующие переключения Fiber сохраняют выбранную синхронную границу. Более поздняя посторонняя активность GC не выдаётся за покрытую этой гарантией.

## 4. Решения перед реализацией

Границе A нужно поддерживаемое правило порядка подготовки приложения и, только при обоснованной необходимости, согласованный контракт доступности. Границе B нужны политика отказа и явный владелец очистки/публикации. Решения должны оставаться отдельными: сигнал делает готовность наблюдаемой, не исправляя момент освобождения ссылок; завершающая проверка замечает объявления, не видя закрытого состояния загрузчика.

Полный сброс контейнера и предположительные повторы не заменяют эти решения. Сохраняются завершённые локальные исправления, действующие проверки через публичные пути и результаты производительности. После фиксации выбранных контрактов реализацию можно вести согласованными участками: каждый включает затронутого владельца, потребителей, диагностику и собственные критерии приёмки.
