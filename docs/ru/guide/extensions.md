# Расширение контейнера

Обработчики разрешения параметров и определения атрибутов передаются через поставщиков конфигурации до вызова `ContainerFactory::create()`. После сборки контейнера соответствующие цепочки обработки не изменяются.

## Пользовательские обработчики параметров

Реализация `ParameterResolverInterface` предоставляет два метода:

- `supports(ParameterTarget $target): bool` определяет, подходит ли обработчик для параметра;
- `resolveParameter(ParameterTarget $target, ParameterResolutionContext $context): ?array` возвращает `[position, value]` либо `null`, чтобы передать разрешение следующему обработчику.

Для источника значения, определяемого одним атрибутом, можно использовать `AttributeMatchingParameterResolver`:

```php
use Componenta\DI\Resolver\Parameter\AttributeMatchingParameterResolver;

#[\Attribute(\Attribute::TARGET_PARAMETER)]
final class TenantId {}

$resolver = new AttributeMatchingParameterResolver(
    TenantId::class,
    static fn($target, $context): array => [$target->position, 'tenant-1'],
);
```

Зарегистрируйте `$resolver` с целочисленным приоритетом через `ConfigProvider::getParameterResolvers()`. Метод `supports()` не должен изменять цепочку обработчиков или сохранять состояние отдельных операций разрешения.

## Определения и сочетания атрибутов

`AttributeDefinition` описывает класс атрибута и необязательный обработчик. Свойства `capabilities`, `requires`, `forbids`, `before` и `after` задают возможности атрибута, ограничения сочетаний и порядок исполнения. `CapabilityPolicy` позволяет ограничить число атрибутов с определённой возможностью у одной цели.

Фабрики обработчиков атрибутов и параметров могут получать зависимости из контейнера во время его сборки. Необходимые классы расширений должны быть доступны к моменту использования. Несовместимое изменение обнаруженных атрибутов может приводить к ошибке проверки вместо повторного исполнения уже завершённой операции.

`ContainerFactory::createWithTargetedAttributeDiscovery($config, $dependencies)` — дополнительный способ сборки, при котором проверка загрузки классов атрибутов ограничивается атрибутами, объявленными у текущего объекта или параметра. Основным способом остаётся `create()`.

## Стратегии создания и внешние контейнеры

Пользовательская стратегия явных определений реализует `DefinitionResolverInterface`: определяет подходящие виды определений, проверяет их и выполняет создание без собственной таблицы регистраций. Дополнительный способ поиска зависимостей реализует `EntryResolverInterface` и принимает `EntryParameters`. Изменения интерфейсов и конструкторов описаны в [руководстве по миграции](../migrations/di6-definitions.md).

`Container::addContainer()` добавляет внешний контейнер PSR-11. Он не может перекрывать защищённые внутренние службы и самостоятельно управляет повторным использованием своих значений. Если записи добавленного контейнера изменились, об этом можно сообщить через `notifyExternalEntriesChanged()`. См. [«Интерфейс контейнера»](container.md).
