# Ленивые объекты и виртуальные прокси

`makeLazy()` откладывает переданный initializer, а `makeProxy()` — переданную фабрику backing-объекта. Сервисы, создаваемые через reflection, выбирают эти стратегии атрибутами `#[Lazy]` и `#[Proxy]`; `#[Proxy]` также поддерживает явные точки внедрения. Для поддерживаемых классов создание не вызывает callback. Инициализация сохраняет порядок конструктора, внедрения свойств и setup, идентичность исключений callback, повторные попытки и нативную идентичность ghost/proxy. `#[NoConstructor]` подавляет только конструктор.

В точке внедрения `#[Make(...), Proxy]` поддерживает конкретный класс с private или protected конструктором, если выбранная прикладная фабрика умеет создавать backing-объект. При создании backing-класса через атрибуты можно использовать `#[NoConstructor]` с обычным жизненным циклом setup. Backing-объект создаётся при инициализации; вызовом конструктора управляет его фабрика либо политика reflection. Класс прокси должен оставаться конкретным, совместимым с объявленным типом и поддерживаться выбранным proxy-адаптером.

Стандартный нативный адаптер также требует **обычный, не ленивый backing-объект**, отличный от самого прокси. PHP принимает объект того же класса. Объект родительского класса допустим лишь тогда, когда класс прокси не добавляет свойств и не переопределяет `__destruct()` или `__clone()`. Прохождения проверки `instanceof` для backing-объекта дочернего класса недостаточно. Если в точке внедрения `#[Make('product'), Proxy]` объявлен родительский тип фактического продукта, укажите конкретный класс: `#[Make('product'), Proxy(ProductChild::class)] public ProductBase $product;`. PHP проверяет эти ограничения после возврата фабрики во время инициализации; их нарушения остаются нативными ошибками PHP. См. [требования PHP к backing-объекту](https://www.php.net/manual/en/reflectionclass.newlazyproxy.php).

В точке внедрения `#[Proxy]`, в том числе `#[Make(...), Proxy]`, DI дополнительно требует, чтобы backing-объект был экземпляром выбранного класса прокси, прежде чем передать его адаптеру. Поэтому объект родительского класса отклоняется с `ResolutionException`, даже если нативный прокси PHP допускает такой вариант. Нативное разрешение родительского класса не ослабляет этот контракт точки внедрения.

Не добавляйте `#[Proxy]` в точке внедрения к цели, которая уже создаётся лениво через `#[Lazy]` или `#[Proxy]` на классе: внутреннее создание вернёт ленивый backing-объект. Используйте `#[Inject]` для общего объекта либо `#[Make]` для нового, оставив выбор стратегии атрибуту класса. Если нужен внешний прокси, выберите обычную прикладную фабрику или `ClassDefinition`, создающие eager backing-объект по своему контракту инициализации. Эти ограничения принадлежат нативному адаптеру; пользовательские proxy-фабрики сохраняют собственные поддерживаемые механизмы.

Стандартный нативный `ProxyFactory` требует хотя бы одного **нестатического сохраняемого свойства экземпляра**. Подходят унаследованное private-свойство, backed get/set hook, readonly или promoted свойство с хранилищем. Классы без свойств, только со статическими свойствами или только с виртуальными hooks не подходят. Пустой `stdClass` и пустые потомки также не выполняют это требование; пользовательский потомок `stdClass` с сохраняемым свойством может оставаться ленивым.

Допустимый для нативного механизма класс без такого свойства получает `ResolutionException` до выделения целевого объекта. `serviceId` содержит каноническое имя класса; сообщение указывает `lazy ghost` или `virtual proxy`, отсутствие сохраняемых свойств и eager-создание как путь миграции. Вследствие выделения цели не вызываются initializer, фабрика, конструктор, setup, setter или деструктор; незавершённый результат не публикуется как shared-сервис. Этот намеренный отказ не создаёт искусственного предыдущего исключения. Другие ограничения PHP при выделении объекта сохраняют прежний путь ошибки и нативный `previous`, включая интерфейсы, traits, абстрактные классы, enum, неподдерживаемые внутренние классы и их потомков. Autoload класса и предшествующие эффекты прикладных расширений не откатываются.

Для обычного eager-создания через reflection следует убрать соответствующий lazy/proxy-маркер класса или точки внедрения. Замена `get()` на `make()` не отключает эти атрибуты. Другой eager-путь — явная обычная фабрика или `ClassDefinition` с их существующими контрактами: фабрика отвечает за инициализацию своего результата, а `ClassDefinition` выполняет конструктор и явные инструкции `call()`, игнорируя DI-атрибуты, включая `SetUp`. Необходимую инициализацию нужно настроить через выбранный путь. Один class-level `#[Proxy]` сам по себе не оборачивает результат непрозрачной прикладной фабрики.

Требование к свойствам принадлежит стандартному нативному адаптеру. Пользовательские реализации `ProxyFactoryInterface` могут использовать другие поддерживаемые механизмы и сохраняют ответственность за отложенные callbacks. Последующие исключения напрямую переданных callbacks для поддерживаемых классов остаются исключениями этих callbacks, если они не входят повторно в границу DI-разрешения. Адаптер не добавляет eager fallback или общую для контейнера проверку возможностей.
