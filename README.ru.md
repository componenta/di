# Componenta DI

**Ветка разработки DI 6, релиз ещё не выпущен.** В `refactor/di6-definitions-callbacks` реализованы согласованные планы определений и callbacks поверх v5.0.6. См. [миграцию определений](docs/migrations/di6-definitions.ru.md) и [миграцию callbacks/union](docs/migrations/di6-callbacks.ru.md). Исходники пока используют синтаксис, совместимый с PHP 8.4; окончательная минимальная patch-версия PHP и выпуск DI 6 зависят от E1 в [спецификации платформы](docs/plans/php85-callbacks.ru.md).

Componenta DI — контейнер внедрения зависимостей для PHP 8.4+, совместимый с PSR-11. Пакет поддерживает автосвязывание через reflection, явные фабрики и сервисы, упорядоченные делегаторы, вызов функций с разрешением аргументов, ленивые объекты, отображение HTTP-запросов и композицию PHP-атрибутов.

Пакет отвечает за создание контейнера и семантику разрешения зависимостей. [`componenta/config`](https://github.com/componenta/config/blob/main/README.ru.md) вызывает провайдеры и создаёт два раздельных значения:

- `Config` содержит только конфигурацию приложения;
- `DependencyDefinitions` передаётся один раз в `ContainerFactory` и не публикуется как сервис контейнера.

Во всех окружениях действует один путь создания контейнера. Componenta DI не компилирует фабрики и не сохраняет сериализованный граф зависимостей.

## Установка

```bash
composer require componenta/di
```

Требуются PHP 8.4+, Componenta Config 3.x, Componenta Caster, Componenta Reflection, Componenta Validation, интерфейсы PSR-11 2.x и PSR-7.

## Основной поток

```text
Environment + упорядоченные провайдеры
    -> ConfigFactory::create()
    -> ConfigComposition { Config, DependencyDefinitions }
    -> ContainerFactory::create()
    -> ContainerValue { container, тот же Config }
```

`ContainerFactory` — единственная публичная фабрика контейнера. Она сохраняет переданные экземпляры `Config` и `Environment` без копирования.

## Быстрый старт

```php
use Componenta\Config\ConfigFactory;
use Componenta\Config\ConfigProvider;
use Componenta\Config\ContainerValue;
use Componenta\Config\Environment;
use Componenta\DI\ContainerFactory;

final readonly class Greeting
{
    public function __construct(public string $message) {}
}

final class AppConfigProvider extends ConfigProvider
{
    protected function getConfig(): array
    {
        return ['greeting.prefix' => 'Привет'];
    }

    protected function getFactories(): array
    {
        return [
            Greeting::class => static fn(
                ContainerValue $context,
                array $params,
            ): Greeting => new Greeting(
                ($params['prefix'] ?? $context->config->string('greeting.prefix')) . '!',
            ),
        ];
    }
}

$environment = new Environment([]);
$composition = (new ConfigFactory())->create(
    $environment,
    new AppConfigProvider(),
);
$containerValue = (new ContainerFactory())->create(
    $composition->config,
    $composition->dependencies,
);
$container = $containerValue->container;

$shared = $container->get(Greeting::class);
$fresh = $container->make(Greeting::class, ['prefix' => 'Добро пожаловать']);

assert($shared->message === 'Привет!');
assert($fresh->message === 'Добро пожаловать!');
assert($containerValue->config === $composition->config);
assert($container->get(Environment::class) === $environment);
```

## Слияние провайдеров

`ConfigFactory` вызывает провайдеры в порядке аргументов и объединяет секции зависимостей до передачи результата в DI:

- factories, aliases, services и parameter resolvers являются реестрами по ключу; позднее значение заменяет раннее с тем же ключом;
- numeric invokables дописываются, а keyed invokables заменяются по ключу;
- цепочки delegators, attribute definitions и attribute capabilities дописываются в порядке провайдеров;
- флаги замены resolver-ов и определений атрибутов используют последнее явно переданное логическое значение.

DI один раз проверяет и нормализует объединённый `DependencyDefinitions` внутри `ContainerFactory::create()`. Пакет не вызывает провайдеры и не копирует определения зависимостей в `Config`.

`ConfigProvider` предоставляет защищённые методы:

```text
getConfig()
getFactories()
getInvokables()
getAliases()
getDelegators()
getServices()
getParameterResolvers()
shouldReplaceParameterResolvers()
getAttributeDefinitions()
shouldReplaceAttributeDefinitions()
getAttributeCapabilities()
```

## Определения зависимостей

### Сервисы

Готовые сервисы являются значениями времени выполнения и сохраняют состояние и идентичность. Допустимы объекты, замыкания, ресурсы, `null` и `false`.

```php
protected function getServices(): array
{
    return [
        ClockInterface::class => new SystemClock(),
        'feature.enabled' => false,
    ];
}
```

### Фабрики

Полная сигнатура фабрики времени выполнения — `(ContainerValue $context, array $params)`. Функция может объявить совместимый префикс этих аргументов. Ошибочная сигнатура отклоняется во время построения контейнера.

```php
protected function getFactories(): array
{
    return [
        Client::class => static fn(ContainerValue $context, array $params): Client =>
            new Client(
                $context->config->string('api.endpoint'),
                $params['timeout'] ?? 10,
            ),
    ];
}
```

Фабрика полностью отвечает за создание своего результата. После возврата результата контейнер не применяет к нему DI-атрибуты.

`ClassDefinition` — декларативная фабрика. Она немедленно вызывает публичный конструктор, затем исполняет явные инструкции `call()` в порядке регистрации, включая повторные вызовы одного метода:

```php
use Componenta\DI\Definition\ClassDefinition;
use Componenta\DI\Definition\Definition;

$definition = ClassDefinition::create(Client::class)
    ->constructor(['endpoint' => 'https://api.example.test', 'timeout' => 10])
    ->call('setLogger', [Definition::reference(LoggerInterface::class)]);
```

По умолчанию аргументы берутся только из определения, переопределений конструктора, переданных в `make()`, и значений параметров PHP по умолчанию. Переопределения `make()` сопоставляются с именами или позициями параметров конструктора; имя имеет приоритет перед позицией. Ключи с именами типов не являются аргументами конструктора. Заменённые ссылки не разрешаются, а runtime-значения остаются литеральными. `ReferenceDefinition` запрашивает зависимость через существующий контейнер; эта зависимость следует собственной регистрации и жизненному циклу.

Вложенные массивы аргументов `ClassDefinition` рекурсивно разрешают значения `ReferenceDefinition`. Циклический массив в `constructor()` или `call()` вызывает `InvalidConfigurationException`. Один нециклический массив можно использовать в нескольких аргументах. Значения, переданные через `make()` или возвращённые ссылками на сервисы, остаются литеральными.

Вызовите `autowire()` или `autowire(true)`, чтобы включить резервный поиск зависимостей по типу для отсутствующих аргументов конструктора и методов. Явные аргументы, включая `null`, имеют приоритет. Если для объявленного типа класса/интерфейса нет доступного сервиса, PHP по-прежнему применяет значение по умолчанию; отсутствие значения обязательного аргумента приводит к ошибке. `autowire(false)` отключает этот резервный поиск. Флаг не включает атрибуты параметров или пользовательские parameter-resolver-ы.

`ClassDefinition` никогда не исполняет DI-атрибуты целевого класса, его свойств, параметров конструктора или настроенных методов. Это относится к `SetUp`, `Inject`, `Lazy`, `Proxy` и `NoConstructor`, даже когда резервное автовнедрение включено. Ошибка конструктора или явного вызова метода прерывает создание; неудачный результат не становится общим. Последующий `get()` или `make()` начинает новую попытку создания.

Неиспользованные аргументы, явно настроенные в `constructor()` или `call()` для отражаемого метода без variadic, вызывают `InvalidConfigurationException` при разрешении: это касается неизвестных имён и лишних позиций. Посторонние runtime-ключи `make()` для фиксированных сигнатур по-прежнему игнорируются. Явные variadic-определения и вызовы магических методов сохраняют правила передачи аргументов PHP.

`constructor()`, `call()` и `autowire()` возвращают новые неизменяемые определения. `call()` заменяет прежний API `method()`. `DefinitionInterface` — маркерный интерфейс; он не требует общего свойства `value` у конкретных определений.

### Invokables и aliases

```php
protected function getInvokables(): array
{
    return [
        Logger::class,
        LoggerInterface::class => Logger::class,
    ];
}

protected function getAliases(): array
{
    return [
        CacheInterface::class => RedisCache::class,
    ];
}
```

Invokable с ключом регистрирует конкретный класс и alias.

### Delegators

Делегатор получает текущее значение сервиса и при необходимости контейнер. Делегаторы выполняются в порядке провайдеров и регистрации.

```php
protected function getDelegators(): array
{
    return [
        Client::class => [
            static fn(Client $client): Client => $client->withMetrics(),
            ['tracing.decorator', 'decorate'],
        ],
    ];
}
```

Отложенная пара «сервис–метод», например `['tracing.decorator', 'decorate']`, должна быть вложена в список цепочки. Это отличает её от цепочки из двух строковых делегаторов.

## API контейнера

`Container` реализует `Psr\Container\ContainerInterface`, `FactoryInterface`, `CallableExecutorInterface` и `ProxyFactoryInterface`.

```php
$shared = $container->get(Service::class);                 // общий результат
$exists = $container->has(Service::class);                 // не выбрасывает исключение
$fresh = $container->make(Service::class, ['id' => 42]);   // новый объект
$result = $container->call([$controller, 'show'], ['id' => 42]);
```

Если pipeline уже разрешил аргументы, передайте в call() адаптер PreparedCallable и окончательный список аргументов PHP. Для этого вызова DI не выполняет повторную инъекцию и обработку атрибутов. Именованные аргументы и значения по умолчанию работают по правилам PHP; variadic должен быть уже раскрыт. Адаптер предоставляет исходный callable перехватывающим executor. Декораторы executor передают адаптер и аргументы дальше без преобразования. Последующие обычные вызовы разрешают аргументы как прежде.

Если явная привязка отсутствует, конкретный класс создаётся через reflection. Явная фабрика имеет приоритет.

Автоматическое разрешение аргументов конструктора, `call()` и `SetUp` поддерживает variadic без отдельного аргумента контекста:

```php
$join = static fn(string ...$parts): string => implode('-', $parts);

$container->call($join, ['one', 'two']);              // 'one-two'
$container->call($join, ['parts' => ['one', 'two']]); // 'one-two'
$container->call($join);                            // ''
```

Массив под именем variadic-параметра задаёт всю коллекцию и имеет приоритет над позиционными значениями, даже если он пустой. Иначе хвост формируется из целочисленных ключей начиная с позиции variadic-параметра, в порядке возрастания позиций. Предыдущие параметры сохраняют обычные правила разрешения по имени, позиции, типу и значению по умолчанию. Посторонние строковые ключи, текущий request и объекты под ключами типов в хвост не добавляются. Автоматического поиска зависимостей для элементов variadic нет.

Каждый элемент должен соответствовать объявленному типу; для `array ...$items` каждый элемент сам является массивом. Строковые ключи внутри явно переданной коллекции становятся именованными variadic-аргументами. Они не могут перекрывать предыдущие параметры; позиционные элементы должны предшествовать именованным. Некорректная коллекция вызывает `ResolutionException`. Параметры по ссылке остаются неподдерживаемыми.

Резолверы параметров и источники-атрибуты могут возвращать variadic-коллекцию. Обработчики атрибутов и преобразователи запускаются один раз для всей коллекции; итоговые элементы проверяются перед вызовом. Если источник не задан, используется пустая коллекция. Раскрытие происходит при вызове, а состояние резолвера хранит одно значение для объявленного параметра.

Для встроенных функций и методов PHP необязательные аргументы остаются пропущенными, если разрешение дошло до стандартных значений по умолчанию. Пропуск отличается от явного `null`: `call('array_keys', ['array' => $data])` возвращает все ключи. Явные значения и пользовательские резолверы с более высоким приоритетом сохраняют приоритет.

`#[Env]` у variadic-параметра читает массив целиком, затем проверяется тип каждого элемента. Так же работают описатели окружения в `SetUp`; коллекция не преобразуется в один скаляр по типу элемента.

Строка `Class::method` и массив `[Class::class, 'method']` поддерживают `__call()` экземпляра. Магические методы получают переданные аргументы по правилам PHP, без автоматического разрешения параметров через reflection. Точный строковый идентификатор сервиса сохраняет приоритет над синтаксисом callable.

Методы изменения контейнера во время выполнения `set()`, `alias()`, `delegator()` и `addContainer()` сохраняются. Они инвалидируют затронутые общие значения и результаты делегаторов без полного перестроения контейнера. Нельзя заменить или затенить основные сервисы DI, `Config`, `Environment`, `ContainerValue` и `DependencyDefinitions`.

Если фабрика или делегатор меняет привязку во время уже начатого `get()` (в том числе при приостановленном Fiber), этот вызов может завершиться с прежним значением. Последующие обращения используют изменённую привязку: старый вызов не восстанавливает инвалидированные записи кеша.

## Атрибуты и отображение запросов

Встроенные атрибуты объектов и параметров:

```text
#[Config] #[Env] #[EntryId] #[Inject] #[Make]
#[Lazy] #[Proxy] #[NoConstructor] #[Init] #[SetUp] #[Cast] #[Transform]
#[CurrentRequest] #[CurrentUri]
#[Header] #[Cookie] #[QueryParam] #[PayloadParam]
#[RequestAttribute] #[ServerParam] #[UploadedFile]
#[MapRequest] #[MapQueryString] #[MapRequestPayload]
#[MapHeaders] #[MapCookies] #[MapRequestAttributes]
#[MapServerParams] #[MapUploadedFiles]
```

`#[CurrentRequest]` и `#[CurrentUri]` — явные источники, допустимые только во время вызова. Тип PSR-7 request или URI сам по себе не означает «текущий запрос», а такое значение нельзя сохранить через аргумент конструктора.

Отображение запроса читает явно выбранные источники PSR-7, обнаруживает конфликты, применяет настроенные преобразования и проверку данных, затем создаёт DTO через тот же `FactoryInterface::make()`.

## Точки расширения

Пользовательские resolver-ы параметров реализуют `ParameterResolverInterface` и регистрируются с целочисленным приоритетом. Пользовательские атрибуты описываются через `AttributeDefinition`; `CapabilityPolicy` задаёт ограничения количества и порядок композиции. Расширения передаются в `DependencyDefinitions` до построения контейнера: после этого цепочки параметров и атрибутов фиксируются.

`AttributeDefinition` владеет снимками массивов capabilities, селекторов и правил с момента создания, до вызова автозагрузчиков при валидации. Изменение переменной, связанной с элементом исходного массива через ссылку, не меняет зарегистрированную семантику, порядок обработчиков или выбор правил. Объекты обработчиков и правил сохраняют идентичность и актуальное состояние приложения; они не клонируются.

Фабрики расширений могут получать обычные зависимости из существующего контейнера. Сначала в порядке регистрации создаются определения атрибутов, затем резолверы параметров. Необходимое расширение атрибута должно быть зарегистрировано раньше фабрики, которая его использует. Если зависимость уже создана с неполной семантикой атрибутов или поздний резолвер мог бы перехватить разрешённый параметр раньше выбранного резолвера, `ContainerFactory::create()` выбрасывает `InvalidConfigurationException`. Проверка использует метаданные атрибутов и классификацию `supports()`, не повторяя конструкторы, обработчики и получение значений. Несвязанные расширения и резолверы с более низким приоритетом допустимы. Зависимость, которой нужен пользовательский резолвер параметров, можно получать в фабрике следующего резолвера либо отложить её получение до завершения создания контейнера.

Выборки `AttributePlan::all()` и `attributes()` сохраняют порядок общего плана, включая наследуемые capabilities и чередование повторяющихся классов атрибутов.

Правила композиции получают метаданные `AttributeUsage`, доступные только для чтения: объявленный класс и аргументы атрибута, его семантическое определение, место применения и порядок объявления. При каждом чтении `arguments` объявленные выражения вычисляются заново; объектные аргументы не сохраняются в общем плане. Поэтому выражение `new` может вызвать конструктор, когда правило явно читает аргументы. Пользовательские правила композиции проверяются при каждом разрешении. При регистрации таких правил DI не мемоизирует планы атрибутов, объектов и параметров: повторные вызовы учитывают актуальные аргументы и состояние правил. Фреймворк создаёт новый экземпляр атрибута только перед фактическим вызовом обработчика.

Если конструирование делает доступным другой объявленный атрибут, порядок исполнения пересчитывается без повторного создания ожидающего экземпляра атрибута. Новые обработчики должны сохранять уже исполненный порядок текущей фазы обработки объекта. Позднее изменение политики входных данных параметра или уже завершённой композиции свойства вызывает `AttributeCompositionException`; конструкторы и обработчики не запускаются повторно. Завершённые композиции параметров продолжают проверяться при разрешении следующих параметров, поэтому несовместимый поздний источник не может попасть в тело вызываемой функции. При создании объекта завершённая фаза before-instantiation проверяется перед вызовом конструктора; обе завершённые фазы объекта остаются под проверкой до конца финальной конфигурации и возврата. Это включает пустую фазу after-instantiation, если обработчик изначально не был доступен. Если конструктор, lifecycle hook или завершающий callback конфигурации открывает несовместимую политику, уже выполненные побочные эффекты не откатываются, а объект не возвращается как успешно разрешённый сервис. Загрузка несвязанных атрибутов допустима.

Lazy-объекты и виртуальные прокси сохраняют политики, выбранные в их исходной фазе before-instantiation. Если позднее эти политики становятся несовместимыми, инициализация завершается ошибкой без повторения этой фазы. Новый `make()` использует уже доступные атрибуты; ранее созданный отложенный объект не перенастраивается.

Внешний PSR-11 контейнер можно добавить через `Container::addContainer()`. Внешние сервисы участвуют в защите от циклов и не могут затенять защищённые основные сервисы.

## Поведение во время выполнения

`get()` кеширует общий результат вместе с результатом цепочки делегаторов. `make()` создаёт новый объект и принимает параметры времени выполнения. Метаданные reflection, подготовленные планы параметров и пути aliases кешируются только в памяти одного контейнера. При выборе resolver для записи без явного определения каждый раз проверяется её текущая доступность, включая состояние правил композиции.

Разработка и боевое окружение используют один `ContainerFactory`, одну нормализацию, проверку и цепочку разрешения. Значения зависимостей времени выполнения не экспортируются, поэтому несериализуемые значения ведут себя одинаково в обоих окружениях.

## Исключения

Ошибки пакета реализуют `Componenta\DI\Exception\ExceptionInterface`, который также расширяет контракт исключений контейнера PSR-11. Основные типы: `InvalidConfigurationException`, `NotFoundException`, `ResolutionException`, `CircularDependencyException`, `ConcurrentResolutionException`, `DelegatorException` и `AttributeCompositionException`.

Если регистрация определения или делегатора завершается ошибкой при проверке либо автозагрузке, `set()` и `delegator()` сохраняют существующее исключение Componenta либо оборачивают внешнюю ошибку в `InvalidConfigurationException`, оставляя исходный throwable в `getPrevious()`. Отказ до публикации изменения сохраняет прежнюю привязку и цепочку делегаторов; независимо завершённые мутации из прикладного кода не откатываются. После публикации все затронутые кеши и цепочки callable инвалидируются до освобождения заменённых корневых ссылок. Синхронно переданные ошибки освобождения становятся `MutationRetirementException`: его readonly `id` и упорядоченные `causes` описывают зафиксированную мутацию, а `getPrevious()` содержит первую причину. Переданное исключение может происходить от независимо зафиксированной вложенной мутации. Границы восстановления и времени жизни описаны в [руководстве миграции](docs/migrations/di6-definitions.ru.md).

После того как DI разрешил явно переданную функцию и передал ей управление, исключения из тела этой функции распространяются без изменения.

## Аудит и архитектурные планы

[Указатель архитектурных планов](docs/plans/README.ru.md) содержит проверенные спецификации, их статус готовности к реализации и полные русские переводы. Выбранные направления:

- **Доступность атрибутов:** сохранить исправленный опрос в текущей 5.x. B2 остаётся условным направлением, требующим обоснования затрат приложения и определённого контракта синхронизации; C не выбран.
- **Владение определениями:** реализовано в этой ветке. `CompositeResolver` владеет неизменяемыми регистрациями; стратегии выполняют переданные определения без собственных карт; все мутации регистрации завершаются до освобождения заменённых корневых ссылок.
