# Componenta DI

**Ветка разработки DI 6, релиз ещё не выпущен.** В `refactor/di6-definitions-callbacks` реализованы согласованные планы определений и callbacks поверх v5.0.6. См. [миграцию определений](docs/migrations/di6-definitions.ru.md) и [миграцию callbacks/union](docs/migrations/di6-callbacks.ru.md). DI 6 сохраняет PHP `^8.4`; новые inline/reference выражения в аргументах атрибутов требуют PHP 8.5. PHP 8.5.13 — минимальная проверенная стабильная patch-версия затронутых нативных trait-callable форм (E1); см. [спецификацию платформы](docs/plans/php85-callbacks.ru.md#8-версия-php-и-совместимость-релиза).

Componenta DI — контейнер внедрения зависимостей для PHP 8.4+, совместимый с PSR-11. Пакет поддерживает автосвязывание через reflection, явные фабрики и сервисы, упорядоченные делегаторы, вызов функций с разрешением аргументов, ленивые объекты, отображение HTTP-запросов и композицию PHP-атрибутов.

Пакет отвечает за создание контейнера и семантику разрешения зависимостей. [`componenta/config`](https://github.com/componenta/config/blob/main/README.ru.md) вызывает провайдеры и создаёт два раздельных значения:

- `Config` содержит только конфигурацию приложения;
- `DependencyDefinitions` передаётся один раз в `ContainerFactory` и не публикуется как сервис контейнера.

Во всех окружениях действует один путь создания контейнера. Componenta DI не компилирует фабрики и не сохраняет сериализованный граф зависимостей.

## Установка

```bash
composer require componenta/di
```

Требуются PHP 8.4+, Componenta Config 3.x, Componenta Caster, Componenta Reflection, Componenta Validation, интерфейсы PSR-11 2.x и PSR-7.

## Основной поток

```text
Environment + упорядоченные провайдеры
    -> ConfigFactory::create()
    -> ConfigComposition { Config, DependencyDefinitions }
    -> ContainerFactory::create()
    -> ContainerValue { container, тот же Config }
```

`ContainerFactory` — основной способ создания контейнера в приложении. Она сохраняет переданные экземпляры `Config` и `Environment` без копирования. Прямой `new Container(...)` также поддерживается через [контракт самостоятельной сборки](docs/migrations/di6-definitions.ru.md#прямое-создание-контейнера).

## Быстрый старт

```php
use Componenta\Config\ConfigFactory;
use Componenta\Config\ConfigProvider;
use Componenta\Config\ContainerValue;
use Componenta\Config\Environment;
use Componenta\DI\ContainerFactory;

final readonly class Greeting
{
    public function __construct(public string $message) {}
}

final class AppConfigProvider extends ConfigProvider
{
    protected function getConfig(): array
    {
        return ['greeting.prefix' => 'Привет'];
    }

    protected function getFactories(): array
    {
        return [
            Greeting::class => static fn(
                ContainerValue $context,
                array $params,
            ): Greeting => new Greeting(
                ($params['prefix'] ?? $context->config->string('greeting.prefix')) . '!',
            ),
        ];
    }
}

$environment = new Environment([]);
$composition = (new ConfigFactory())->create(
    $environment,
    new AppConfigProvider(),
);
$containerValue = (new ContainerFactory())->create(
    $composition->config,
    $composition->dependencies,
);
$container = $containerValue->container;

$shared = $container->get(Greeting::class);
$fresh = $container->make(Greeting::class, ['prefix' => 'Добро пожаловать']);

assert($shared->message === 'Привет!');
assert($fresh->message === 'Добро пожаловать!');
assert($containerValue->config === $composition->config);
assert($container->get(Environment::class) === $environment);
```

## Слияние провайдеров

`ConfigFactory` вызывает провайдеры в порядке аргументов и объединяет секции зависимостей до передачи результата в DI:

- factories, aliases, services и parameter resolvers являются реестрами по ключу; позднее значение заменяет раннее с тем же ключом;
- numeric invokables дописываются, а keyed invokables заменяются по ключу;
- цепочки delegators, attribute definitions и attribute capabilities дописываются в порядке провайдеров;
- флаги замены resolver-ов и определений атрибутов используют последнее явно переданное логическое значение.

DI один раз проверяет и нормализует объединённый `DependencyDefinitions` внутри `ContainerFactory::create()`. Пакет не вызывает провайдеры и не копирует определения зависимостей в `Config`.

`ConfigProvider` предоставляет защищённые методы:

```text
getConfig()
getFactories()
getInvokables()
getAliases()
getDelegators()
getServices()
getParameterResolvers()
shouldReplaceParameterResolvers()
getAttributeDefinitions()
shouldReplaceAttributeDefinitions()
getAttributeCapabilities()
```

## Определения зависимостей

### Сервисы

Готовые сервисы являются значениями времени выполнения и сохраняют состояние и идентичность. Допустимы объекты, замыкания, ресурсы, `null` и `false`.

```php
protected function getServices(): array
{
    return [
        ClockInterface::class => new SystemClock(),
        'feature.enabled' => false,
    ];
}
```

### Фабрики

Полная сигнатура фабрики времени выполнения — `(ContainerValue $context, array $params)`. Функция может объявить совместимый префикс этих аргументов. Известные непосредственные callable, кроме строк, проверяются при регистрации определений, в том числе при построении контейнера. Строки и ещё не разрешённые спецификации методов сервисов разрешаются и проверяются при обращении к фабрике; регистрация не создаёт объект отложенной фабрики.

```php
protected function getFactories(): array
{
    return [
        Client::class => static fn(ContainerValue $context, array $params): Client =>
            new Client(
                $context->config->string('api.endpoint'),
                $params['timeout'] ?? 10,
            ),
    ];
}
```

Фабрика полностью отвечает за создание своего результата. После возврата результата контейнер не применяет к нему DI-атрибуты.

`ClassDefinition` — декларативная фабрика. Она немедленно вызывает публичный конструктор, затем исполняет явные инструкции `call()` в порядке регистрации, включая повторные вызовы одного метода:

```php
use Componenta\DI\Definition\ClassDefinition;
use Componenta\DI\Definition\Definition;

$definition = ClassDefinition::create(Client::class)
    ->constructor(['endpoint' => 'https://api.example.test', 'timeout' => 10])
    ->call('setLogger', [Definition::reference(LoggerInterface::class)]);
```

По умолчанию аргументы берутся только из определения, переопределений конструктора, переданных в `make()`, и значений параметров PHP по умолчанию. Переопределения `make()` сопоставляются с именами или позициями параметров конструктора; имя имеет приоритет перед позицией. Ключи с именами типов не являются аргументами конструктора. Заменённые ссылки не разрешаются, а runtime-значения остаются литеральными. `ReferenceDefinition` запрашивает зависимость через существующий контейнер; эта зависимость следует собственной регистрации и жизненному циклу.

Вложенные массивы аргументов `ClassDefinition` рекурсивно разрешают значения `ReferenceDefinition`. Циклический массив в `constructor()` или `call()` вызывает `InvalidConfigurationException`. Один нециклический массив можно использовать в нескольких аргументах. Значения, переданные через `make()` или возвращённые ссылками на сервисы, остаются литеральными.

Вызовите `autowire()` или `autowire(true)`, чтобы включить резервный поиск зависимостей по типу для отсутствующих аргументов конструктора и методов. Явные аргументы, включая `null`, имеют приоритет. Если для объявленного типа класса/интерфейса нет доступного сервиса, PHP по-прежнему применяет значение по умолчанию; отсутствие значения обязательного аргумента приводит к ошибке. `autowire(false)` отключает этот резервный поиск. Флаг не включает атрибуты параметров или пользовательские parameter-resolver-ы.

`ClassDefinition` никогда не исполняет DI-атрибуты целевого класса, его свойств, параметров конструктора или настроенных методов. Это относится к `SetUp`, `Inject`, `Lazy`, `Proxy` и `NoConstructor`, даже когда резервное автовнедрение включено. Ошибка конструктора или явного вызова метода прерывает создание; неудачный результат не становится общим. Последующий `get()` или `make()` начинает новую попытку создания.

Неиспользованные аргументы, явно настроенные в `constructor()` или `call()` для отражаемого метода без variadic, вызывают `InvalidConfigurationException` при разрешении: это касается неизвестных имён и лишних позиций. Посторонние runtime-ключи `make()` для фиксированных сигнатур по-прежнему игнорируются. Явные variadic-определения и вызовы магических методов сохраняют правила передачи аргументов PHP.

`constructor()`, `call()` и `autowire()` возвращают новые неизменяемые определения. `call()` заменяет прежний API `method()`. `DefinitionInterface` — маркерный интерфейс; он не требует общего свойства `value` у конкретных определений.

### Invokables и aliases

```php
protected function getInvokables(): array
{
    return [
        Logger::class,
        LoggerInterface::class => Logger::class,
    ];
}

protected function getAliases(): array
{
    return [
        CacheInterface::class => RedisCache::class,
    ];
}
```

Invokable с ключом регистрирует конкретный класс и alias. Invokable напрямую вызывает конструктор без аргументов, используя значения PHP по умолчанию и не обрабатывая DI-атрибуты. Ошибка конструктора сохраняет существующее исключение Componenta, включая исходную диагностику циклической зависимости; внешняя ошибка становится `ResolutionException` с исходным throwable в `getPrevious()`. Неудачный результат не сохраняется как общий сервис, и последующее разрешение может повторить попытку.

### Delegators

Делегатор получает текущее значение сервиса и при необходимости контейнер. Делегаторы выполняются в порядке провайдеров и регистрации.

```php
protected function getDelegators(): array
{
    return [
        Client::class => [
            static fn(Client $client): Client => $client->withMetrics(),
            ['tracing.decorator', 'decorate'],
        ],
    ];
}
```

Отложенная пара «сервис–метод», например `['tracing.decorator', 'decorate']`, должна быть вложена в список цепочки. Это отличает её от цепочки из двух строковых делегаторов.

## API контейнера

`Container` реализует `Psr\Container\ContainerInterface`, `FactoryInterface`, `CallableExecutorInterface` и `ProxyFactoryInterface`.

```php
$shared = $container->get(Service::class);                 // общий результат
$exists = $container->has(Service::class);                 // идентификатор известен
$fresh = $container->make(Service::class, ['id' => 42]);   // объект из конвейера создания
$result = $container->call([$controller, 'show'], ['id' => 42]);
```

Если pipeline уже разрешил аргументы, передайте в call() адаптер PreparedCallable и окончательный список аргументов PHP. Для этого вызова DI не выполняет повторную инъекцию и обработку атрибутов. Именованные аргументы и значения по умолчанию работают по правилам PHP; variadic должен быть уже раскрыт. Адаптер предоставляет исходный callable перехватывающим executor. Декораторы executor передают адаптер и аргументы дальше без преобразования. Последующие обычные вызовы разрешают аргументы как прежде.

Prepared-адаптер передаёт аргументы по значению и не поддерживает параметры по ссылке. Если нативному callable нужны ссылки, передайте исходный callable непосредственно в `CallableInvoker` и массив аргументов с этими ссылками.

Если явная привязка отсутствует, конкретный класс создаётся через reflection. Явная фабрика имеет приоритет.

`has()` возвращает `true`, если идентификатор известен и его конфигурация приведёт к ошибке при разрешении. Эту ошибку сообщает `get()`. Если провайдер завершает проверку владения идентификатором с ошибкой, оба метода сообщают о ней исключением контейнера PSR-11. Автоматическая подстановка аргументов может использовать значение по умолчанию, если тип необязательного параметра невозможно разрешить.

Автоматическое разрешение аргументов конструктора, `call()` и `SetUp` поддерживает variadic без отдельного аргумента контекста:

```php
$join = static fn(string ...$parts): string => implode('-', $parts);

$container->call($join, ['one', 'two']);              // 'one-two'
$container->call($join, ['parts' => ['one', 'two']]); // 'one-two'
$container->call($join);                            // ''
```

Массив под именем variadic-параметра задаёт всю коллекцию и имеет приоритет над позиционными значениями, даже если он пустой. Иначе хвост формируется из целочисленных ключей начиная с позиции variadic-параметра, в порядке возрастания позиций. Предыдущие параметры сохраняют обычные правила разрешения по имени, позиции, типу и значению по умолчанию. Посторонние строковые ключи, текущий request и объекты под ключами типов в хвост не добавляются. Автоматического поиска зависимостей для элементов variadic нет.

Каждый элемент должен соответствовать объявленному типу; для `array ...$items` каждый элемент сам является массивом. Строковые ключи внутри явно переданной коллекции становятся именованными variadic-аргументами. Они не могут перекрывать предыдущие параметры; позиционные элементы должны предшествовать именованным. Некорректная коллекция вызывает `ResolutionException`. Параметры по ссылке остаются неподдерживаемыми.

Резолверы параметров и источники-атрибуты могут возвращать variadic-коллекцию. Обработчики атрибутов и преобразователи запускаются один раз для всей коллекции; итоговые элементы проверяются перед вызовом. Если источник не задан, используется пустая коллекция. Раскрытие происходит при вызове, а состояние резолвера хранит одно значение для объявленного параметра.

Для встроенных функций и методов PHP необязательные аргументы остаются пропущенными, если разрешение дошло до стандартных значений по умолчанию. Пропуск отличается от явного `null`: `call('array_keys', ['array' => $data])` возвращает все ключи. Явные значения и пользовательские резолверы с более высоким приоритетом сохраняют приоритет.

`#[Env]` у variadic-параметра читает массив целиком, затем проверяется тип каждого элемента. Так же работают описатели окружения в `SetUp`; коллекция не преобразуется в один скаляр по типу элемента.

Строка `Class::method` и массив `[Class::class, 'method']` поддерживают `__call()` экземпляра. Магические методы получают переданные аргументы по правилам PHP, без автоматического разрешения параметров через reflection. Точный строковый идентификатор сервиса сохраняет приоритет над синтаксисом callable.

Методы изменения контейнера во время выполнения `set()`, `alias()`, `delegator()` и `addContainer()` сохраняются. Они инвалидируют затронутые общие значения и результаты делегаторов без полного перестроения контейнера. Нельзя заменить или затенить основные сервисы DI, `Config`, `Environment`, `ContainerValue` и `DependencyDefinitions`.

Если фабрика или делегатор меняет привязку во время уже начатого `get()` (в том числе при приостановленном Fiber), этот вызов может завершиться с прежним значением. Последующие обращения используют изменённую привязку: старый вызов не восстанавливает инвалидированные записи кеша.

## Ленивые объекты и виртуальные прокси

`makeLazy()` откладывает переданный initializer, а `makeProxy()` — переданную фабрику backing-объекта. Сервисы, создаваемые через reflection, выбирают эти стратегии атрибутами `#[Lazy]` и `#[Proxy]`; `#[Proxy]` также поддерживает явные точки внедрения. Для поддерживаемых классов создание не вызывает callback. Инициализация сохраняет порядок конструктора, внедрения свойств и setup, идентичность исключений callback, повторные попытки и нативную идентичность ghost/proxy. `#[NoConstructor]` подавляет только конструктор.

В точке внедрения `#[Make(...), Proxy]` поддерживает конкретный класс с private или protected конструктором, если выбранная прикладная фабрика умеет создавать backing-объект. При создании backing-класса через атрибуты можно использовать `#[NoConstructor]` с обычным жизненным циклом setup. Backing-объект создаётся при инициализации; вызовом конструктора управляет его фабрика либо политика reflection. Класс прокси должен оставаться конкретным, совместимым с объявленным типом и поддерживаться выбранным proxy-адаптером.

Стандартный нативный адаптер также требует **обычный, не ленивый backing-объект**, отличный от самого прокси. PHP принимает объект того же класса. Объект родительского класса допустим лишь тогда, когда класс прокси не добавляет свойств и не переопределяет `__destruct()` или `__clone()`. Прохождения проверки `instanceof` для backing-объекта дочернего класса недостаточно. Если в точке внедрения `#[Make('product'), Proxy]` объявлен родительский тип фактического продукта, укажите конкретный класс: `#[Make('product'), Proxy(ProductChild::class)] public ProductBase $product;`. PHP проверяет эти ограничения после возврата фабрики во время инициализации; их нарушения остаются нативными ошибками PHP. См. [требования PHP к backing-объекту](https://www.php.net/manual/en/reflectionclass.newlazyproxy.php).

В точке внедрения `#[Proxy]`, в том числе `#[Make(...), Proxy]`, DI дополнительно требует, чтобы backing-объект был экземпляром выбранного класса прокси, прежде чем передать его адаптеру. Поэтому объект родительского класса отклоняется с `ResolutionException`, даже если нативный прокси PHP допускает такой вариант. Нативное разрешение родительского класса не ослабляет этот контракт точки внедрения.

Не добавляйте `#[Proxy]` в точке внедрения к цели, которая уже создаётся лениво через `#[Lazy]` или `#[Proxy]` на классе: внутреннее создание вернёт ленивый backing-объект. Используйте `#[Inject]` для общего объекта либо `#[Make]` для нового, оставив выбор стратегии атрибуту класса. Если нужен внешний прокси, выберите обычную прикладную фабрику или `ClassDefinition`, создающие eager backing-объект по своему контракту инициализации. Эти ограничения принадлежат нативному адаптеру; пользовательские proxy-фабрики сохраняют собственные поддерживаемые механизмы.

Стандартный нативный `ProxyFactory` требует хотя бы одного **нестатического сохраняемого свойства экземпляра**. Подходят унаследованное private-свойство, backed get/set hook, readonly или promoted свойство с хранилищем. Классы без свойств, только со статическими свойствами или только с виртуальными hooks не подходят. Пустой `stdClass` и пустые потомки также не выполняют это требование; пользовательский потомок `stdClass` с сохраняемым свойством может оставаться ленивым.

Допустимый для нативного механизма класс без такого свойства получает `ResolutionException` до выделения целевого объекта. `serviceId` содержит каноническое имя класса; сообщение указывает `lazy ghost` или `virtual proxy`, отсутствие сохраняемых свойств и eager-создание как путь миграции. Вследствие выделения цели не вызываются initializer, фабрика, конструктор, setup, setter или деструктор; незавершённый результат не публикуется как shared-сервис. Этот намеренный отказ не создаёт искусственного предыдущего исключения. Другие ограничения PHP при выделении объекта сохраняют прежний путь ошибки и нативный `previous`, включая интерфейсы, traits, абстрактные классы, enum, неподдерживаемые внутренние классы и их потомков. Autoload класса и предшествующие эффекты прикладных расширений не откатываются.

Для обычного eager-создания через reflection следует убрать соответствующий lazy/proxy-маркер класса или точки внедрения. Замена `get()` на `make()` не отключает эти атрибуты. Другой eager-путь — явная обычная фабрика или `ClassDefinition` с их существующими контрактами: фабрика отвечает за инициализацию своего результата, а `ClassDefinition` выполняет конструктор и явные инструкции `call()`, игнорируя DI-атрибуты, включая `SetUp`. Необходимую инициализацию нужно настроить через выбранный путь. Один class-level `#[Proxy]` сам по себе не оборачивает результат непрозрачной прикладной фабрики.

Требование к свойствам принадлежит стандартному нативному адаптеру. Пользовательские реализации `ProxyFactoryInterface` могут использовать другие поддерживаемые механизмы и сохраняют ответственность за отложенные callbacks. Последующие исключения напрямую переданных callbacks для поддерживаемых классов остаются исключениями этих callbacks, если они не входят повторно в границу DI-разрешения. Адаптер не добавляет eager fallback или общую для контейнера проверку возможностей. [Реализованный план](docs/plans/propertyless-lazy-lifecycle.ru.md) описывает обоснование и границы совместимости.

## Атрибуты и отображение запросов

Встроенные атрибуты объектов и параметров:

```text
#[Config] #[Env] #[EntryId] #[Inject] #[Make]
#[Lazy] #[Proxy] #[NoConstructor] #[Init] #[SetUp] #[Cast] #[Transform]
#[CurrentRequest] #[CurrentUri]
#[Header] #[Cookie] #[QueryParam] #[PayloadParam]
#[RequestAttribute] #[ServerParam] #[UploadedFile]
#[MapRequest] #[MapQueryString] #[MapRequestPayload]
#[MapHeaders] #[MapCookies] #[MapRequestAttributes]
#[MapServerParams] #[MapUploadedFiles]
```

`#[CurrentRequest]` и `#[CurrentUri]` — явные источники, допустимые только во время вызова. Тип PSR-7 request или URI сам по себе не означает «текущий запрос», а такое значение нельзя сохранить через аргумент конструктора.

Отображение запроса читает явно выбранные источники PSR-7, обнаруживает конфликты, применяет настроенные преобразования и проверку данных, затем создаёт DTO через тот же `FactoryInterface::make()`.

HTTP-данные отклоняются, если они подставляют значение параметра, чей атрибут распознан как явный источник, например `#[EntryId]`. Если источник обнаружен поздно при подготовке метаданных или зависимостей, DI повторяет проверку до передачи значения ожидающему resolver, обработчику атрибута, callback `Transform` или caster в `Cast`. Проверка также выполняется между параметрами зависимостей callback `Transform`.

Проверяется весь переданный массив, включая значения соседних параметров; после завершающей подготовки параметров и конструктора проверка повторяется до передачи аргументов конструктору или вызову `SetUp`. Каждое чтение `ObjectCreationContext::parameters` проверяет текущую попытку создания до выдачи массива; обработчики, которые его не читают, не запускают отложенные поставщики параметров.

Перед возвратом DTO DI освобождает входные данные, принадлежавшие мапперу, и перепроверяет источники, которые использовали конструктор и `SetUp` этого DTO.

Уже начавший работу callback или расширение может выполнить побочные эффекты: они не откатываются и не повторяются, а несовместимое позднее изменение по-прежнему препятствует успешному завершению DTO или callable. Сведения о происхождении данных остаются внутренними и не добавляются в контексты пользовательских resolver-ов или обработчиков.

`MapRequest(afterMap: ...)` позволяет дополнительно преобразовать весь отображённый массив до создания DTO, разрешая зависимости остальных параметров callback через DI. Проверка исходных данных по-прежнему выполняется первой; результат должен быть массивом и проходит итоговые проверки источников. `afterMap: null` сохраняет прежний путь. Атрибуты отдельных источников, пользовательские подклассы mapper, декларативные опции, отдельный вызов `transform()`, массив вместе с `Transform` и прикладные адаптеры обработчиков поддерживаются. Пользовательские адаптеры запросов получают настроенный `RequestAttributeHandler` по имени его класса. Полные примеры для PHP 8.4/8.5 и протокол пользовательского mapper приведены в [сравнении существующих и callback-вариантов](docs/plans/request-mapping-examples.ru.md) ([English](docs/plans/request-mapping-examples.md)).

## Точки расширения

Пользовательские resolver-ы параметров реализуют `ParameterResolverInterface` и регистрируются с целочисленным приоритетом. Пользовательские атрибуты описываются через `AttributeDefinition`; его селекторы `before` и `after` задают порядок композиции. `CapabilityPolicy` ограничивает количество атрибутов с указанной capability на одной цели. Расширения передаются в `DependencyDefinitions` до построения контейнера: после этого цепочки параметров и атрибутов фиксируются.

`AttributeDefinition` владеет снимками массивов capabilities, селекторов и правил с момента создания, до вызова автозагрузчиков при валидации. Изменение переменной, связанной с элементом исходного массива через ссылку, не меняет зарегистрированную семантику, порядок обработчиков или выбор правил. Объекты обработчиков и правил сохраняют идентичность и актуальное состояние приложения; они не клонируются.

Фабрики расширений могут получать обычные зависимости из существующего контейнера. Сначала в порядке регистрации создаются определения атрибутов, затем резолверы параметров. Регистрируйте необходимые расширения атрибутов раньше фабрик, которые их используют. `ContainerFactory::create()` выбрасывает `InvalidConfigurationException`, если bootstrap обнаруживает несовместимые метаданные атрибутов или находит вновь применимый резолвер перед уже выбранным в цепочке. Bootstrap проверяет метаданные атрибутов и повторно проверяет `supports()` на доступных целях. Результаты и побочные эффекты завершённых вызовов сохраняются. Несвязанные расширения и резолверы с более низким приоритетом допустимы.

Подготовьте классы и алиасы, влияющие на пользовательскую классификацию параметров, до первого разрешения, которое от них зависит. Это относится и к запросам алиаса во временных замыканиях, цель которых может исчезнуть до итоговой проверки. Зависимость можно получить в следующей фабрике, когда нужные резолвер и метаданные готовы, или отложить её получение до их доступности.

Если применимость резолвера определяется одним атрибутом, зарегистрируйте `AttributeMatchingParameterResolver($attribute, $resolve)` с нужным приоритетом. Он выбирает параметры через `ParameterTarget::hasAttribute()`. Callback получает цель и контекст разрешения и возвращает `[$target->position, $value]` либо `null` для продолжения цепочки. Bootstrap может перепроверить это условие по уже загруженным объявлениям после освобождения временной цели.

Для параметра с объявленными атрибутами вызовите `$target->watchAttributeAvailability($name)` в пользовательском `supports()` перед проверкой имени через нативный рефлектор. Метод регистрирует ещё не объявленный класс, интерфейс или алиас без вызова автозагрузчика. После объявления имени следующее разрешение затронутой кешированной цели повторит классификацию.

Контейнер создаёт снимок спецификации фабрики расширения `[owner, method]` в начале материализации этого расширения, до проверки callable и разрешения владельца. Переназначение ссылочных переменных вызывающего кода не перенаправляет текущий вызов; изменения до начала материализации следующего расширения остаются видимыми. Объекты фабрик сохраняют идентичность и актуальное состояние приложения.

Выборки `AttributePlan::all()` и `attributes()` сохраняют порядок общего плана, включая наследуемые capabilities и чередование повторяющихся классов атрибутов.

Правила композиции получают метаданные `AttributeUsage`, доступные только для чтения: объявленный класс и аргументы атрибута, его семантическое определение, место применения и порядок объявления. При каждом чтении `arguments` объявленные выражения вычисляются заново; объектные аргументы не сохраняются в общем плане. Поэтому выражение `new` может вызвать конструктор, когда правило явно читает аргументы. Применимые пользовательские правила композиции выполняются при каждом разрешении, поэтому повторные вызовы учитывают актуальные аргументы и состояние правил. DI может кешировать планы, которые не зависят от пользовательских правил. Фреймворк создаёт новый экземпляр атрибута только перед фактическим вызовом обработчика.

Если конструирование делает доступным другой объявленный атрибут, порядок исполнения пересчитывается без повторного создания ожидающего экземпляра атрибута. Новые обработчики должны сохранять уже исполненный порядок текущей фазы обработки объекта. Позднее изменение политики входных данных параметра или уже завершённой композиции свойства вызывает `AttributeCompositionException`; конструкторы и обработчики не запускаются повторно. Завершённые композиции параметров продолжают проверяться при разрешении следующих параметров, поэтому несовместимый поздний источник не может попасть в тело вызываемой функции. При создании объекта завершённая фаза before-instantiation проверяется перед вызовом конструктора; обе завершённые фазы объекта остаются под проверкой до конца финальной конфигурации и возврата. Это включает пустую фазу after-instantiation, если обработчик изначально не был доступен. Если конструктор, lifecycle hook или завершающий callback конфигурации открывает несовместимую политику, уже выполненные побочные эффекты не откатываются, а объект не возвращается как успешно разрешённый сервис. Загрузка несвязанных атрибутов допустима.

Lazy-объекты и виртуальные прокси сохраняют политики, выбранные в их исходной фазе before-instantiation. Если позднее эти политики становятся несовместимыми, инициализация завершается ошибкой без повторения этой фазы. Новый `make()` использует уже доступные атрибуты; ранее созданный отложенный объект не перенастраивается.

При обычном создании через `ObjectPipeline::create(resolveParameters: ...)` DI перед возвратом проверяет атрибуты, которые стали доступны при освобождении аргументов, принадлежавших текущей попытке. Для нативных lazy-объектов и виртуальных прокси проверка охватывает работу DI-инициализатора или фабрики backing-объекта. PHP может освобождать захваченные значения после завершения этого вызова.

Внешний PSR-11 контейнер можно добавить через `Container::addContainer()`. Внешние сервисы участвуют в защите от циклов и не могут затенять защищённые основные сервисы.

Пользовательские fallback-резолверы получают аргументы через `EntryParameters`. Передавайте этот объект, когда создание продолжает другой резолвер или оно откладывается до инициализации. См. [руководство по миграции](docs/migrations/di6-definitions.ru.md#пользовательские-fallback-резолверы).

## Поведение во время выполнения

Для локальных записей `get()` кеширует общий результат вместе с результатом цепочки делегаторов запрошенного ID. Если запрошенным ID владеет внешний контейнер, каждый результат `get()` поступает непосредственно из него; внешний контейнер определяет, будет ли значение общим. Локальные кеши результатов и делегаторы к такому результату не применяются.

`make()` при каждом вызове разрешает локальное определение или использует резервную стратегию и принимает параметры времени выполнения. Он не использует общие значения, внешние контейнеры и делегаторы и требует объект в результате. Фабрика по-прежнему определяет идентичность своего результата и может вернуть существующий объект.

Метаданные reflection, подготовленные планы параметров и пути aliases кешируются только в памяти одного контейнера. При выборе resolver для записи без явного определения каждый раз проверяется её текущая доступность, включая состояние правил композиции.

Разработка и боевое окружение используют один `ContainerFactory`, одну нормализацию, проверку и цепочку разрешения. Значения зависимостей времени выполнения не экспортируются, поэтому несериализуемые значения ведут себя одинаково в обоих окружениях.

## Исключения

Ошибки пакета реализуют `Componenta\DI\Exception\ExceptionInterface`, который также расширяет контракт исключений контейнера PSR-11. Основные типы: `InvalidConfigurationException`, `NotFoundException`, `ResolutionException`, `CircularDependencyException`, `ConcurrentResolutionException`, `DelegatorException` и `AttributeCompositionException`.

Если регистрация определения или делегатора завершается ошибкой при проверке либо автозагрузке, `set()` и `delegator()` сохраняют существующее исключение Componenta либо оборачивают внешнюю ошибку в `InvalidConfigurationException`, оставляя исходный throwable в `getPrevious()`. Отказ до публикации изменения сохраняет прежнюю привязку и цепочку делегаторов; независимо завершённые мутации из прикладного кода не откатываются. После публикации все затронутые кеши и цепочки callable инвалидируются до освобождения заменённых корневых ссылок. Синхронно переданные ошибки освобождения становятся `MutationRetirementException`: его readonly `id` и упорядоченные `causes` описывают зафиксированную мутацию, а `getPrevious()` содержит первую причину. Переданное исключение может происходить от независимо зафиксированной вложенной мутации. Границы восстановления и времени жизни описаны в [руководстве миграции](docs/migrations/di6-definitions.ru.md).

После того как DI разрешил явно переданную функцию и передал ей управление, исключения из тела этой функции распространяются без изменения.

Изменения публичных расширений описаны в [руководстве миграции определений](docs/migrations/di6-definitions.ru.md).

Пакет сохраняет PHP `^8.4`; затронутые нативные trait-callable формы проходят E1 на стабильном PHP 8.5.13 — минимальной проверенной patch-версии этих форм.

B2 для опроса отсутствующих атрибутов остаётся отдельным будущим направлением.
